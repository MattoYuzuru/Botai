# Подробная диагностика подключения

Связанные требования: FR-005–FR-008, FR-016, NFR-013. Режим помогает проследить новое
подключение от сообщения до результата: по одному `thread_id`, `job_id` или `connection_id`.
Он не восстанавливает подробности прошлых проходов, которые система не записывала.

## Включение и выключение

В GitHub откройте **Actions → deploy → Run workflow**, выберите актуальный `main`
с успешным CI и значение `diagnostics`:

| Значение | Результат |
|---|---|
| `keep` | Сохранить текущий режим сервера; при первом деплое диагностика выключена |
| `on` | Включить подробную диагностику |
| `off` | Выключить запись новых диагностических событий |

То же через GitHub CLI:

```bash
gh workflow run deploy.yml --ref main -f diagnostics=on
gh workflow run deploy.yml --ref main -f diagnostics=off
```

Каждый запуск проходит обычную сборку и деплой. Выбор начинает действовать после успешного
обновления контейнеров, а не в момент нажатия кнопки. Автодеплой зелёного `main` сохраняет
выбранный режим. Устаревший SHA или версия без успешного CI не выкладываются даже при
ручном запуске. Проверить режим без чтения секретной конфигурации:

```bash
ssh -T mnema 'sudo -n docker exec botai-worker-1 printenv BOTAI_DIAGNOSTICS'
```

Источник режима на сервере — `BOTAI_DIAGNOSTICS=true|false` в `/srv/botai/compose.vars`.
Docker Compose передаёт его API, воркеру и прокси. Файл также содержит пароль БД:
не выводите его целиком. Ручное редактирование файла не меняет уже работающий процесс;
штатный способ применения — деплой. `remote-deploy.sh TAG keep|on|off` проверяет выбор до
чтения входных секретов. Если обновление не прошло, возвращаются предыдущий образ и
предыдущий режим диагностики. При неудаче проверки отката скрипт завершает работу с ошибкой.

## Какие данные записываются

События содержат время, компонент, идентификаторы связи, этап, результат, статический код
причины, счётчики и длительности. Для адресов используются отпечатки, глубина пути и число
параметров: по ним можно сопоставить переходы, не сохраняя личные значения адреса.
Диагностика показывает, например, прошла ли API-проверка сессии, был ли восстановлен токен,
сколько страниц просмотрено, откуда исчезла выборка и на каком шаге отклонён рецепт.

События поиска показывают выбранного провайдера, код причины fallback/cooldown,
количество результатов и задержки. Они не содержат query, выдачу или ключи. API-проба,
авторизованный DOM, проверенный canary и успешный sync остаются разными этапами;
публичный результат поиска не заменяет ни один из последних трёх.

`auth.session.request` различает обычное, принудительное и явно ручное восстановление
по `force`/`manual_login`. `auth.entry_ready` с `entry_verified=true` означает проверку
запрошенной страницы браузером, а не только API-пробу. Адрес представлен прежними
отпечатками и счётчиками path/query; личный путь не записывается. Эти события не
подтверждают получение учебных данных — для этого нужны canary и sync.

`canary.candidate` различает индекс кандидата, `auth_type` (`none/cookie/bearer`),
`transport` (`http/rendered`), фазу запроса/ответа и результат проверки. Это названия режимов,
не значения credentials. `auth.source_response` добавляет фактический HTTP status,
признак редиректа и отказа replay, а адрес оставляет отпечатком. Отказ отдельного replay
ещё не доказывает потерю браузерного входа.

`browser.auth_permit` и `browser.auth_permit_refused` показывают окно шага входа
([security.md](../architecture/security.md) §0.2). `browser.auth_permit` с `phase=request` — окно
открыто для auth-фрейма (`window_ms`, `allow_host_count`), `outcome=rejected` с причиной — не
открыто. С `phase=response` — POST пропущен: `navigation` отличает отправку формы от XHR/fetch,
`post_count` — сколько запросов уже взяло окно. `browser.auth_permit_refused` — POST отклонён,
запрос до сервера не дошёл. Причины (`reason`): `auth_read_only` (входная страница ещё проверяется),
`auth_no_permit` (нет окна: шага человека не было), `auth_window_expired` (окно старше 15 с),
`auth_context_changed` (документ или страница сменились), `auth_host_not_allowed` (хост не из
входа подключения), `auth_window_exhausted` (больше четырёх POST на окно), `auth_ui_missing`
(фрейм больше не показывает вход), `auth_scan_failed` (не удалось проверить фрейм). Пример разбора:
`auth_no_permit` или `auth_read_only` на POST при загрузке страницы — телеметрия, её остановка
нормальна; `auth_host_not_allowed` перед `request_failed` с `blocked_by_client=true` и
`navigation=true` — форма отправлялась на чужой хост. Поля формы, query values и ввод не
записываются; адреса — только отпечатками.

`auth.guard_refused` фиксирует, что guard остановил запрос входа и поток открыл запасной экран
(`fallback=true`) либо завершился с `error_code=login_guard_refused`. Этот код означает отказ нашего
guard, а не недоступность сайта: для недоступного сайта остаётся `source_unavailable`.

Для нового движка `learn.research_saved` содержит ревизию checkpoint, фазу,
накопительные шаги/токены/время/чтения, размер frontier по счётчику и число неопределённых
вызовов. `job.claim_lost` означает отзыв права прежнего worker на публикацию. Сам ciphertext,
адреса frontier, кандидаты, model output и значения сессии не журналируются. Кооперативный
`job.requeued` не является ошибкой источника и не расходует транспортный retry.

В режиме `on` сохраняется тот же запрет на пароли, коды MFA, cookie, bearer,
`Authorization`, содержимое хранилищ браузера, HTML/тела ответов, кадры и ввод, тексты
сообщений, промпты и свободные рассуждения LLM. Режим не включает `DEBUG` для сторонних
библиотек; `LLM_DEBUG_TRACES=false` задан в production явно. Содержимое сайтов и модели
не может задавать поля журналов. Это структурная диагностика по allowlist, без сырого дампа.

## Хранение и чтение

JSONL-файлы находятся в `/var/log/botai/diagnostics` внутри именованного тома
`botai_diagdata`. Том общий для компонентов и сохраняется после замены контейнеров.
Каталог принадлежит UID 10001 (`botai`), права — `0700`; публичного API для чтения нет.
Лимиты по умолчанию: 24 часа хранения, размер файла 10 МиБ, две ротационные копии.
Общий объём ограничен 30 МиБ на компонент; малые почасовые файлы сохраняются до срока,
а при большом объёме старые удаляются раньше. Почасовой файл может быть удалён до часа
раньше срока. Сводка читается потоково, выгрузка ограничена 50 000 событиями с явной
отметкой усечения. Решения прокси связываются с заданием по отпечатку разрешения.
Очистка выполняется работающим приложением; ротация может удалить старые события раньше
срока при большом потоке. Выключение записи не удаляет существующие файлы немедленно:
к ним продолжают применяться правила хранения.

Настройки `BOTAI_DIAGNOSTICS_RETENTION_HOURS`, `BOTAI_DIAGNOSTICS_MAX_BYTES` и
`BOTAI_DIAGNOSTICS_BACKUP_COUNT` передаются через Compose. Их изменение требует применения
конфигурации. Нельзя удалять том `pgdata` или выполнять `down -v` ради очистки диагностики.

После прохода достаточно ссылки на чат. Его ID — значение `thread` в адресе. Оператор
читает только нужную последовательность на сервере:

```bash
ssh -T mnema 'sudo -n docker exec botai-worker-1 python -m botai.core.diagnostics --thread THREAD_ID'
ssh -T mnema 'sudo -n docker exec botai-worker-1 python -m botai.core.diagnostics --job JOB_ID'
ssh -T mnema 'sudo -n docker exec botai-worker-1 python -m botai.core.diagnostics --connection CONNECTION_ID'
```

Чтение работает и после выключения записи, пока файлы не удалены по сроку/ротации.
Обычные Docker-логи остаются отдельным источником; у них своя ротация и они могут исчезнуть
при пересоздании контейнера. События SSE завершённых заданий по-прежнему хранятся 10 минут:
диагностическая последовательность от этого срока не зависит.

## Проверка перед живым проходом

1. Дождаться успешного деплоя `diagnostics=on` и проверить значение в воркере.
2. Владелец проходит вход и подключение своими учётными данными. Тесты разработчика
   используют только синтетический `fakeuni` на loopback.
3. Передать ссылку на чат и примерное время. Не пересылать пароль, cookie или токен.
4. После разбора выключить запись через `diagnostics=off`.
