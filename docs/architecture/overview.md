# Botai — архитектура

Статус: **accepted**, 2026-10-27. Текстовое описание; диаграммы — [HLD](hld.md) и [LLD](lld.md).
Связанные: [требования](../product/requirements.md), [безопасность](security.md),
[контракты](contracts.md), [план работ](../plan/workstreams.md).

## 1. Главная идея

Система состоит из двух контуров с разной ценой и разной частотой:

| Контур | Когда работает | Цена | Детерминизм |
|---|---|---|---|
| **Обучение** (learning) | Один раз на вуз (и при поломке) | Дорого: удалённый браузер + LLM | Нет, человек в цикле |
| **Исполнение** (execution) | Каждый sync, каждый пользователь | Почти бесплатно: HTTP + разбор | Да, по рецепту |

Всё, что агент понял про вуз, выражается как **рецепт** — декларативный JSON без
личных значений. Это единственный мост между контурами. Если рецепт нельзя
выразить декларативно — значит, агент ещё не закончил работу.

```
                    ┌──────────────── Контур обучения (редко) ────────────────┐
  Студент ──вход──▶ │ BrowserSvc(Chromium+screencast) → Observer → Explorer   │
                    │        ↑ человек вводит пароль/MFA/капчу                │
                    │        └── LLM предлагает рецепт → lint → canary        │
                    └──────────────────────┬─────────────────────────────────┘
                                           ▼ recipe@rev (без личных данных)
                    ┌──────────────── Контур исполнения (часто) ──────────────┐
  Планировщик ────▶ │ Runner: HTTP по рецепту + сессия пользователя → Normalizer│
                    │                     ↓                                   │
                    │        Снимки → домен (курсы/пары/дедлайны/оценки)       │
                    └──────────────────────┬─────────────────────────────────┘
                                           ▼
  PWA ◀── REST/SSE ── API(BFF) ◀── Chat Agent (RAG по данным пользователя)
```

## 2. Компоненты

| # | Компонент | Ответственность | Не отвечает за |
|---|---|---|---|
| C1 | **PWA** (React) | Экраны, дизайн-система, маскот, офлайн-чтение, установка | Секреты, прямые запросы к вузам |
| C2 | **API / BFF** (Fastify) | Аутентификация пула, REST+SSE, права, квоты, оркестрация заданий | Хождение в вузы напрямую |
| C3 | **BrowserSvc** | Пул Chromium, трансляция экрана (CDP screencast) по WS, ввод пользователя, снятие состояния сессии | Решение капчи, хранение пароля |
| C4 | **EgressProxy** | Фильтрующий CONNECT-прокси, allowlist хостов на подключение, блок приватных диапазонов, бюджеты запросов | Бизнес-логика |
| C5 | **Explorer** (агент обучения) | Наблюдение XHR, гипотезы об эндпоинтах, вопросы пользователю, черновик рецепта | Запись данных в вуз |
| C6 | **RecipeStore** | Версии рецептов, lint, canary, откат, привязка к origin | Пользовательские секреты |
| C7 | **Runner** | Детерминированное исполнение рецепта с сессией пользователя, ретраи, backoff | Вызовы LLM |
| C8 | **Normalizer** | Приведение ответов к домену, идемпотентный upsert снимков | Сетевые запросы |
| C9 | **Scheduler/Worker** | Плановые sync, очередь, дедупликация заданий, изоляция отказов | UI |
| C10 | **ChatAgent** | Ответ по данным пользователя + RAG, инструменты только на чтение | Произвольный доступ к секретам |
| C11 | **ActionBroker** | Предложение write-запроса, одноразовое подтверждение человеком, исполнение | Самостоятельное решение о действии |
| C12 | **Vault** | Конвертное шифрование секретов, AAD, ротация | Логика источников |
| C13 | **Index** (RAG) | Эмбеддинги и поиск по подключённым документам и страницам | Хранение секретов |

Границы доверия и угрозы — в [security.md](security.md).

## 4. Модель данных

Ядро домена одинаково для всех вузов; специфика вуза живёт в рецепте, а не в схеме.

```
User ──1:N── Space(university) ──1:N── Connection(origin) ──1:1── Secret(encrypted)
                   │                          │
                   │                          └──N:1── Recipe(origin, revision)
                   │
                   ├──1:N── Course ──1:N── Assignment ──1:N── Deadline
                   ├──1:N── ScheduleEvent (course?, teacher?, location?, source)
                   ├──1:N── Grade
                   ├──1:N── Person (преподаватель)
                   ├──1:N── Document (файл/таблица/страница) ──1:N── Chunk(vector)
                   └──1:N── Fact (подтверждённый ответ RAG + срок годности)
```

Правила, общие для всех сущностей:

- `source_id`, `source_url`, `fetched_at` обязательны. Данных «ниоткуда» нет.
- `external_id` уникален в паре `(connection_id, external_id)` — записи двух
  вузов не сталкиваются.
- Снимок пишется идемпотентно: повторный sync не создаёт дублей и не удаляет
  прежний успешный снимок при частичной ошибке.
- Таблица `secrets` хранит только шифртекст; расшифровка возможна только в
  процессе, который держит мастер-ключ вне БД.

Полные схемы — [contracts.md](contracts.md).

## 5. Ключевые потоки

### 5.1 Подключение вуза

```
PWA           API             BrowserSvc        Explorer        RecipeStore
 │ POST /connections            │                 │                 │
 │─────────────▶ создаёт draft  │                 │                 │
 │ ◀── SSE job stream ──────────┤                 │                 │
 │ открыть окно входа ─────────▶│ запускает ctx   │                 │
 │ ◀═ WS: кадры экрана ═════════│                 │                 │
 │ ══ WS: мышь/клавиатура ═════▶│ (человек вводит пароль/MFA/капчу) │
 │                              │ признак успеха  │                 │
 │                              │─── сессия ─────▶│ наблюдение XHR  │
 │ ◀── SSE: шаги размышления ───┼─────────────────┤                 │
 │ ◀── SSE: вопрос (ui-блок) ───┼─────────────────┤                 │
 │ ── ответ структурой ────────▶│                 │                 │
 │ ◀── SSE: итог «вот что нашёл»┼─────────────────┤                 │
 │ ── подтверждение ───────────▶│                 │ lint + canary ─▶│ rev+1
 │ ◀── connection: active ──────┤                 │                 │
```

Вопрос агента — это **элемент интерфейса**, а не текст: см. схему `AgentUiBlock`
в [contracts.md](contracts.md). Клиент рисует его своими компонентами из
дизайн-системы (подход A2UI; свою подмножественную схему держим ради контроля).

### 5.2 Синхронизация

Scheduler → задание `sync(connection)` → Runner берёт `recipe@active`,
расшифровывает сессию, выполняет GET'ы через EgressProxy (allowlist = origin
рецепта), Normalizer пишет снимок. LLM не вызывается.

Ошибки: `401/403` или редирект на логин → `needs_reauth`, плановые попытки
останавливаются, прежние данные остаются и помечаются устаревшими.
`429/5xx` → экспоненциальный backoff, соблюдение лимитов источника.
Разбор не сошёлся → `recipe_drift`, рецепт помечается, автор получает задачу
на переобучение, остальные пользователи вуза не теряют старые данные.

### 5.3 Чат

Запрос → классификация: (1) данные пользователя — SQL по домену, LLM только
формулирует; (2) процедурный вопрос — RAG по `Document`/`Fact` с проверкой
срока годности; (3) нет основания — честный ответ + предложение подключить
источник или ограниченный поиск по разрешённым origin'ам.
Инструменты чата — только чтение. Весь текст, пришедший из вуза, помечен как
данные и не может изменить поведение агента.

### 5.4 Write-действие

Explorer разбирает форму → `ActionProposal` (метод, URL, поля, человекочитаемое
описание) → PWA показывает `ApprovalCard` → пользователь правит и подтверждает →
ActionBroker исполняет **ровно подтверждённый запрос** один раз, с истечением
подтверждения. Разобранная форма сохраняется как переиспользуемый шаг.

## 7. Что осознанно отложено

- Горизонтальное масштабирование: один сервер, один воркер-пул.
- Мультирегион и репликация БД.
- Публичная регистрация и биллинг.
- Мобильные нативные приложения — только PWA.
- Деплой: собирается и проверяется локально; выкладка — последний этап.
