## 1. Главная идея

Система состоит из двух контуров с разной ценой и разной частотой:

| Контур | Когда работает | Цена | Детерминизм |
|---|---|---|---|
| **Обучение** (learning) | Один раз на вуз (и при поломке) | Дорого: удалённый браузер + LLM | Нет, человек в цикле |
| **Исполнение** (execution) | Каждый sync, каждый пользователь | HTTP + разбор; для rendered recipe — Chromium | Да, по рецепту, без LLM |

Всё, что агент понял про вуз, выражается как **рецепт** — декларативный JSON без
личных значений. Это единственный мост между контурами. Если текущий контракт не позволяет
выразить источник, исследование остаётся неполным с конкретным ограничением; модель не
заменяет отсутствующую capability исполняемым parser code.

[Factory v2](factory-v2.md) добавляет per-request auth proof, nested/weekly data DSL и
проверенный native browser replay. Reader сохраняет v1; producer v2 по умолчанию выключен.
Код v2 собран в интеграционной ветке, полный CI и выпуск ещё проверяются.

```
                    ┌──────────────── Контур обучения (редко) ────────────────┐
  Студент ──вход──▶ │ BrowserSvc(Chromium+screencast) → Observer → Explorer   │
                    │        ↑ человек вводит пароль/MFA/капчу                │
                    │        └── LLM предлагает рецепт → lint → canary        │
                    └──────────────────────┬─────────────────────────────────┘
                                           ▼ recipe@rev (без личных данных)
                    ┌──────────────── Контур исполнения (часто) ──────────────┐
  Планировщик ────▶ │ Runner: HTTP по рецепту + сессия пользователя → Normalizer│
                    │                     ↓                                   │
                    │        Снимки → домен (курсы/пары/дедлайны/оценки)       │
                    └──────────────────────┬─────────────────────────────────┘
                                           ▼
  PWA ◀── REST/SSE ── API(BFF) ◀── Chat Agent (RAG по данным пользователя)
```

| C4 | **EgressProxy** | Фильтрующий CONNECT-прокси, allowlist хостов на подключение, блок приватных диапазонов, бюджеты запросов | Бизнес-логика |
| C5 | **Explorer** (агент обучения) | Свежие DOM/XHR, наблюдаемые ссылки и проверенные вкладки, вопросы пользователю, черновик рецепта | Выдуманные эндпоинты, произвольные скрипты и запись данных в вуз |

## 4. Модель данных

Ядро домена одинаково для всех вузов; специфика вуза живёт в рецепте, а не в схеме.

```
User ──1:N── Space(university) ──1:N── Connection(origin) ──1:1── Secret(encrypted)
  │                │                          │
  │                │                          └──N:1── Recipe(origin, revision)
  │                │
  │                ├──1:N── Course ──1:N── Assignment ──1:N── Deadline
  │                ├──1:N── ScheduleEvent (course?, teacher?, location?, source)
  │                ├──1:N── Grade
  │                ├──1:N── Person (преподаватель)
  │                ├──1:N── Document (файл/таблица/страница) ──1:N── Chunk(vector)
  │                └──1:N── Fact (подтверждённый ответ RAG + срок годности)
  │
  ├──1:N── ChatThread ──1:N── ChatMessage ──1:N── Attachment(bytes)
  └──0:1── Space "Мои материалы" (без вуза): документы и вложения вне вуза
```

Вуз и его источники ([план v3 §3.5](../plan/agent-hub-v3.md), ADR-0013):

- `Space` — **один вуз одного студента**: уникальны `(user_id, university_id)`, а пространство
  «Мои материалы» (`university_id` пуст) — одно на пользователя; оба правила держат частичные
  уникальные индексы. Название пространства — название вуза из справочника или выученной строки
  `universities` («НИУ ВШЭ»), а не адрес сайта. `shortTitle` и `aliases` берутся оттуда же
  (алиасы — из справочника имён `spaces/university-names.json`; ни адресов, ни интеграций
  в нём нет). Создание пространства идемпотентно: `service.ensure_space`, `POST /spaces`.
- `Connection` — **источник** вуза (кабинет, Smart LMS, документация, таблица, документ).
  `title` человеческий: заданное имя, затем заголовок страницы, затем название вида, но не
  голый хост. `kind` — `portal|lms|schedule|site|sheet|doc|document|calendar|other`
  (`sheet` — таблица, `doc` — документ или страница по ссылке, `document` — загруженный
  файл). `entry_url` — страница интерфейса источника без секретных query.
- `ConnectionOut` отдаёт `threadId` (тред последней задачи источника, если он ещё есть) и
  `activeTask {jobId, kind, state}`: плашки источников ведут в тред задачи.
- `Attachment` — файл чата: байты в Postgres (`bytea`, до 20 МиБ), владелец обязателен, тип
  определяется по байтам. Создаётся несвязанным (`POST /attachments`), связывается с сообщением
  при отправке (`message_id`), удаляется вместе с тредом. Документное вложение индексирует
  задание `INGEST`: оно читает байты из `attachments` и **сначала** пишет `Document`, текст и
  `Chunk` (документ ищется и читается), и только потом задаёт вопросы о таблицах. Хранение,
  отдача (`inline`, `private, no-store`, `nosniff`, HTML — только как текст-вложение) и квота —
  в [контракте вложений](../plan/agent-hub-v3.md#36-вложения-и-документы-ws4).
- Ссылки Google Docs/Sheets/Slides/Drive («доступ по ссылке») нормализуются в публичный
  экспорт общим сервисом `sources/public_links.py`; закрытый документ — честная ошибка, а не
  пустой результат.

Полные схемы — [contracts.md](contracts.md).

## 5. Ключевые потоки

### 5.1 Подключение вуза

Актуальный вход — чат с `purpose=connect`. У CONNECT-задания сначала может не быть
подключения: API сохраняет сообщения, ссылки и уточнения в durable inbox, затем связывает
его с пространством и origin. Исходный path/query остаётся в контексте исследования.
Секретный ввод идёт API → Vault → LoginFlow, минуя историю сообщений и модель.

LoginFlow проверяет сессию по выученной API-пробе или проходит вход. Explorer отдельно
проверяет авторизацию отрисованной страницы: API `200` не заменяет эту проверку.
Ограниченные localStorage/sessionStorage разрешённых origin восстанавливаются из Vault
до запуска скриптов страницы. CAPTCHA, MFA и новый хост требуют человека.

```
PWA           API             BrowserSvc        Explorer        RecipeStore
 │ POST /connections            │                 │                 │
 │─────────────▶ создаёт draft  │                 │                 │
 │ ◀── SSE job stream ──────────┤                 │                 │
 │ открыть окно входа ─────────▶│ запускает ctx   │                 │
 │ ◀═ WS: кадры экрана ═════════│                 │                 │
 │ ══ WS: мышь/клавиатура ═════▶│ (человек вводит пароль/MFA/капчу) │
 │                              │ признак успеха  │                 │
 │                              │─── сессия ─────▶│ наблюдение XHR  │
 │ ◀── SSE: шаги размышления ───┼─────────────────┤                 │
 │ ◀── SSE: вопрос (ui-блок) ───┼─────────────────┤                 │
 │ ── ответ структурой ────────▶│                 │                 │
 │ ◀── SSE: итог «вот что нашёл»┼─────────────────┤                 │
 │ ── подтверждение ───────────▶│                 │ lint + canary ─▶│ rev+1
 │ ◀── connection: active ──────┤                 │                 │
```

Уточнения об источнике и видах данных принимаются обычным сообщением чата. Для пароля,
MFA и конкретных подтверждений остаются защищённые `AgentUiBlock`; клиент рисует их
компонентами дизайн-системы. Общая просьба включает обнаружение видов из существующего
словаря, явный выбор ограничивает область. Инструменты, обновление наблюдений и бюджеты —
[адаптивное исследование](../research/adaptive-observation.md).

Перед canary Explorer экспортирует обновлённую браузерную сессию и сохраняет её в Vault:
SPA могла обновить cookies/bearer/storage во время исследования. Неудача одного кандидата
не прекращает проверку остальных; поддерживаемый альтернативный auth mode проверяется
исполнителем на том же описании чтения. При отказе кандидатов автор получает структурные
findings и один дополнительный раунд. Успех требует canary итогового рецепта. При v2 producer
compiler связывает каждый HTTP endpoint/bootstrap с успешным наблюдаемым запросом и сам
формирует Cookie/Bearer policy; rendered replay получает проверенный browser plan.
Checkpoint/fencing, свежая проверка после рестарта и накопительный Job usage вне TTL знаний —
в [LLD исследования](source-research.md); контрактный этап — [ADR-0012](../adr/0012-verified-source-factory-v2.md).

Обнаруженный вид данных ещё не является подключением. Автор создаёт декларативный
рецепт, затем выполняются schema/lint, canary на сессии студента, подтверждение и
сохранение ревизии. Только успешный sync пишет данные, которые читают экраны и чат.
Исчерпание бюджета или техническая ошибка дают неполный результат, а не утверждение
«данных нет». Публичная выдача не доказывает наличие личного расписания.

### 5.2 Синхронизация

Scheduler → задание `sync(connection)` → Runner берёт `recipe@active`,
расшифровывает сессию, выполняет GET'ы через EgressProxy (allowlist = origin
рецепта), Normalizer пишет снимок. LLM не вызывается.

Область `connections.data_scope` хранится отдельно от общей спецификации: явные виды
и исключения действуют на следующих sync, после повторного входа и рестарта. Runner
ограничивает endpoints и необходимые bootstrap-шаги до сети, а перед записью повторно
проверяет текущую область. Узкий выбор одного студента не сокращает общий рецепт
других. Смена области сама по себе не удаляет уже импортированные данные.

Ошибки: `401/403` или редирект на логин → `needs_reauth`, плановые попытки
останавливаются, прежние данные остаются и помечаются устаревшими.
`429/5xx` → экспоненциальный backoff, соблюдение лимитов источника.
Разбор не сошёлся → `recipe_drift`, рецепт помечается, автор получает задачу
на переобучение, остальные пользователи вуза не теряют старые данные.

### 5.3 Чат

Запрос → классификация: (1) данные пользователя — SQL по домену, LLM только
формулирует; (2) процедурный вопрос — RAG по `Document`/`Fact` с проверкой
срока годности; (3) нет основания — честный ответ + предложение подключить
источник или дать ссылку. Для актуальных публичных сведений доступен `search_public_web`
через отдельный [SearchService](../development/public-search.md).
Инструменты чата — только чтение. Весь текст, пришедший из вуза, помечен как
данные и не может изменить поведение агента.

### 5.4 Write-действие

Explorer разбирает форму → `ActionProposal` (метод, URL, поля, человекочитаемое
описание) → PWA показывает `ApprovalCard` → пользователь правит и подтверждает →
ActionBroker исполняет **ровно подтверждённый запрос** один раз, с истечением
подтверждения. Разобранная форма сохраняется как переиспользуемый шаг.

## 7. Что осознанно отложено

- Горизонтальное масштабирование: один сервер, один воркер-пул.
- Мультирегион и репликация БД.
- Публичная регистрация и биллинг.
- Мобильные нативные приложения — только PWA.

Выпуск выполняется из зелёного актуального `main` через GitHub Actions; полный набор
проверок для текущей работы запускается в CI. Порядок выкладки и отката —
[deployment.md](../plan/deployment.md).
