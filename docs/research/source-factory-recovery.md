# Почему успешный вход ещё не даёт работающий источник

Дата исследования: 29.10.2026. Базовая ревизия: `57f424233ef62b8804f678b86f0ecbd483a84090`.
Связь: FR-005–FR-011, FR-016, FR-018, NFR-003–NFR-008, NFR-012–NFR-013.

## Вывод

Фабрику декларативных адаптеров следует сохранить. Основной подтверждённый разрыв — между
успешным наблюдением браузера и воспроизведением рецепта. Отказ отдельного способа чтения
принимался за утрату входа; исследование завершалось, не проверив альтернативы и не передав
результат исполнения обратно автору. Увеличение общего таймаута этот разрыв не исправляет.

Для долгого самостоятельного подключения нужен цикл исследования с сохранением состояния,
проверяемыми инструментами и диагностикой исполнения. Его следующий архитектурный этап
описан в принятом [ADR-0011](../adr/0011-resumable-source-discovery.md). После исследования
владелец поручил рефакторинг; код первого этапа подготовлен в рабочей ветке. Его границы
и приёмка — [план рефакторинга](../plan/source-research-refactor.md). Живые источники
новым кодом не проверены. Этот разбор сохраняет состояние исходного инцидента; последующий
[ADR-0012](../adr/0012-verified-source-factory-v2.md) и [factory v2](../architecture/factory-v2.md)
добавили контракт и код auth/data/browser в интеграционной ветке. Полный CI/выпуск и живое
подключение здесь не объявляются завершёнными.

## Что наблюдалось

Производственный чат прочитан через авторизованный интерфейс владельца. Структурные события
получены штатной диагностической командой по ID чата. На момент проверки API, worker и proxy
соответствовали базовой ревизии; это не устанавливает образ, исполнявший более ранние попытки.
Сырые сообщения, адреса личных запросов, DOM и состояние авторизации в репозиторий не внесены.

Последний повтор подключения расписания 29 октября, 15:38 МСК:

| Этап | Наблюдение | Что это доказывает |
|---|---|---|
| Проверка сессии | HTTP 200, bearer присутствует, 6 cookies | Успешна конкретная проба |
| Исходная страница | `auth.entry_ready`, `entry_verified=true` | Браузер принял запрошенное представление |
| Исследование | 1 страница, 11 запросов; `finished`, `limited=false` | Цикл сам завершился, лимит не достигнут |
| Автор | 1 кандидат, 3 сомнения; lint принят | Синтаксис и ограничения прошли; данные ещё не проверены |
| Canary | `session_expired`, примерно через 114 мс после начала | Исполнитель отказал; точный HTTP status и auth mode не записаны |
| Всё задание | Около 28 секунд | Общий таймаут не причина этого прохода |

Нельзя заключить, что выбран неправильный `cookie/bearer`, истёк токен или сайт запрещает
доступ: для такого вывода не хватает диагностических полей. Наличие bearer в сессии не
доказывает, что конкретный endpoint требует bearer. Передача текущего состояния и изоляция
кандидатов — подтверждённые дефекты кода; их причинная роль в конкретном ответе сайта
остаётся гипотезой до нового прохода.

В другом подключении сбой произошёл раньше: три раза guard блокировал `POST document`
формы входа на уже разрешённый host. Затем примерно через 3 секунды возникало
«Страница входа не завершила загрузку». Canary не запускалась. Из старых событий нельзя
установить, почему конкретно не подошло разрешение формы: отсутствовало разрешение,
изменилась эпоха/frame/action или не завершилось сканирование. Снять защиту для всех POST
было бы неверным исправлением.

Подробная диагностика была включена. Она хранится отдельно от SSE: стандартно 24 часа,
с дополнительными ограничениями размера/ротации. Завершённые SSE-события живут 10 минут;
история сообщений сохраняется отдельно. Переключатель диагностики увеличивает наблюдаемость,
но не повышает качество модели и не включает более строгую canary.

## Независимый браузерный эксперимент

Отдельный агент с `high` effort получил только авторизованную вкладку владельца и задачу
прочитать расписание. Вне репозитория создан приватный HTML/CSS/JS-прототип: 12 занятий за
три недели, 21 день, 15 явно пустых дней. Сохранились дата, время, предмет, тип занятия,
группа, помещение, преподаватель, источник и время чтения. Ссылки доступа к онлайн-паре
исключены. Авторизационные секреты не извлекались.

Агент сверил поля всех 12 карточек с локальным UI. Координатор самостоятельно сравнил
исходную текущую неделю с прототипом и проверил переключение следующей недели. Это
независимая выборочная проверка результата агента, не повторная сверка всех карточек.

Затруднения оказались обычными браузерными: выбранная дата и URL обновлялись раньше карточек,
AX и DOM использовали разные роли ячеек, число даты встречалось в календаре дважды. Свежий DOM
и проверка согласованного состояния позволили продолжить без вопроса владельцу.

Доступный Computer Use API не предоставлял сетевые headers/response inspection. Поэтому
API-endpoint и переносимый серверный рецепт **не установлены**. Прототип — сохранённый снимок,
не автоматическая синхронизация. Эксперимент доказывает читаемость страницы текущего Chrome;
он не доказывает вход в новом Chromium, перенос сессии или повторный sync без модели.

## Дефекты и ограничения исходной реализации

| Наблюдение в коде | Последствие | Направление исправления |
|---|---|---|
| Первый `SessionExpired` в `_author_and_verify` выбрасывал ошибку всего задания | Следующие HTTP/rendered-кандидаты не проверялись | Изоляция кандидатов и ограниченные проверки доступных auth bindings |
| `_observe` закрывал handle и передавал исходную session | Ротация cookies/bearer/storage при исследовании терялась для canary и sync | Экспорт актуальной session перед закрытием, сохранение в Vault |
| `_restore` всегда ставил сохранённый Authorization | Новый токен приложения заменялся старым | Собственный Authorization приложения имеет приоритет |
| Primary origin выводился из первого host allowlist | Порядок IdP/API hosts мог изменить origin экспортированной сессии | Сохранять `session.origin`, если явный origin не задан |
| Автор получал ошибки lint, но не canary | После ошибки исполнения требовалась новая ссылка от человека | Один ограниченный цикл исправления по структурным findings |
| HTTP 401/403 одинаково классифицируются как `SessionExpired` | Отказ endpoint может выглядеть как отказ входа | В обучении это отказ конкретной проверки; повторный вход подтверждается отдельно браузером |
| `jobProblem` сохранял только legacy `login_failed`, остальные коды терялись | Подтверждённая ошибка источника становилась общей «неполадкой BotAI» | Сохранять известные машинные коды, неизвестный текст не отображать |
| Разрешение auth POST изымалось до проверки соответствия | Отклонённый запрос мог лишить следующую форму разрешения | Изымать только после полной успешной проверки; сохранять одноразовость |
| `auth_document` мог скрывать отказ навигации сетевым timeout | Причину блока нельзя было отличить от медленного сайта | Возвращать ошибку текущей навигации, добавить причины arm/refusal |

Для исходной ревизии этого исследования выбор `auth.type` всё ещё не связан декларативно с наблюдаемым request. Схема умеет `none`,
`cookie`, `bearer`, но не произвольную комбинацию или обновление токена. Проверка нескольких
уже поддержанных вариантов уменьшает зависимость от догадки модели, но не заменяет
проектируемые executor-owned bindings. Комбинацию cookie+bearer нельзя объявлять
поддержанной без изменения контракта и тестов.

## Почему «дать больше свободы» требует инструментов

В базовой ревизии весь CONNECT допускает 1800 секунд, но отдельный discovery ограничен 90 секундами,
10 шагами, 12 страницами и 200 наблюдаемыми запросами. В рассмотренном проходе эти границы
не достигались. Они всё равно мешают более сложным источникам, и должны стать бюджетами
возобновляемой работы вместо причины потерять всё исследование.

Действия planner: навигация по наблюдаемой ссылке, исследование наблюдаемого ответа,
активация проверенной ARIA-вкладки и завершение. Date picker, обычный фильтр, кнопочная
пагинация, произвольный iframe и неизвестное POST-чтение этим не покрываются. Если элемент
не представлен инструментом, дополнительное время модели не создаст эту возможность.

Следует добавлять общие проверяемые capabilities: выбор даты/диапазона, локальные фильтры,
пагинацию, frame-scoped наблюдение, bounded ожидание данных, разбор безопасных файлов.
Выбор делает модель по evidence reference; executor проверяет актуальную ревизию DOM,
происхождение, разрешённый трафик и ожидаемый эффект. Неизвестное write/POST/GraphQL не
становится чтением по уверению модели или подписи кнопки.

Есть и отдельный предел языка данных: текущий JSON Pointer выбирает один список, а transforms
обрабатывают отдельное значение. В схеме нет общего обхода вложенных массивов с полями
родителя, склейки раздельных даты/времени и разворота недельного правила в события. Добавление
браузерного click этого не исправит. Эти операции следует вводить как ограниченные
декларативные преобразования с лимитом результата, явной таймзоной и контрактными тестами,
если наблюдаемый источник действительно их требует. Их необходимость для конкретного
нового личного API нельзя установить по одному DOM-прототипу.

Полнота ограничена словарём доменных сущностей и выразительностью DSL. Обещание «абсолютно
любая информация любого сайта навсегда» технически неверно: сайты меняются, данные могут
быть недоступны, требовать человека или неподдержанное преобразование. Продуктовое обещание —
агент самостоятельно исследует доступное, проверяет результат, сохраняет переносимую
спецификацию и честно сообщает конкретное оставшееся ограничение.

## Следующая приёмка

1. Синтетическая SPA: cookie replay отказал, bearer или следующий rendered кандидат дал
   правильные записи; выбранное доказанное описание воспроизводится без модели.
2. Ротация сессии при discovery: canary и следующий sync используют свежую версию Vault;
   старый Authorization не заменяет новый, чужие origin не получают секрет.
3. Все варианты не прошли: автор получает безопасные findings, делает одну коррекцию;
   повтор не цикличен и не подменяет отсутствие проверки утверждением «данных нет».
4. Неавторизационный POST не расходует разрешение формы; успешный auth permit одноразовый;
   смена страницы/эпохи отзывает его; data POST и WS по-прежнему запрещены.
5. В UI сохраняется исходный известный код ошибки; произвольные detail/секреты не эхоируются.
6. После CI владелец проходит новый вход и подтверждение на настоящих источниках. Canary,
   нормализованный календарь и второй sync проверяются раздельно. Старый лог и локальный
   Chrome-прототип этого не заменяют.

## Внешние источники

Официальная [документация Playwright по авторизации](https://playwright.dev/python/docs/auth)
разделяет cookies, localStorage, IndexedDB и sessionStorage; обычный storage state не покрывает
всю возможную авторизацию приложения. [APIRequestContext](https://playwright.dev/python/docs/api/class-apirequestcontext)
внутри BrowserContext разделяет с ним cookies; отдельный HTTP-клиент должен восстановить
нужное состояние явно. Это поддерживает вывод о необходимости проверить handoff, но не
устанавливает причину конкретного производственного HTTP-отказа. Новые API документации
нельзя применять без сверки с закреплённой в проекте Playwright 1.63.0.
