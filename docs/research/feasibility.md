# Botai — исследование технической реализуемости

Дата: 2026-10-26. Горизонт источников: октябрь 2026.
Обозначения уверенности: **Ф** — проверенный факт с источником, **П** — допущение/оценка автора, **?** — не удалось проверить.

Продукт: mobile-first PWA для студентов РФ. Агент один раз исследует сайты вуза под сессией
студента и выводит декларативный read-only **рецепт** (origin + GET-эндпоинты + маппинг JSON-полей,
без персональных значений). Далее все студенты этого вуза синхронизируются своей сессией без LLM.
Хостинг — российский VPS, без VPN. Сначала общий ключ DeepSeek на закрытый пул, позже BYOK.

Важные практические ограничения Playwright ([docs/auth](https://playwright.dev/docs/auth)), **Ф**:

- `storageState` покрывает cookies, localStorage, IndexedDB и WebAuthn, **но не sessionStorage**
  (обходится дампом + `addInitScript`). Modeus хранит `id_token` именно в `sessionStorage` — см. §2.3.
- Нет механизма обнаружения истечения состояния: «you need to delete the stored state when it expires».
- Файл состояния содержит cookies/headers, достаточные для подмены личности пользователя.
- Для Chromium в Docker нужен `--ipc=host`, иначе возможен OOM-крэш
  ([docs/docker](https://playwright.dev/docs/docker)). Playwright **не** публикует требования к RAM/`/dev/shm` — **?**.

#### Что AGPL-3.0 значит для хостируемого сервиса

[AGPL-3.0 §13](https://www.gnu.org/licenses/agpl-3.0.html) добавляет к обычному copyleft сетевой
триггер: если вы **модифицируете** Программу и ваша версия взаимодействует с пользователями по
сети, вы обязаны «prominently offer all users interacting with it remotely … an opportunity to
receive the Corresponding Source of your version … at no charge, from a network server». **Ф**
(фрагменты процитированы с gnu.org; полный абзац при юридическом использовании нужно
перепроверить — gnu.org отдал 429, **?**).

Следствие для нас (**П**, требует юрпроверки):

- Втянуть `workflow-use` или `Integuru` в хостируемый бэкенд — значит ввести Corresponding Source
  всего окружающего сервиса в зону обязательства.
- Рабочая граница: AGPL-компоненты живут **только как offline/операторский инструмент этапа
  обучения**, не импортируются и не линкуются в сервис, пользователи не взаимодействуют с ними
  по сети, а наружу идёт **только плоский артефакт данных — JSON-рецепт**. Доктрина «mere
  aggregation» это поддерживает, но первичную FSF-формулировку подтвердить не удалось (**?**).
- Удачно, что эта лицензионная граница **совпадает** с архитектурной (LLM на обучении → нуль LLM
  на replay). Хостируемая часть остаётся на Playwright (Apache-2.0), mitmproxy/har-to-openapi (MIT).
- Открытый вопрос: обязательства при **немодифицированном** AGPL-коде в сетевом сервисе. §13
  текстуально обусловлен «if you modify the Program»; консенсус практиков — всё равно предложить
  источник (легко: ссылка на upstream). **?**

### 2.3 LMS и данные вуза: что реально достижимо без партнёрства

| Источник | Путь доступа без партнёрства | Реалистичность | Ув. |
|---|---|---|---|
| **Moodle Web Services** | `POST /login/token.php?username=…&password=…&service=moodle_mobile_app` → токен. Работает, потому что мобильный сервис защищён **отдельной** capability `moodle/webservice:createmobiletoken`, разрешённой роли **authenticated user** по умолчанию (обычная `createtoken` — только manager) | **Высокая** на дефолтном HTTPS-Moodle 3.0+: админ не нужен. Ломается, если выключены mobile services, снята capability, выставлен `restrictedusers` или IP-фильтр | Ф |
| Функции Moodle | `core_calendar_get_action_events_by_timesort`, `core_calendar_get_calendar_monthly_view`, `mod_assign_get_assignments`, `gradereport_user_get_grade_items` — все в ядре и в сервисе `moodle_mobile_app`; две календарные доступны по AJAX | дают расписание, дедлайны **и оценки** | Ф |
| Moodle iCal export | Приватная ссылка с `authtoken`, отдаёт .ics без логина (bearer-URL) | **деградированный фолбэк**: нет оценок, нет метаданных заданий, грубое окно времени. Включён ли по умолчанию — **?** | Ф/? |
| **Canvas LMS** | Студент может сам выпустить personal access token в `/profile` | **Закрыт политикой.** Canvas прямо пишет: просить другого пользователя сгенерировать токен и ввести его в ваше приложение — «a violation of Canvas' API Policy»; многопользовательские приложения ОБЯЗАНЫ использовать OAuth, а developer key выдаёт админ вуза | Ф |
| Canvas ICS feed | Приватная ссылка Calendar Feed | работает, детали (формат URL, исключение To Do) подтверждены только сторонними страницами — **?** | ?/Ф |
| **Blackboard Learn REST** | Нет | **Жёстко закрыт**: нужна регистрация приложения на developer-портале **и** действие Learn System Administrator (Integrations → REST API integrations), по умолчанию ни одно приложение к API не допущено | Ф |
| **Modeus** (УрФУ, ТюмГУ, …) | Публичного API нет. Де-факто все независимые клиенты логинятся через SSO вуза в headless-браузере и извлекают JWT `id_token` из `sessionStorage`; кэш ~20 мин → короткий TTL | **Средняя**, но **только** через replay сессии/cookie. Прецеденты: [ModeusSchedule.MSAuth](https://github.com/serega404/ModeusSchedule.MSAuth), [Mihendy/modeus-sync](https://github.com/Mihendy/modeus-sync) (ADFS `sso.urfu.ru`), [fy8io/modeus-sync](https://github.com/fy8io/modeus-sync), [urfu-mcp](https://github.com/be1pheg0r/urfu-mcp). UI отдаёт расписание только ~2 недели вперёд | Ф |
| **1С:Университет ПРОФ** | Стандартного веб-API расписания в публичных источниках **нет**; подробная документация за пейволлом its.1c.ru. Есть «Интеграция с МАХ» (только ПРОФ ред. 2.3) и мастер-классы по выгрузке расписания в MAX | **Низкая**: любой «API» — то, что опубликовал интегратор конкретного вуза; покрытие per-university, не платформенное. MAX-путь благословлён вендором, но это интеграция **на стороне вуза** | Ф/? |
| **ЕТИС ПГНИУ** и подобные | Официального API нет; все неофициальные клиенты авторизуются как студент и **парсят HTML**: [ETIS-mobile](https://github.com/Damego/ETIS-mobile) (в RuStore, «автоматическая авторизация»), [ЕТИС REBORN](https://etisreborn.ru/) (только переписывает CSS/HTML в браузере, «данные не уходят на сторонние серверы»), [etis3.0](https://github.com/sergei20032121-lgtm/etis3.0) | **Средняя** технически. Экосистема ЕТИС уже расколота ровно по нашему вопросу доверия — и это продуктовый сигнал: REBORN делает «ничего не покидает браузер» своим дифференцирующим преимуществом | Ф |

Два вывода, способных обрушить план (**приоритет на эмпирическую проверку**):

1. **Работает ли `login/token.php` для аккаунтов Moodle за институциональным SSO/OIDC?** Есть
   нерешённый issue, указывающий на отказ ([o365-moodle#1888](https://github.com/microsoft/o365-moodle/issues/1888)).
   Если не работает — Moodle-путь обрушивается именно на тех вузах, которые наиболее вероятны в скоупе. **?**
2. **Moodle «включён по умолчанию» — двусмысленно, но разрешимо**: в ядре сервис идёт с
   `enabled => 0`, при этом доки говорят, что mobile-доступ включён по умолчанию на новых
   HTTPS-установках 3.0+. Верно и то, и другое: админская настройка переключает сервис. **Ф**
   ([Moodle app guide for admins](https://docs.moodle.org/500/en/Moodle_app_guide_for_admins),
   [Using web services](https://docs.moodle.org/503/en/Using_web_services),
   [capability createmobiletoken](https://docs.moodle.org/en/Capabilities/moodle/webservice:createmobiletoken))

Риск-заметка (**П**): Moodle-путь — это обмен **пароля** на токен, а не OAuth-согласие. Студент
вводит пароль вуза в наш клиент. Архитектурно это то же самое, против чего предупреждают вузы,
даже если эндпоинт санкционирован Moodle, и это противоречит [ADR-0001](../adr/0001-login-form-mirroring.md)
(пароли не храним и не принимаем). Поэтому в Botai Moodle-токен — только то, что студент **уже
имеет и добавляет сам** (FR о дополнительных секретах), а не то, что сервер выпускает по паролю.
Для ВШЭ этот путь закрыт фактически — см. §6, п. 2.

**Вердикт по генеративному UI: не принимать A2UI, определить собственную маленькую схему.** (**П**)

Обоснование:

- Нам нужен **узкий** набор: один вопрос — чекбоксы / радио / текстовое поле / выбор из списка
  («какой из этих трёх календарей твой?», «подтверди отправку заявления?»). Это 5–8 типов виджетов,
  а не универсальный UI-язык.
- A2UI сейчас — public preview с v1.0 в статусе RC: поверхность спеки будет двигаться, а 16,8k★ при
  возрасте репозитория 13 месяцев отражают внимание, а не продакшн-внедрение (**П**).
- A2UI и AG-UI **не конкуренты по одной оси** и композируемы: AG-UI стандартизует поток событий,
  A2UI — полезную нагрузку описания UI (**П**).
- Архитектура A2UI (JSON + наши компоненты) **правильна по безопасности** для приложения, держащего
  сессию вуза, — в отличие от MCP Apps, которые шлют HTML в iframe. Поэтому заимствуем **идею
  A2UI**, но не её схему; при стабилизации v1.0 переоценить.
- MCP брать **для инструментов агента** (не для UI), а `elicitation` из ядра MCP — как семантику
  «сервер спрашивает пользователя». Схему рендеринга этого вопроса определяем сами.

### 2.6 PWA: что iOS реально позволяет в 2026

| Возможность | Состояние на iOS в 2026 | Ув. |
|---|---|---|
| Web Push | С **iOS/iPadOS 16.4** (released 2023-03-27). caniuse держит iOS Safari **16.4 → 27.2 как «partial»**, статус за 2026 не снят (на desktop Safari «full» с 18.0) | Ф |
| Требование установки | **Да, всё ещё обязательно**: push даётся только Home Screen web app, не вкладке Safari. Но в **Safari 26 / iOS 26** любой сайт, добавленный на домашний экран, открывается как web app **по умолчанию** (ранее нужен был мета-тег/манифест); Apple заявляет «zero conditions» для installability. Т.е. требование осталось, а порог его выполнения упал почти до нуля | Ф |
| Нет install API | Нет `beforeinstallprompt`, нет `appinstalled` — установка только вручную через Share sheet, приложение обязано объяснять это пользователю | Ф |
| User gesture | Разрешение запрашивается только из жеста; без transient activation `pushManager.subscribe()` отклоняется `NotAllowedError` | Ф/? (точная формулировка найдена не на webkit.org) |
| Badging API | **Поддержан** с 16.4, в т.ч. из service worker при обработке фонового push. Ставить бейдж **после** `showNotification()` | Ф |
| Notification `actions` | **Не поддержаны** в классическом Web Push на Safari/iOS (в Chromium — да). По Declarative Web Push сторонние источники утверждают поддержку `actions`, но сам [пост WebKit](https://webkit.org/blog/16535/meet-declarative-web-push/) их не называет — **противоречие не снято** | Ф/? |
| `image`, маска `badge`, `requireInteraction`, `renotify`, `vibrate`, `timestamp` | Игнорируются; иконка — всегда иконка самого web app, не пер-уведомление | Ф (вторичные источники) |
| **Silent / data-only push** | **Невозможен.** `userVisibleOnly: true` обязателен; WebKit фиксирует, вызывался ли `showNotification()` в push-событии, и предупреждает, что отсутствие вызова «may trigger removal of the push subscription» | Ф |

| **Periodic Background Sync** | MDN: «not Baseline … Experimental … Limited availability». Даже в Chrome разрешение выдаётся только **установленному** приложению, запущенному как отдельное, и частота зависит от site engagement score. На iOS — нет | Ф |
| **Фоновое обновление без UI** | **Нельзя.** Нет Background Sync, нет Periodic Sync, нет silent push. Единственное окно фонового исполнения — вызов service worker по push, который обязан закончиться **видимым** уведомлением; внутри этого окна работу делать можно (напр. `setAppBadge()` разрешён) | Ф |
| Квоты хранения | [WebKit storage policy](https://webkit.org/blog/14403/updates-to-storage-policy/): origin quota до **60%** диска, overall до **80%** для браузера. **Standalone web app получает ТУ ЖЕ квоту**, что и во вкладке — никакого бонуса. Вытеснение — по origin целиком, LRU; origin исключается, если есть активная страница или storage персистентный; `persist()` WebKit выдаёт по эвристикам, включая «whether the website is opened as a Home Screen Web App» | Ф |
| Правило 7 дней | Источник — не storage-policy 2023, а [ITP 2020](https://webkit.org/blog/10218/): script-writable storage (вкл. IndexedDB) удаляется после **7 дней использования Safari** без взаимодействия; дни, когда Safari не открывали, не считаются. Home Screen web app **не часть Safari** и имеет свой счётчик дней использования → регулярное использование таймер сбрасывает. Переопределяет ли выданный `persist()` ITP-таймер — **недокументировано** | Ф/? |

**Проектное следствие (П):** «ежедневная синхронизация» на iOS не может быть фоновой. Схемы:
(1) sync на открытии приложения; (2) sync, подвешенный на **видимый** push («расписание обновлено»);
(3) серверный pull по расписанию, PWA только читает готовое. Для нас №3 — единственный надёжный:
сервер держит сессию и реплеит рецепт, PWA ничего фонового не делает.

  (Python-драйвер + браузер): **Chromium headless 706 МБ**, headful 1094 МБ, WebKit headless 588 МБ
  ([datawookie.dev, 2025-06-06](https://datawookie.dev/blog/2025-06-06-playwright-browser-footprint/)) — **Ф**
  как измерение, но это **пол**, а не цена за вкладку; CPU там не измерялся.
- Правила большого пальца (**Ф-2**, блоги, не контролируемые бенчмарки): полный инстанс 300–500 МБ
  с одной активной страницей; **BrowserContext — дёшев: ~2–5 МБ**, по другой разбивке ~150–300 МБ
  главный процесс + ~10 МБ на контекст, потому что `newContext()` не поднимает новые GPU/network
  процессы. 10 контекстов ≈ 800 МБ суммарно. Блокировка картинок/шрифтов/медиа срезает память на
  40–60%. Перезапускать браузер каждые несколько сотен страниц — утечки накапливаются.
- Контраргумент: вкладка с утечкой или бесконечным циклом задевает соседей по процессу — экономия
  на контекстах имеет цену в радиусе поражения (**Ф-2**).
- **Оценка (П, не публикованная цифра):** в 8 ГБ влезает модель «один общий Chromium (~0,7–1,0 ГБ)
  + 10–50 МБ на контекст», и это единственная, при которой остаётся место под Postgres и
  эмбеддер. Отдельные инстансы по 300–500 МБ упираются на **8–12 сессиях**, реалистично меньше.
  CPU на контекст измерений не найдено — **?**.

**Рекомендация (П):** старт — RuVDS Drive 2 (2 699 ₽ ≈ $30/мес при предоплате 3 мес) как
единственная цена, подтверждённая у вендора. На 1000 пользователей — вынести браузерный пул на
отдельный узел 6 vCPU / 16 ГБ (RuVDS Drive 3, 4 999 ₽) и оставить БД/API на первом.

## 4. Вердикт по реализуемости — по возможностям

| # | Возможность | Оценка | Причина | Главная неизвестность |
|---|---|---|---|---|
| a | **Логин в удалённом браузере под управлением пользователя; MFA/CAPTCHA решает человек** | **Высокая** | Playwright `storageState` покрывает cookies/localStorage/IndexedDB/WebAuthn (**Ф**); человек в контуре снимает и MFA, и CAPTCHA, и этический вопрос обхода антибота. Прецеденты работают: все клиенты Modeus так и делают (**Ф**) | **Нет сигнала об истечении сессии** — Playwright честно пишет «you need to delete the stored state when it expires» (**Ф**); и `sessionStorage` не покрывается, а Modeus держит `id_token` именно там с кэшем ~20 мин (**Ф**). Значит нужен собственный детектор «сессия умерла» и UX повторного логина, частота которого пока неизвестна |
| b | **Однократное обучение read-only рецепта** | **Средняя** | Прецедент ровно этой архитектуры существует (Integuru: HAR+LLM → детерминированный код; workflow-use: запись → replay без AI) (**Ф**). Контекст 1M у DeepSeek позволяет держать HAR и DOM в одном окне (**Ф**). Стоимость прогона $0,25 — несущественна (**П**) | **Доля вузов, где read-only данные вообще лежат за GET-эндпоинтами с JSON.** ЕТИС-клиенты **парсят HTML** (**Ф**) — для таких вузов «origin + GET + маппинг JSON» как формат рецепта не применим, и схему придётся расширять до селекторов DOM, что резко увеличивает хрупкость |
| c | **Сведённое расписание нескольких вузов** | **Высокая** | Как только рецепты есть, слияние — чистая работа над данными. На часть вузов есть санкционированные пути: Moodle WS с самовыпуском токена (**Ф**), iCal-экспорт (**Ф**) | **Нормализация.** Modeus отдаёт только ~2 недели вперёд (**Ф**), Moodle iCal — грубое окно, 1С — per-university. Единая модель «занятие/дедлайн/оценка» поверх источников разной полноты — неоценённая работа |
| d | **RAG-чат по собственным данным студента** | **Высокая** | Корпус крошечный (расписание + дедлайны + оценки одного человека): 10k–100k чанков → 60–600 МБ векторов, внутри pgvector на 8 ГБ (**П**). Русские энкодеры есть, Apache-2.0/MIT, int8 ONNX готов для USER-bge-m3 (**Ф**). $0,00064 за ответ (**П**) | **Пропускная способность CPU при индексации.** Публичных цифр для bge-m3/mE5 на CPU нет (**?**); косвенная оценка ~2 эмбеддинга/с на 4 ядрах в int8 (**Ф** для близкой модели) означает, что первичная индексация 1000 студентов — часы, и int8 может не дать прироста без AVX512-VNNI (**Ф**) |
| e | **Одобренные write-действия (подача заявления через форму вуза)** | **Низкая** | Технически Playwright это делает. Но: write-запросы несут CSRF-токены, одноразовые nonce и многошаговые визарды, которые декларативный рецепт не описывает; поломка здесь не «нет данных», а **ошибочно поданный документ**. Плюс это ровно то поведение, против которого вузы предупреждают (**Ф**: ПГНИУ) | **Правовая и репутационная экспозиция**, а не техника. Неизвестно, существует ли хоть один вуз, где регламент это допускает. До выяснения — не строить |
| f | **Подключение Google Sheet, к которому студенту дали доступ** | **Средняя** | Google Sheets API + OAuth — санкционированный путь с согласием пользователя, read-only scope существует, всё документировано | **Доступ к Google OAuth с российского VPS** и прохождение верификации приложения Google для sensitive/restricted scopes. Не проверялось в этом исследовании (**?**). Фолбэк — «Опубликовать в веб» как CSV, что не требует OAuth, но требует действия владельца таблицы |
| g | **Подключение почтового ящика студента** | **Низкая** | Для Gmail нужен restricted scope `gmail.readonly` → обязательный security assessment Google, дорого и долго для закрытого пула. Для российских провайдеров (Mail.ru, Яндекс) есть IMAP и OAuth, но ящик — самый чувствительный источник: там и пароли, и финансы, и всё остальное | **Пропорциональность.** Даже если доступ получить, непонятно, какую долю учебных дедлайнов почта даёт сверх LMS. Сначала измерить ценность, потом строить |

## 5. Главные риски, по убыванию

| # | Риск | Почему серьёзен | Митигация |
|---|---|---|---|
| 1 | **Вытеснение MAX / Госуслугами** | ФЗ от 29.12.2025 кладёт электронные студбилет и зачётку в вузовские сервисы + Госуслуги + MAX (**Ф**). MAX уже имеет бот расписания, модуль интеграции 1С и 230k+ студенческих чатов (**Ф\***). Государственный канал бесплатен для вуза, обязателен по закону и не ломается при смене логина. Он забирает нашу самую понятную функцию — «покажи расписание и зачётку» | **Не конкурировать за ту функцию.** Защитимое — то, чего MAX структурно не делает: **межвузовское** сведение (студент в двух вузах/магистратура+курсы), дедлайны из LMS (не из 1С), и чат-агент над собственными данными. Позиционировать как слой поверх, а не замену. Готовить рецепт для самого MAX, если появится читаемый интерфейс |
| 2 | **ToS вузов и официальное неодобрение** | ПГНИУ прямо называет сторонние клиенты ЕТИС неодобренными (**Ф\***). Canvas прямо запрещает паттерн «пользователь вставляет свой токен» для многопользовательских приложений (**Ф**). Blackboard без действия админа вуза недоступен вообще (**Ф**). Один публичный конфликт с крупным вузом может закрыть канал привлечения | Приоритизировать **санкционированные** пути: Moodle mobile-токен (вуз сам включил сервис), iCal-экспорт, Google OAuth. Держать режим «ничего не покидает устройство» как опцию — ЕТИС REBORN сделал это своим преимуществом (**Ф**). **Не** хранить пароли: только session state с явным TTL. Не реализовывать write-действия (см. 4e). **Пробел:** официальных текстов запрета найти не удалось — отсутствие находки не равно отсутствию запрета, нужна адресная проверка регламентов по каждому целевому вузу (**?**) |
| 3 | **Беговая дорожка поломок логина** | Studo, единственный зарубежный аналог с 400+ вузами, живёт с регулярными поломками логина (**Ф\***). Одновузовские боты умирают за 1–2 года (**Ф\***). У нас хуже: ломается не только логин, но и рецепт. `storageState` не даёт сигнала истечения (**Ф**), Modeus-токен живёт минуты (**Ф**) | Автоматический канарейка-мониторинг по каждому рецепту (один известный ответ в сутки), автоматическое заведение задачи «переобучить» при расхождении, и амортизация: обучение одного вуза стоит $0,25 (**П**), так что переобучение дёшево **деньгами** и дорого **вниманием человека**. Версионировать рецепты, уметь откатываться. Бюджет $30/волну на 40 вузов (**П**) закладывать сразу |
| 4 | **Стоимость и злоупотребление единым общим ключом** | Один ключ без квот = 1000 пользователей могут за день сжечь месячный бюджет (**П**). Пополнять его из РФ можно только через посредника (**Ф**), автопополнения нет → реальный риск обрыва сервиса на пустом балансе | Квота на пользователя в день с первого дня. Жёсткий лимит токенов и шагов на один прогон обучения (контекст 1M делает один прогон способным сжечь $2–3, **П**). Чат — на `flash`, не на `v4-pro`. Планировщик обучения — в off-peak UTC (ровно ×0,5, **Ф**). Prompt caching обязателен (без него input×50 на кэшируемой части, **П**). Алерт на остаток баланса с запасом на срок прохождения платежа через посредника. BYOK — не «позже», а первый клапан перегрева |

Случайная линковка в бэкенд открывает исходники сервиса | Политика: AGPL-компоненты только как offline-инструмент оператора, наружу отдают **только JSON-рецепт** (**П**, требует юрпроверки). В хостируемом коде — исключительно Apache-2.0/MIT/PostgreSQL License. `browserless` — не использовать. Отдельно зафиксировать запрет на stealth-форки: `patchright` API-совместим с Playwright, т.е. подмена в одну строку (**Ф**) |
| 6 | **Невозможность фоновой синхронизации на iOS** | Ни Background Sync, ни Periodic Sync, ни silent push — ни в одной версии iOS по 27.2 (**Ф**). Обещание «всё само обновляется» на iOS невыполнимо на клиенте | Синхронизация **серверная**: сервер держит сессию, реплеит рецепт по расписанию, PWA только читает. Видимый push как сигнал «обновилось». Не обещать фоновую свежесть на клиенте |
| 7 | **Хранение сессий как актив для атакующего** | Файл `storageState` содержит cookies и headers, достаточные для подмены личности пользователя — это прямая формулировка Playwright (**Ф**). У нас это в масштабе тысяч студентов на одном VPS | Вне скоупа этого документа: детали — за `docs/architecture/security.md` (владеет другой агент). Здесь фиксирую только то, что риск первого порядка и что архитектурная альтернатива — режим «сессия не покидает устройство» — существует и имеет живой прецедент (ЕТИС REBORN, **Ф**) |
