# Самостоятельное исследование учебного кабинета

Статус: **предложение**, 2026-10-28. Диагностика включается отдельным переключателем;
описанное здесь изменение поведения пока не реализовано.
Связанные требования: FR-005–FR-009, FR-016, FR-032, NFR-004–NFR-008, NFR-013.

## Почему нынешний агент останавливается

`learn/observe.py` сам обходит ссылки `a[href]` на том же origin: до шести страниц,
двенадцати ссылок с каждой страницы и тридцати интересных запросов. Порядок меню влияет
на результат. Важный пункт в конце меню может не попасть в просмотренные страницы.
JavaScript-карточки, вкладки и кнопки без `href` такой обход не открывает.

Модель в `learn/author.py` получает уже собранное наблюдение и предлагает рецепт для
одного заданного вида данных. Инструменты навигации ей не передаются; системный промпт
прямо говорит, что она не управляет браузером. `LearningIntent` по умолчанию выбирает
`scheduleEvents`, поэтому нейтральное «подключи вуз, вот курсы» не означает автоматического
обнаружения курсов, заданий и дедлайнов. Простое увеличение числа страниц не решает эти
два ограничения.

У обычного чат-агента также нет общего Web Search. `search_documents` ищет в PostgreSQL
по уже подключённым документам; название `websearch_to_tsquery` обозначает синтаксис
полнотекстового запроса PostgreSQL, а не поиск в интернете.

## Предлагаемый цикл

1. Открыть переданную пользователем страницу с восстановленным состоянием входа.
   Отдельно проверить вход в API и в самой отрисованной странице. Положительный ответ
   API не доказывает, что интерфейс кабинета авторизован.
2. Передать модели очищенный снимок DOM, видимые подписи, список обнаруженных ссылок
   и действий, структурные образцы ответов XHR/fetch и текущую цель пользователя.
3. Модель выбирает следующий шаг по идентификатору из наблюдаемого набора: перейти
   по ссылке, открыть безопасную вкладку, посмотреть уже полученный ответ, вернуться,
   завершить исследование или задать обоснованный вопрос. Произвольные адреса и
   исполняемый JavaScript из ответа модели не исполняются.
4. Сервер проверяет допустимость действия, выполняет его через существующий браузер
   и EgressProxy и снимает новое наблюдение. После изменения страницы прежние ID
   элементов недействительны. Навигация, прочитанные данные и выводы имеют источники.
5. При общей просьбе подключить вуз агент обнаруживает доступные виды данных. При
   явной просьбе подключить только расписание сохраняет эту границу. Отсутствующие
   и запрещённые пользователем виды не запрашиваются повторно.
6. Для найденного источника остаётся существующая цепочка: декларативный рецепт →
   schema/lint → canary на сессии пользователя → итог и подтверждение → первый sync.

Для начала достаточно внутреннего планировщика в `learn/` и расширения наблюдений.
Новая зависимость или смена всего браузерного стека не обязательны. Понадобится отдельно
уточнить протоколы браузера для безопасных действий и состояние намерения; изменения
публичных контрактов оформляются отдельно по правилам репозитория.

## Границы автономности

Агент свободно выбирает чтение внутри разрешённого источника. Капча/MFA остаются
человеку; новые хосты проходят существующее согласование; операции записи — конкретное
одноразовое подтверждение. POST по умолчанию не разрешается только потому, что модель
назвала его чтением: GraphQL и другие POST-интерфейсы потребуют отдельного решения
контракта безопасности. Содержимое страницы не может разрешать действия.

Нужны общие лимиты времени, шагов, запросов и токенов, учёт посещённых состояний,
остановка повторяющихся действий, возможность отмены и сохранение проверенных
промежуточных находок. Достижение лимита должно называться лимитом исследования,
а не утверждением «в вузе нет расписания».

Отдельный Web Search полезен для публичной документации и поиска официального сайта.
Он не заменяет доступ к авторизованному кабинету. Поисковые запросы не должны включать
данные студента; найденные внешние адреса не расширяют allowlist автоматически.

Полное состояние браузерной авторизации хранится только зашифрованным в Vault:
cookies и необходимое состояние хранилищ, отдельно от доступных модели наблюдений.
В диагностике сохраняются признаки и счётчики, без самих значений.

## Проверка на синтетическом вузе

- Пользователь даёт страницу курсов без списка видов данных: найдены курсы и задания,
  расписание исследовано отдельным пунктом меню; итог показывает проверенные источники.
- Нужный пункт расположен после десятой ссылки, карточка курса работает без `href`:
  агент выбирает релевантный переход и видит появившийся XHR.
- API принимает токен, но интерфейсу нужен localStorage: вход восстанавливается либо
  агент сообщает о потере авторизации, а не об отсутствии данных.
- Неизвестный хост, write-кнопка, инъекция в DOM, повторяющийся переход, исчерпание
  бюджета и отмена не приводят к обходу ограничений или ложному успешному результату.
- После подтверждения рецепт переиспользуется и синхронизируется без модели.

## Проверенные первичные источники

- [Playwright: Network](https://playwright.dev/docs/network) — наблюдение HTTP/XHR/fetch,
  ожидание ответа после действия и управление сетевыми маршрутами.
- [Playwright: BrowserContext](https://playwright.dev/docs/api/class-browsercontext) —
  состояние cookies/localStorage и опционально IndexedDB; его можно передавать в памяти.
- [Stagehand: Observe](https://docs.stagehand.dev/v4/basics/observe) — обнаружение действий,
  структурированный результат и проверка перед исполнением. Это образец разделения
  наблюдения и исполнения, не решение об установке Stagehand.
- [Browser Use: параметры агента](https://docs.browser-use.com/open-source/customize/agent/all-parameters) —
  инструменты, ограничения шагов, времени и повторов, история и структурированный вывод.
  Это сравнительный источник, не решение о новой зависимости.
