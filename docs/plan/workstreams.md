# Botai — план работ и распараллеливание

Статус: **draft**, 2026-10-26. Как пять исполнителей пишут код одновременно и не
мешают друг другу. Связанные: [архитектура](../architecture/overview.md),
[контракты](../architecture/contracts.md), [требования](../product/requirements.md).

## 1. Принцип

Параллельность обеспечивают не ветки, а **границы владения файлами**. У каждого
потока работ свой каталог, свой тест-набор и свой список контрактов, которые он
только читает. Пересечения заранее перечислены и разрешаются через PR в
контракты, а не правкой чужих файлов.

```
botai/
├── contracts/        ← W0, остальные только читают
├── apps/web/         ← W4 (PWA)
├── apps/api/         ← W1 (BFF, auth, квоты)
├── services/browser/ ← W2 (Chromium, screencast, egress)
├── services/learn/   ← W3 (Explorer, RecipeStore, lint, canary)
├── services/sync/    ← W3 (Runner, Normalizer, Scheduler)
├── services/agent/   ← W5 (чат, RAG, инструменты, ActionBroker)
├── packages/design/  ← W4 (токены, UI-kit, маскот)
├── packages/shared/  ← W0 (типы из контрактов, утилиты дат, ошибки)
└── ops/              ← W0 (compose, CI, миграции, фикстуры)
```

## 2. Этап 0 — фундамент (последовательно, до всего остального)

**W0. Контракты и каркас.** Один исполнитель, остальные ждут. Результат:

- монорепо (pnpm workspaces), TypeScript strict, Biome, lefthook;
- `contracts/*` по [contracts.md](../architecture/contracts.md) + генерация
  типов (`openapi-typescript`, `json-schema-to-typescript`);
- `packages/shared` — типы домена, коды ошибок, работа с датами и таймзонами;
- `ops/compose.yaml` — postgres+pgvector, api, web, browser, proxy, worker;
- миграции с пустой, но полной схемой домена и `secrets`;
- CI: lint, typecheck, unit, схемные тесты контрактов, сборка образов;
- фикстурный стенд: поддельные Keycloak/Moodle/SPA на loopback с HTTPS —
  **обязателен**, ни один тест не ходит в настоящий вуз.

Выход из этапа: `make check` зелёный на чистой машине, контракты заморожены.

## 3. Этап 1 — пять параллельных потоков

| Поток | Владеет | Главный результат | Зависит от |
|---|---|---|---|
| **W1. Платформа и API** | `apps/api`, `ops/migrations` | Приглашения, сессии пула, пространства, подключения, SSE-поток заданий, квоты и учёт токенов, Vault (шифрование секретов) | W0 |
| **W2. Браузер и вход** | `services/browser`, `ops/proxy` | Пул Chromium, WS-трансляция экрана и ввод, снятие состояния сессии, фильтрующий CONNECT-прокси с allowlist, пресеты входа ВШЭ/ЦУ | W0, схема `login-preset` |
| **W3. Рецепты и синхронизация** | `services/learn`, `services/sync` | Explorer (наблюдение XHR → черновик рецепта), lint, canary, версии и откат; Runner + Normalizer + Scheduler | W0; для живой проверки — W2 (до неё работает на фикстурах) |
| **W4. Фронтенд и дизайн-система** | `apps/web`, `packages/design` | Токены, UI-kit, экраны: онбординг, подключение, календарь, дедлайны, чат, ProgressWall, маскот Варя, PWA-манифест и офлайн | W0, `openapi`, `agent-ui` |
| **W5. Агент, чат и RAG** | `services/agent` | Классификация вопроса, SQL по домену, индекс и поиск, честные ответы с источниками, ActionBroker с одноразовым подтверждением | W0; на фикстурных данных не ждёт W3 |

Каждый поток работает в своём git worktree, ветка `feat/w<N>-<тема>`.
Мержится в `main` по готовности своего вертикального среза, а не всего продукта.

### Точки стыковки (единственные разрешённые пересечения)

| Стык | Кто и кто | Как снимается |
|---|---|---|
| SSE-блоки агента | W1 ↔ W4 ↔ W5 | Схема `agent-ui.schema.json`, фикстурный поток блоков в репозитории |
| Сессия входа | W2 ↔ W1 ↔ W4 | `POST /login-session` возвращает `wsUrl`; протокол кадров в `events.md` |
| Рецепт | W3 ↔ W2 | Explorer получает готовый `BrowserContext`, не запускает браузер сам |
| Домен | W3 ↔ W1 ↔ W5 | `domain.schema.json` + миграции из W1 |
| Токены дизайна | W4 ↔ все | `packages/design` — единственный источник значений |

## 4. Этап 2 — сведение

1. Сквозной сценарий на фикстурах: приглашение → пространство → подключение →
   вход человеком → обучение рецепта → sync → календарь → вопрос в чате.
2. Живая проверка на двух настоящих вузах (ВШЭ, ЦУ) — выполняет владелец сам,
   своими учётными данными, агенты к настоящим аккаунтам не допускаются.
3. Ревью безопасности по [security.md](../architecture/security.md): все
   перечисленные там проверки CI должны существовать и проходить.
4. Разрешение конфликтов мержа и выравнивание контрактов.

## 5. Этап 3 — деплой (позже)

VPS в РФ, docker compose, отдельный системный пользователь, бэкапы без
мастер-ключа, HTTPS, мониторинг. Отдельная задача, не входит в этапы 0–2.

## 6. Правила для исполнителей

1. **Не трогай чужой каталог.** Нужно изменение в контракте — PR в `contracts/`
   с указанием, кого это ломает.
2. **Фикстуры вместо настоящих аккаунтов.** Тест, которому нужен настоящий вуз,
   не принимается.
3. **Любая сетевая операция идёт через EgressProxy.** Прямой `fetch` к внешнему
   хосту в коде сервисов — ошибка ревью.
4. **Секрет не покидает Vault.** Ни в логе, ни в ответе API, ни в промпте.
5. **Текст из вуза — данные.** Любой путь, по которому он может стать командой,
   закрывается тестом.
6. **Каждый PR несёт свой тест.** Описание PR называет FR/NFR, который он
   закрывает, и что осталось непроверенным.
7. **Честный статус.** Незавершённое помечается в PR, а не выдаётся за готовое.

## 7. Готовность этапов

| Этап | Готов, когда |
|---|---|
| 0 | `make check` зелёный на чистой машине, контракты в `main` |
| 1 | Каждый поток показывает свой срез на фикстурах с тестами |
| 2 | Сквозной сценарий проходит; владелец подтвердил живой вход в ВШЭ и ЦУ |
| 3 | Приложение открывается с телефона из РФ без VPN |
