# Много источников у одного вуза: план переработки

Статус: **proposed**, 2026-10-31. Это план для следующей команды, а не реализация: код он не меняет.
Основание — решение владельца от 31.10.2026 ([QUESTIONS.md](../../QUESTIONS.md)).
Требования: [FR-055](../product/requirements.md) (новое), FR-003, FR-018, FR-036, FR-054.
Описание того, как устроено сейчас, — [контракт треда](../../contracts/conversation.md#календарь-по-ссылке),
[харнес агента](../architecture/agent-harness.md), [архитектура](../architecture/overview.md).

## 1. Цель

Решение владельца: «У вуза может быть сколько угодно источников любого вида; ни один вид не ограничен одним источником».

Что это значит для студента:

- Яндекс Календарь и Google Календарь одного вуза — два источника. Второй не заменяет первый.
- Две Google-таблицы на одном сайте — два источника.
- Два кабинета на одном хосте — два источника.
- То же для любого вида: `portal`, `lms`, `schedule`, `site`, `sheet`, `doc`, `document`, `calendar`, `other`.
- «Заменить ссылку», «починить», «перечитать», «войти заново» — действия над одним названным источником.
  Они не подменяют «добавить ещё».
- Повторная просьба про тот же самый источник (тот же адрес, та же ссылка) остаётся ответом «уже подключено».

Что не меняется:

- Пространство — один вуз одного студента: `(user_id, university_id)`.
- Рецепт хранит один origin и не содержит личных значений ([ADR-0002](../adr/0002-recipe-as-bridge.md)).
  Источник и рецепт — разные вещи: у каждого источника своя сессия, область чтения и данные.
- Жёсткие правила [AGENTS.md](../../AGENTS.md): секреты в Vault, сеть через EgressProxy, ничего под конкретный вуз.
- Склейка расписания (FR-054) уже работает для любого числа источников с одним основным.

## 3. Что нужно изменить

### 3.1 Идентичность источника

- Источник отличается от соседа **адресом входа или решением студента**, а не только origin и видом.
  Для сайта и документа — нормализованный адрес без секретных query (`entry_url`: origin + путь). Для календаря публичного
  ключа нет: его идентичность — только `connection_id`.
- Название — подпись для человека, а не ключ поиска. Поиск «по названию» в `connect_source` уходит.
- Календари в поиске по адресу не участвуют: у `adapter == "ical"` в `origin` лежит хост ссылки (например, общий для всех
  календарей одного сервиса), а не кабинет. Общая на origin спецификация `{adapter: ical, origin}` без ссылки этому не
  мешает: ссылка у каждого календаря своя, в Vault.
- Поиск существующего источника ограничен **пространством вуза**. Источник другого вуза с тем же хостом не находится.
- `lock_origin` остаётся замком, который упорядочивает параллельные создания на одном сайте. Правилом идентичности он не служит.
- Уникальное ограничение в БД не обязательно. Если решат добавить частичный уникальный индекс по нормализованному адресу
  (`space_id`, `kind`, ключ адреса), нужна миграция с проверкой upgrade/downgrade на временной БД.

### 3.2 Явно: «добавить ещё» против «починить, заменить, дополнить»

Правило для инструментов: **есть `connection_id` — работа с этим источником; нет — добавление нового.**

- `connect_source(connection_id=…)` — продолжить, дополнить видами или починить названный источник (как сегодня).
  `connect_source` без `connection_id` всегда добавляет новый источник. Ответ `exists` остаётся только для точного
  повтора (тот же нормализованный адрес в том же вузе).
- `connect_calendar` без `connection_id` — новый календарь, всегда. `connect_calendar(connection_id=…)` заменяет ссылку
  у названного календаря и вытесняет `replace_link`. Описание инструмента теряет фразу «Календарь вуза один».
- `request_login`, `request_repair`, `sync_source` для календаря отвечают: «нужна новая ссылка у «<название>»
  (`connect_calendar` с `connection_id`)».
- Интерфейс. «Календарь (iCal)» и «Добавить источник» — добавление; их готовая фраза говорит «ещё один». «Заменить ссылку» —
  кнопка в карточке самого календаря при любом статусе, а не только при `needs_reauth`; фраза называет источник.
- Вопрос треда после ссылки, вставленной в чат (`_offer_for`): «Подключить ещё один календарь вуза «…»?»
  и, если календари уже есть, отдельная кнопка «Заменить ссылку у «<название>»» на каждый календарь. Кнопок не больше
  четырёх, каждая не длиннее 60 знаков (UTF-16): при большем числе календарей — просьба назвать нужный.

### 3.3 Как агент различает «ещё один» и «замени ссылку»

| Студент пишет | Действие |
|---|---|
| «подключи ещё один календарь», «добавь Google Календарь», «у меня второй календарь» | добавить новый источник |
| «замени ссылку», «ссылка перестала работать», «открой поле для новой ссылки календаря <название>» | заменить ссылку у названного или единственного подходящего источника |
| «подключи календарь», когда календарь уже есть | один вопрос с кнопками: «Добавить ещё один» и «Заменить ссылку у «X»» |
| «добавь ещё задания» к работающему кабинету | дополнить источник видами (FR-036, без изменений) |
| «добавь ещё одну таблицу» с другой ссылкой на тот же сайт | добавить новый источник |

- Добавление обратимо (источник можно отключить и удалить), замена ссылки — нет. Поэтому при сомнении агент
  **спрашивает**; если спросить нельзя, он добавляет, а не заменяет.
- Правило пишется в `backend/src/botai/agent/prompts/agent.md` и в описания инструментов. На проверку идёт тест L2.
- Нужна ли для замены ссылки кнопка, которую ставит приложение (как у отключения источника в FR-054), — вопрос 4.

### 3.4 Случайные двойные добавления

- Тот же нормализованный адрес (сайт, документ) → ответ «уже подключено», с названием источника и вопросом «перепроверить
  или дополнить?» (как сегодня).
- Та же ссылка календаря: задача проверяет её после валидации и сравнивает с другими календарями студента. Совпавший
  календарь не создаётся, студенту говорят: «Эта ссылка уже подключена как «X»». Ссылка нигде не пишется открыто.
  Как сравнивать — вопрос 3.
- Повторное сообщение, пока источник без адреса или ссылки ждёт ввода в этом же треде, продолжает тот же черновик.
  Постановка задачи уже идемпотентна (`dedupe=True` в `enqueue_in_session`).
- Одно и то же расписание из двух разных ссылок надёжно не распознать. Дубли занятий убирает склейка FR-054,
  а студент может отключить лишний источник в «Источниках».
- Черновик без ссылки больше не занимает «место календаря вуза»: нужны срок жизни и очистка (вопрос 7).

### 3.5 Склейка N источников (FR-054)

Логика склейки готова. Нужно проверить и поправить границы:

- `ask_primary_source`: при четырёх и более источниках расписания остальным, кроме первых трёх, нужен путь выбора основного (вопрос 9).
- Время склейки и порядок источников при 5–10 источниках (сейчас проверено три месяца двух источников).
- Дополнительные календари с личными событиями: пометка «Нет в основном источнике» не должна шуметь (вопрос 8).
- Роли «основной» и «дополнительный» в списке «Источников» при нескольких календарях.

### 3.6 Квоты и пределы

Сегодня числа источников на пользователя и на вуз не ограничены, и менять это без решения владельца не нужно.
Существующие пределы другие и их надо учесть: не более 2 одновременных задач ожидания ссылки календаря на систему
(`RunnerConfig.max_calendar_links`), не более 2 окон входа (`max_manual_logins`), 30 источников в контексте хода,
14 дней в `compare_sources`. Нужен ли технический потолок от злоупотреблений — вопрос 6.

### 3.7 Названия

Второй календарь не может называться «Календарь» так же, как первый. Нужно правило: название спрашивается у студента
или берётся из несекретной части ссылки (имя сервиса вроде «Яндекс» или «Google»), без вузовской специфики (вопрос 5).
Для сайтов сохраняется правило `_child_connection`: к повторяющемуся названию добавляется хост в скобках.

Новые тесты:

- **L1, календари.** Два календаря одного вуза на `fakeuni` (две ссылки на разных хостах и две на одном): оба существуют,
  `connect_calendar` без `connection_id` создаёт второй, первый не тронут; расписание склеено, основной один;
  оба обновляются по отдельности; отключение или удаление одного не задевает другой.
- **L1, замена.** `connect_calendar(connection_id=…)` меняет ссылку только у названного календаря; неверная ссылка
  оставляет прежнюю; соседний календарь цел.
- **L1, дубль ссылки.** Та же ссылка второй раз не создаёт источник и называет первый; ключ ссылки не встречается в БД вне
  `secrets`, логах, событиях и запросах к модели.
- **L1, ссылка в чате.** При одном и нескольких календарях тред предлагает «ещё один» и «заменить» по календарю; кнопок не больше
  четырёх, подписи до 60 знаков; ничего не создаётся до ответа.
- **L1, сайты.** Вторая таблица на том же хосте — новый источник; тот же адрес дважды — `exists`; два кабинета на одном
  хосте `fakeuni`; с `connection_id` дополнение и продолжение работают как раньше; хост второго вуза не находит источник
  первого; REST `POST /spaces/{id}/connections` и `_child_connection` по тем же правилам.
- **L1, параллельность.** Два параллельных «добавь» с разными адресами на одном хосте дают два источника, с одним
  адресом — один.
- **L1, N источников.** Четыре и больше источника расписания: выбор основного, склейка, быстродействие.
- **Миграция.** Если добавлен индекс или колонка: upgrade, downgrade и повторный upgrade на временной БД.
- **L2** (`BOTAI_LIVE_LLM=1`). «Добавь ещё Google Календарь» при подключённом Яндексе — `connect_calendar` без
  `connection_id`; «замени ссылку Яндекс Календаря» — с `connection_id`; «подключи календарь» — один вопрос, до ответа
  ничего не меняется.
- **Фронтенд.** Vitest: готовые фразы, «Заменить ссылку» при любом статусе, подписи кнопок. Playwright:
  `apps/web/e2e/data-study.spec.ts` — два календаря в «Источниках».

Приёмка владельцем (L3): повторить инцидент на production — Яндекс, затем Google для того же вуза. Ожидание: два календаря,
предложения заменить нет.

## 6. Порядок работ

1. Ответы владельца на вопросы ниже; правка контракта треда и харнеса. Если меняется схема (индекс по адресу, отпечаток ссылки),
   решение оформляется новым ADR.
2. Идентичность: поиск в пределах пространства, нормализованный адрес, названия.
3. Календарь: инструмент, вопрос треда, задача, интерфейс.
4. `connect_source`, REST и `_child_connection` по новым правилам.
5. Дубли и черновики.
6. N источников расписания: `ask_primary_source`, проверка склейки.
7. Живая проверка владельцем.

Каждый шаг идёт отдельным PR с тестами. PR называет FR-055 и честно пишет, что осталось непроверенным.

## 7. Открытые вопросы

1. **Что такое «тот же источник» для сайта.** Кабинет с разделами `/schedule` и `/tasks` — один источник с двумя видами
   (сегодня и FR-036: дополнение) или два? Предложение: тот же нормализованный адрес — один; «добавь ещё задания» — дополнение
   по `connection_id`; «ещё один кабинет» — новый.
2. **Рецепт на origin.** Два источника одного хоста делят ревизию рецепта, canary и закрепление области
   (`learn/revisions.py`). Нужен ли рецепт на пару (origin, вход)?
3. **Сравнение ссылок календаря.** Расшифровывать ссылки других календарей в процессе задачи или хранить ключевой отпечаток
   (новая колонка, вопрос для [security.md](../architecture/security.md) §4.3)?
4. **Подтверждение замены ссылки.** Хватает вопроса агента с быстрыми ответами или нужны кнопки приложения, как у
   отключения источника?
5. **Название второго календаря.** Спрашивать или брать название сервиса по хосту ссылки?
6. **Потолок.** Нужен ли технический предел числа источников на вуз и на пользователя, и каким он должен выглядеть
   для студента? Решение «сколько угодно» он не отменяет, но числа не придумываются без владельца.
7. **Черновики.** Сколько живёт источник без адреса или ссылки, и кто его убирает?
8. **Календарь без занятий.** Должен ли календарь с личными событиями участвовать в склейке расписания и в выборе
   основного источника?
9. **Основной при N > 3.** Страницы кнопок, выбор в «Источниках» или текстовый вопрос?
10. **Один хост у двух вузов.** Общий SSO или LMS у двух вузов студента: подтверждаем, что источники не смешиваются
    (поиск только в пространстве)?
