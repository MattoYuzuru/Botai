# План рефакторинга длительного исследования

Статус: **разрешён владельцем, реализация начата**, 29.10.2026.
Цель: продолжать дорогое исследование после перезапуска и границы среза, сохраняя фабрику,
изоляцию пользователя, ограничения записи и проверяемое происхождение данных.
[Решение](../adr/0011-resumable-source-discovery.md), [LLD](../architecture/source-research.md).

## Первый сквозной этап

1. Ввести неизменяемый claim fence на существующем Job; защитить context, завершение,
   heartbeat, публикацию сессии, ревизии и domain commit. Разделить retry failures и
   кооперативное продолжение; не сбрасывать `attempts`.
2. Добавить зашифрованный checkpoint 1:1 с Job, Vault codec, additive migration,
   tenant/claim/intent/version checks, TTL и ограничение размера.
3. Разделить durable knowledge и ephemeral Discovery runtime. Сохранять frontier после
   действий; при новом BrowserHandle перепроверять страницы, строить новые refs и
   возвращаться к незавершённому фронту. Сохранённые кандидаты заново canary, без повторного
   авторства успешных видов. Граница среза освобождает браузер и продолжает тот же Job.
4. Добавить конфигурацию, диагностические счётчики и сквозные synthetic fixtures.
   Включение нового пути на production — отдельная выкладка после полного CI.

Публичные recipe/API/SSE schemas в первом этапе не меняются. Текущие незакоммиченные
исправления предыдущего исследования сохраняются; это одна рабочая ветка с явным статусом.

Код первого этапа подготовлен в рабочей ветке: fenced Job/context, зашифрованная таблица
checkpoint, сохранение frontier и предложений перед canary, свежая проверка после рестарта,
накопительные бюджеты и feature flag. Включение по умолчанию остаётся выключенным.
Следующие контрактные capabilities/преобразования из раздела ниже сюда не входят.
Ограничения первого этапа: TTL удаляет временные счётчики вместе со знаниями; закрепление
первого sync проверяет intent/spec, а вычисленные диапазоны динамических дат не сохраняет.

## Приёмка

| Сценарий | Наблюдаемый результат |
|---|---|
| A потерял claim, B получил тот же Job | A не меняет checkpoint, события, сессию, ревизию, снимок и секретные ответы B |
| Recovery до нового claim | Старый context не переводит queued обратно в running |
| Повторный claim тем же worker name | Поколение отличает старую попытку |
| Превышен бюджет одного среза | Checkpoint сохранён, браузер закрыт, тот же Job продолжен без расхода failure retry |
| Рестарт в середине обхода | Frontier и бюджет восстановлены; старые DOM refs не исполняются |
| Сбой после commit активации до sync | Атомарная квитанция позволяет продолжить sync; новая ревизия и повторное авторство не создаются |
| Уже есть кандидат | Свежая canary даёт новые реальные records; автор повторно не вызывается без причины |
| Уточнение во время логина/MFA | Тот же защищённый вход завершается без повторных вопросов; до исследования применяется inbox, отмена по-прежнему отзывает claim |
| Scope/intent изменился | Исключённые виды не читаются и старое подтверждение не активирует другой результат |
| Чужой user/job/connection, stale CAS | Чтение/запись отклонены, ciphertext не переносим между контекстами |
| Общая ревизия изменилась во время первого sync | Закрепление за подтверждённым spec отклоняет подмену до записи; снимок сохранён |
| Отражённый секрет в URL и ротация сессии | Адрес исключён из памяти, старое значение не появляется в prompt следующего runtime |
| Проверка plaintext | В DB/логах/API нет маркеров checkpoint/сессии/ввода |
| TTL/неизвестная версия/повреждение | Нет ложного восстановления или потери снимка; после TTL теряются временные знания и счётчики исследования, квитанция активации остаётся |
| Additive migration | Upgrade сохраняет старые строки; downgrade/re-upgrade только временной БД |
| CAPTCHA/POST/WS/новый host | Прежние границы сохраняются, автоматического обхода нет |

Локально — затронутые pytest с обязательным Postgres, реальные Chromium/worker/proxy
на fakeuni, Ruff/Pyright и guards. Проверки выполняются через workstation-dev resource `heavy`
в спокойной фазе общего checkout. Полный `make check`/CI — на окончательной интегрированной
ревизии. L2 модели и реальные вузы локальными L1-сценариями не подтверждаются.

## Следующие этапы

Отдельные контрактные PR добавляют auth binding и необходимые преобразования/браузерные
capabilities. Для каждого — совместимость старых рецептов, отрицательные security fixtures,
canary в новом runtime и replay без модели. Новые инфраструктурные узлы не планируются.
После CI владелец проверяет настоящие источники: вход, canary, нормализованный экран,
повторный sync. Только после этого допустим статус production-verified.
