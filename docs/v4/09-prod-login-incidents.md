пробовать активный общий рецепт канарейкой (это дешевле 2 000 запросов); различать
`RESEARCH_BUDGET` и `SOURCE_RATE_LIMITED`.

### 2.3 Точный корень (лоадер)

1. **Неизвестная форма входа + отсутствие login-пресета для `misis.ru`** (в `login_presets`
   есть только `edu.hse.ru`, `lk.hse.ru`, `my.centraluniversity.ru`): поток не может
   подтвердить сессию. `_try_finish` (`browser/login.py:776–833`) требует, чтобы страница
   была узнаваемой, не требовала авторизации и чтобы `_entry_ready` принял входной URL;
   для неизвестного портала/редиректа на другой хост это не выполняется, и цикл ждёт.
2. **«Я вошёл» — просьба, а не доказательство** (`_DONE_UNCONFIRMED_HINT`,
   `done_grace_s=90`): после нажатия сервер проверяет и, не подтвердив, продолжает ждать;
   `human_wait_s=30 мин`, но экран живёт по TTL 10 мин с продлением от ввода.
3. **Единственный терминатор — TTL экрана.** После 10 минут без ввода экран истекает, и
   задача отменяется «the login screen was closed»; UI узнаёт об этом только постфактум
   («Подключение отменено»). До этого `waiting_user` неотличим от «вечной загрузки».
4. **Кросс-хостовый вход не дотянут**: 8 POST отклонены `auth_host_not_allowed`, 2 —
   `auth_read_only`, 16 — `auth_no_permit`; ещё 26 POST страницы заблокированы read-only
   контекстом — часть шагов входа физически не проходит через guard.

### 2.4 Побочный инцидент: пароль в чате

В 07:48:48 пользователь отправил в чат логин и пароль открытым текстом. Агент отказался
их принимать и попросил удалить сообщение, но **сообщение осталось в истории**
(`chat_messages`). Значения в этот документ не переносятся; для v4 это аргумент за secret
broker и вычистку секретоподобного из истории.

Фикс: явные состояния «вход не подтверждён / нужен человек» с таймаутом и сообщением в
чат; подтверждение через probe/навигацию для неизвестных порталов; научение пресета из
ручного входа; продление TTL только по WS-виду и с уведомлением; не отменять задачу
молча; удалять секретоподобные сообщения.

## 3. Удалённый экран: реальные метрики

Конфиг (`browser/screen.py`): `ttl_s=600` (+ продление на 600 с каждым вводом до

| МИСИС `…3YXZZ8` | 1 337,9 с (07:48:00–08:10:17) | 6 345 | **1 048** | **4,74** | `ttl` (10 мин после последнего ввода) |

отказов 403**. Тикет одноразовый и живёт 60 с (`browser/router.py`), поэтому каждый
реконнект требует нового тикета. Фактическая картина: HSE — 1 accepted + 1 отказ (повтор
со старым тикетом); МИСИС — 8 accepted + 7 отказов (в основном повторный старый тикет

07:58:33, 07:59:10, 07:59:46, 08:00:02 (каждые ~30–45 с), между ними — 403 на устаревший
тикет. Это похоже на нестабильный канал (VPN/сеть) и/или цикл реконнекта в UI.

Чего нет в метриках: **RTT, байты, фактический quality/fps, причины обрыва WS, число
дропнутых кадров** — не логируются. Качество и fps подбираются в памяти и умирают вместе
с экраном; восстановить «как было» нельзя. Вывод: экран работал на 1,5–4,7 fps при
390×760, типичный ввод-эхо без метрик; для v4 — включить персистентные метрики
(frames/bytes/fps/dropped/quality/rtt/close-reason), пинговать WS, обновлять тикет при
обрыве и не строить реконнект на одноразовом тикете.

## 4. Иностранный VPN и таймауты

- **Caddy access-логов для `botai.mnema.app` нет**: в блоке сайта нет директивы `log`
  (только `encode` + `reverse_proxy`), `/var/log/caddy` пуст, глобальный `log` управляет
  runtime-логом. Поэтому **499/504 посчитать нельзя** — это блокер, а не «нет проблем».
- Что видно в `journalctl -u caddy`: 11 предупреждений `aborting with incomplete response
  … reading: context canceled` в окне **07:36:12–08:00:52** (длительности 0,01–0,5 с) —
  клиент оборвал потоковый ответ (SSE/долгий HTTP), сервер не таймаутил. Плюс 16 ошибок
  `502` на рестартах api 30.10 10:30/12:06/13:22–13:23 (не текущие инциденты).
- **Сервер не тормозил**: в диагностике api 8 183 завершённых запроса, из них ни одного
  >10 с; статусы 200 ×7 857, 204 ×92, 201 ×22, 202 ×36, 304 ×145, **401 ×17, 403 ×3,
  404 ×6, 405 ×3, 400 ×1, 503 ×1**; 5xx в окнах логина нет.
- **Владелец ходил через зарубежный адрес**: 2.27.23.184 (keykomi из
  `docs/plan/deployment.md`) сделал **1 731** запрос к API: 384 списка тредов, 311
  подключений, 52 расписания, 48 «сегодня», 47 дедлайнов, 29 `/me` (8 из них 401; всего у трёх
  клиентов 13 × 401) — браузерная сессия шла через внешний сервер, часть запросов
  теряла сессию. Два приглашённых клиента сделали 617 и 815 запросов.
- Причина клиентских обрывов не доказуема без access-лога: сервер отдаёт быстро,
  наблюдаются клиентские отмены стримов и реконнекты WS (раздел 3). Отделить «VPN» от
  «UI перезагружает страницу» по имеющимся данным нельзя.

Фикс: включить Caddy access-лог (с вырезанием `request`-полей и query), добавить
`dial_timeout`/`response_header_timeout` в блок `botai` (как у `mnema.app`: 2 с/30 с),
логировать WS close-code и длительности стримов, настроить алерты на 499/5xx/WS-403.

## 8. Что осталось неизвестным

1. Почему при наличии расшаренного рецепта `lk.hse.ru` прогон приглашённого не дошёл до
   `canary.*` — по трассам видно только 340 фаз `observe` и 6 `author`; возможно, рецепт
   не был выбран базой из-за отличий сессии/вида, но прямого события нет.
2. Точные URL страниц, на которых стоял исследовательский контекст: диагностика хранит
   только хеши хостов/путей; 344/433 снимка с `auth_required` — вывод по флагу, не по URL.
3. Подтвердился ли вход в МИСИС фактически (страница после 07:54 стабильна и похожа на
   кабинет): сервер не зафиксировал `auth.session.ready`; проверить можно только живым
   прогоном с тем же аккаунтом.
4. 499/504 и распределение задержек по клиентам — нет Caddy access-лога; вывод о «VPN»
   опирается на внешний адрес владельца, WS-реконнекты и клиентские отмены.
5. Финальные 2 минуты HSE-задачи (08:04:28–08:06:28) — диагностика обрезана по
   `event_budget`; восстановлены только итоговые `_research_usage` и сообщения чата.
