# 19. Действия: политика автономии, журнал, идемпотентность (фаза 3.1)

Статус: **реализовано 2026-10-31** (пункт 3.1 плана, [D-006](06-decisions.md)). Код:
`backend/src/botai/actions/`, инструменты `agent/v4/tools/actions.py`, REST
`actions/api.py`, миграция `d6b8f2a14c73`; тесты `backend/tests/actions/`,
`backend/tests/api/`, `backend/tests/db/test_actions_migration.py`.

Документ объясняет: как агент получает право на запись, как это решается, что попадает в
журнал, как обеспечена идемпотентность и что осталось. Основание — D-006: **write-действия
разрешены**, политику задаёт владелец (`auto`/`ask`/`never`), деструктивные и денежные по
умолчанию `ask`, а не запрещены; каждое действие журналируется и идемпотентно там, где
возможно; агент показывает, что именно отправляет.

## 1. Модель политики

Таблица `action_policies`: `(user_id, scope_kind, scope_id, action_class) → mode, limits,
note`. Области: `global`, `site` (host), `space`, `source`; **самая конкретная побеждает**
(`source > space > site > global`), при равенстве — более поздняя по `updated_at`.

Классы действий (`action_class`): `read`, `write_soft`, `write_destructive`, `money`, `auth`.
Модель может объявить класс, но **не может его занизить**: явный `read` на DELETE остаётся
деструктивным; маркеры `money`/`auth` повышают класс; браузерные действия — минимум
`write_soft`. Это защита от «агент назвал отправку формы чтением».

Режимы (`mode`):

| mode | Что происходит |
|---|---|
| `auto` | выполняется сразу, журнал пишется |
| `ask` | владельцу показывается точный method/URL/поля; выполнение — после «Разрешить» |
| `never` | не выполняется, в журнал пишется отказ, модели возвращается понятная причина |

**Дефолты:** `read` → `auto`; `write_soft`, `write_destructive`, `money`, `auth` → `ask`.
Лимиты владельца (`max_per_hour`/`max_per_day` в `limits`) могут поднять `auto` до `ask` с
причиной; понизить класс или обойти `never` лимит не может.

## 2. Инструменты агента

`build_action_tools(services, user_id, http_transport, control)` (подключается в wiring v4):

| Инструмент | Что делает |
|---|---|
| `action_propose` | описывает действие (класс, method/URL, поля, intent), не отправляя; возвращает решение политики/вопрос владельцу |
| `action_execute` | выполняет по политике (`auto`), либо фиксирует `ask`/`never`; идемпотентен по ключу |
| `action_history` | читает журнал действий владельца (фильтры по источнику/классу/решению) |

Схемы требуют `transport`+`intent` и (для `http`) `method`/`url`; поля с именами вида
`password`/`token`/`secret` в журнал не попадают. Если у run'а нет канала вопросов,
`ask`-действие возвращает `approval_required` и ждёт решения через API.

## 3. Исполнение и журнал

`actions/engine.py` — единственная точка «решить и выполнить»: `prepare → decide → execute →
journal`. HTTP-действия используют тот же клиент, что `http_request`; браузерные — переданный
`BrowserControl` (у API браузера нет: такие действия выполняются внутри run'а).

`actions_log` хранит: решение и режим, класс и область, `intent`, предложение (redacted),
`request {method, url, body_kind, body_bytes, body_sha256}` (значения тела не сохраняются —
только хеш), `result` (статус/краткий итог), `rollback` (подсказка, если playbook её дал),
`idempotency_key`, ссылки `run_id`/`job_id`/`source_id`, времена. Заголовки и cookie — только
имена; секретные поля — `***`; bearer/JWT в свободном тексте маскируются. Тест с тремя
sentinel-секретами проверяет, что их нет ни в предложении, ни в запросе, ни в результате.

**Идемпотентность.** Ключ — явный (`idempotency_key`) или производный от run'а и канонического
payload (`run:<run_id>:sha256(...)`). Повтор с тем же ключом возвращает уже записанный
результат и **не отправляет** запрос второй раз; уникальный индекс `(user_id,
idempotency_key)` не даёт двум run'ам случайно выполнить одно и то же. Новый run с тем же
предложением — это законное второе действие.

## 4. REST

Все эндпоинты — под текущим пользователем; чужое → 404. Ошибки — problem+json с `code`.

| Метод и путь | Назначение |
|---|---|
| `GET /api/v1/action-policies` | список политик владельца |
| `PUT /api/v1/action-policies` | создать/обновить (`scopeKind`, `scopeId?`, `actionClass`, `mode`, `limits?`, `note?`) |
| `DELETE /api/v1/action-policies/{id}` | удалить политику |
| `GET /api/v1/action-policies/effective?url=&source_id=&space_id=` | эффективные режимы по классам (с `escalated`) |
| `GET /api/v1/actions` | журнал (фильтры `source_id`, `action_class`, `decision`, `limit`) |
| `GET /api/v1/actions/{id}` | одно действие |
| `POST /api/v1/actions/{id}/decision` | `approve`/`deny` для `ask`; 409 если уже решено/не спрашивалось |

Решение по `ask` записывает решение, но **не выполняет запрос из API**: журнал намеренно не
хранит тело/заголовки, поэтому отправить может только run, который владеет запросом и
браузером; повтор с тем же ключом подхватывает одобрение и выполняет ровно один раз.

## 5. v3-совместимость

`JobKind.ACTION` при `agent_engine=v3` идёт прежним путём (`agent/actions.py`), при `v4`
делегируется в `actions/legacy.py`: одобренный v3-proposal перепроверяет `approvedHash`,
исполняется новым движком и журналируется (`legacy:<proposal_id>`); повтор — `CONFLICT`;
политика `never` даёт `FORBIDDEN` без запроса. Старые строки и аудит не переписываются.

## 6. Тесты

`pytest tests/actions tests/api tests/db -q` — политики/дефолты/приоритет областей, L1 на
fakeuni: `auto` выполняется один раз, `ask` спрашивает и выполняет после «Разрешить» (или не
выполняет после «Запретить»), `never` не выполняет и не спрашивает; идемпотентность (повтор
не отправляет второй запрос); redaction (sentinel-секреты отсутствуют в журнале); невозможность
занизить класс; REST-контракты; v3-мост; миграция upgrade→downgrade→upgrade.

## 7. Что осталось

- **3.3/3.4 (фоновая автономия и стоимость)** не входили в эту итерацию: расписаний
  sync/health/repair и «продолжить после мягкого лимита» через UI пока нет; лимиты v4-runtime
  (`agent_limits_*`, hard stop) уже работают, учёт usage есть.
- API-решение по `ask` не исполняет запрос само (см. §4) — для браузерных действий это
  архитектурное следствие, что браузер живёт в run'е; для HTTP можно добавить inline-исполнение
  отдельным решением.
- Карточка действия в UI (детали предложения, «Разрешить/Запретить/Всегда для источника») —
  следующий шаг web-слоя; API для неё готов.
- Журнал не хранит тела запросов по дизайну (только хеш); для отката используются подсказки
  `rollback` из playbook, а не реконструкция тела.
