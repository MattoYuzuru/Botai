# 03. Источники и «Учёба»: единая модель, подключение, склейка

Статус: **спецификация пивота v4**, 2026-10-31. Основание — [README](README.md), [решения владельца](06-decisions.md) (D-004,
D-006, D-008, D-011, D-013, D-016, D-018) и [план](05-implementation-plan.md) §2. Здесь целевая модель источников и интерфейс
«Учёбы»; это не утверждение о реализации: как сейчас — [01-as-is.md](01-as-is.md), runtime/песочница/браузер —
[02-architecture.md](02-architecture.md). Потребители: `backend/src/botai/{sources,spaces,domain, agent,api}`, `apps/web/src`,
`contracts/`; изменение контракта — отдельным PR (`AGENTS.md` §9).

## 0. Кратко: что меняется

| Сейчас (v3) | v4 |
|---|---|
| `Space` — вуз **или** «Мои материалы» (`spaces/service.py:43`) | `Space` — только вуз; одно на пару «студент — вуз» |
| `Connection` — одно подключение на origin; второй кабинет на том же сайте — тот же источник | `Source` — живая запись; источников сколько угодно, второй кабинет/таблица/календарь живут одновременно |
| Знание о вузе — рецепт из 4 адаптеров (`sources/factory.py`) | **playbook**: декларативная часть, селекторы, JS, код, тесты, health, версии; рецепт — частный случай |
| Парсер пишет только фабрика; lint запрещает личные значения | агент пишет и правит playbook сам; песочница; личное — в параметрах и секретах |
| Склейка только расписания (`domain/merge.py`, FR-054) | общий overlay для любого вида: приоритет, доверие, дедуп, происхождение полей, конфликты |
| «Документы и вложения» — отдельный раздел, «Добавить документ» — отдельный шит | документ — источник или артефакт источника; отдельных раздела и мастера нет |

Главное: **вуз — единица интерфейса, источник — часть вуза, вид данных — свойство источника.** Агент сам добавляет, тегирует,
чинит и склеивает источники; владелец подтверждает и настраивает приоритеты.

## 1. Модель

### 1.1. Определения

- **University** — запись справочника (`universities`), общая для двух пользователей.
- **Space** — вуз одного пользователя: `unique(user_id, university_id)`; пространства без вуза нет.
- **Source** — любая точка доступа/данных у вуза: сайт, раздел, кабинет, LMS, найденный API, календарь по секретной ссылке,
  Google-таблица, документ по ссылке, загруженный файл, почта. Источник — «что это, где лежит, как читать, чем обновлять»; он
  живёт в БД, а не является типом адаптера в коде.
- **Kinds** — множество видов источника: природа (что за точка доступа) + данные (что читается).
- **Playbook** — знание «как читать и обновлять»: адрес, вход, эндпоинты, селекторы, код, проверки, тесты, происхождение, версии
  (§2).
- **Artifact** — прочитанное: страница, ответ API, файл, письмо, HAR, скриншот, лог; материал провенанса и RAG. **Overlay** —
  вычисление одного представления из нескольких источников вуза при чтении: приоритет, доверие, дедуп, заполнение пустых полей,
  конфликты (§4).

### 1.2. Что бывает источником (примеры владельца)

| Источник | Природа | Виды данных | Как читается |
|---|---|---|---|
| `lk.hse.ru` (кабинет ВШЭ) | сайт/кабинет | расписание, дедлайны, задания, оценки, новости | браузер + HTTP по найденным запросам |
| `my.centraluniversity.ru` (LMS ЦУ) | LMS | расписание, курсы, задания, дедлайны, оценки | сессия, API и SPA-страницы |
| `hse.ru`, страница документации ОП | сайт/документ | документы, новости | HTTP/HTML/PDF |
| Календарь Яндекса/Google/Outlook по секретной ссылке | календарь | расписание, дедлайны | без входа, только ссылка |
| Google-таблица «запись на экзамен» | таблица | дедлайны, задания, документы | публичный экспорт/API |
| PDF/DOCX/XLSX/скачанный файл | файл/документ | документы, расписание, дедлайны | извлечение текста/таблиц |
| Почта студента (фильтр по вузу) | почта | сообщения, документы, дедлайны | IMAP/API с app password |
| Произвольный сайт кафедры с дедлайнами | сайт | дедлайны, задания, документы | как любой сайт |

Второй календарь/таблица/кабинет — **новый источник**, а не замена (`FR-055`, D-004). Тот же нормализованный адрес или та же
ссылка второй раз не создаются: ответ «уже подключено».

### 1.3. Kinds: природа + виды данных

`kinds` — множество в БД и API, без единственного значения. **Природа:** `site` 🌐, `portal` 🏛, `lms` 🎓, `api` 🔌, `calendar` 🗓,
`sheet` 📊, `doc` 📄, `file` 📎, `mail` ✉️, `feed` 📰, `other` ❔. **Данные:** `schedule` (занятия), `deadlines` (сроки), `assignments`
(задания), `courses` (предметы), `grades` (оценки), `people` (преподаватели), `locations` (аудитории), `news` (новости),
`documents` (документы/файлы), `messages` (письма/объявления).

Природу ставит агент при пробе; виды данных — из пробы и подтверждения владельцем; вид появляется в UI только при наличии записей.
Внутренний словарь возможностей чтения (`Kind` в `backend/src/botai/contracts/specs.py`) не плодит третий словарь: у него взаимно-однозначное
соответствие с видами данных (`scheduleEvents` ↔ `schedule`). Источник без подтверждённых видов — черновик и не виден в
производных экранах.

### 1.4. Идентичность источника

Источник отличается **адресом входа или решением пользователя**, а не origin'ом и не видом (отменяет поиск по origin,
`spaces/service.py:283`). `identity_key` — нормализованный адрес: `https`, хост в нижнем регистре (IDN → punycode), порт по
умолчанию отброшен, путь без завершающего `/`, фрагмент и секретные query удалены; для календаря — `link:<sha256(ссылки)>`
(открыто ссылка не хранится), файла — `file:<sha256>`, почты — `mail:<ящик>`. Один адрес в одном вузе — один источник; повтор
отвечает «уже подключено» со статусом, а не создаёт второй черновик. «Другой кабинет на том же хосте» — явное решение владельца:
агент спрашивает и создаёт второй источник с отдельным `identity_key` (`…/cabinet#2`) и отдельной сессией. `title` — подпись, не
ключ поиска; один сайт у двух вузов — два источника в разных пространствах, данные и сессии не смешиваются, общий playbook
возможен (D-018); предела числа источников/видов нет, операционные лимиты — не архитектурный потолок.

### 1.5. Инварианты

1. Нет данных «ниоткуда»: у каждой записи `source_id`, `external_id`, провенанс (`source_url`, `open_url`, `fetched_at`,
   `playbook_rev`, `artifact_id`); `(source_id, external_id)` уникален.
2. Источник отключается (данные скрываются, не удаляются) и удаляется (данные/секреты удаляются); отказ одного не ломает остальные.
3. Секрет источника (пароль, MFA, ключ-ссылка, app password) — только шифртекст в Vault, не в API/логах/промптах; cookie/сессия —
   рабочий материал инструментов (D-008).
4. Любое изменение данных прослеживается до прогона, артефакта и ревизии playbook.

### 1.6. «Мои материалы», файлы, вложения

Пространства «Мои материалы» больше нет: удаляются `MATERIALS_TITLE`/`MATERIALS_SHORT_TITLE`, индекс `uq_spaces_user_id_materials`
(`db/models.py:105-124`), фолбэки в `list_sources` и подписи. **Загруженный файл — источник** природы `file` с видом `documents` в
выбранном вузе (почти так уже работает: `attachments/service.py:start_ingest` создаёт подключение и `INGEST`). **Документ,
найденный на странице источника**, — артефакт этого источника; отдельного «документа без источника» не существует. Если
тред/переключатель не отвечает, к какому вузу файл, — агент спрашивает (по умолчанию вуз текущего треда). **Миграция:** один
вопрос владельцу, в какой вуз перенести источники «Моих материалов» (вуз один — автоматически); перенос сохраняет файлы и текст,
при отказе источники в архиве, пока не выбран вуз; D-016 разрешает пересоздание, но данные не удаляются без нужды.

## 2. Playbook: знание агента о том, как читать источник

### 2.1. Что это и чем заменяет адаптер

Playbook — версионируемое знание «как получить данные и как понять, что они не сломались». Не привязан жёстко к origin: может
описывать сайт/API и переиспользоваться двумя пользователями и двумя источниками одного вуза; личные значения (группа, ОП, ящик,
токен) — в параметрах источника и Vault, не в общем playbook. Сегодня фабрика (`sources/factory.py`) знает ровно четыре адаптера
(`recipe`, `moodle_ws`, `ical`, `document`) и запрещает агенту код. В v4 playbook заменяет и адаптер, и рецепт: рецепт — частный
случай `format=recipe`; агент может писать любой код парсера (Python/JS) и исполнять его в песочнице; проверка — тесты, canary на
сессии владельца и health прогонов. `adapter_specs`, `login_presets`, Factory v2 удаляются после миграции (05 §2.1), их содержимое
переносится в playbook.

### 2.2. Состав playbook

```jsonc
{
  "format": "code",                          // recipe | code | browser
  "university_id": null, "owner_id": null,   // null = общий; иначе личный
  "title": "ЛК ВШЭ: расписание и задания", "origin": "https://lk.hse.ru",
  "auth": { "mode": "session", "entry_url": "https://lk.hse.ru/",
            "login_steps": ["login-form", "mfa-if-asked"],
            "secret_refs": ["password", "cookies"] },
  "entrypoints": [
    { "url": "/api/schedule?week={weekStart}", "method": "GET", "format": "json" },
    { "url": "/api/tasks", "method": "GET", "format": "json" } ],
  "reads": [
    { "data_kind": "schedule", "request": "schedule", "paging": "dateWindow",
      "extract": "code", "keys": { "external_id": "id", "startsAt": "start" } },
    { "data_kind": "deadlines", "request": "tasks", "extract": "code" } ],
  "code": { "artifact": "sha256:…", "entrypoint": "parse.py:main", "language": "python" },
  "selectors": { "scheduleRow": "[data-lesson]" },   // если HTML/SPA без кода
  "schedule": { "every": "3h", "windowDays": 35, "rateLimitPerMin": 12 },
  "health": { "checks": ["session-valid", "schedule-non-empty", "fields-required"],
              "expected": { "scheduleEvents": { "min": 1 }, "maxAgeHours": 12 } },
  "tests": [ { "name": "расписание недели", "fixture": "artifact:…", "assert": "count > 0" } ],
  "provenance": { "learned_at": "…", "by": "agent", "run_id": "…", "session": "author",
                  "observations": ["artifact:…"], "model": "…" },
  "notes": "После смены семестра у /api/schedule меняется term — проверять."
}
```

Обязательны `format`, `origin`, `auth.mode`, `reads` (минимум один вид), `health`, `provenance`, `schedule`. Код и бинарные файлы
— в content-addressed хранилище артефактов, в БД — `sha256` и точка входа.

### 2.3. Декларативный recipe — частный случай

`format=recipe` — JSON по `contracts/recipe.schema.json` (окна дат, пагинация, repeat-правила, `uiUrl`, `links`, `attributes`),
исполняется детерминированно без песочницы кода: быстрый и дешёвый путь. Агент вправе написать recipe, дополнить его
кодом/браузерным планом или заменить кодом, если схема перестала выражать данные. Lint больше не запрещает личные значения;
требование другое: общий playbook без секретов и личных параметров (проверяется тестом на утечки), личное выносится в
`source_bindings.params` или playbook становится личным.

### 2.4. Исполнение в песочнице

Прогоны (`PROBE`, `SYNC`, `REPAIR`, `ACTION`) исполняет воркер в изолированной песочнице: произвольная сеть, HTTP-клиент, браузер
с сессией пользователя, Python/JS, файлы задания; никакого `eval` в процессе API (05 §2.2), лимиты — ресурсы/время/стоимость, а не
«нельзя». Вход playbook — `params` источника + secret-хендлы из брокера; выход — нормализованные записи по видам + артефакты +
отчёт health. Браузерный прогон использует реальный Chrome/CDP и профиль владельца (D-007); cookie, bearer, storage, HAR доступны
агенту (D-008), пароль/MFA/ключ-ссылка — нет. Артефакты (страницы, JSON, файлы, HAR, скриншоты, лог шагов, трасса) сохраняются —
это топливо починки и материал RAG (§4.5).

### 2.5. Жизненный цикл, health, откат

`draft → canary → active → deprecated | rolled_back`, как у ревизий рецепта (`learn/revisions.py`), но с более широким содержимым.
`draft` — написан, не проверен; `canary` — прогон тестов и health-проверок на сессии владельца, успех обязателен для `active`;
`active` — используется синхронизацией, прошлая ревизия хранится для отката. Health после каждого прогона: структура ответа,
обязательные поля, ожидаемая непустота, возраст данных; три `drift` подряд → откат на прошлую активную ревизию и задача починки.
История: прогоны и ревизии с автором (агент/владелец), временем, артефактами и диффом; откат — действие агента, не ручная правка БД.

### 2.6. Починка агентом

1. `SYNC` упал или health заметил drift → источник в `error`/`stale`, прежние данные остаются с пометкой устаревания.
2. Агент получает `REPAIR` с артефактами и трассой упавшего прогона, сам открывает источник (браузер/HTTP/код), сравнивает с
   playbook, находит изменившийся адрес/селектор/формат.
3. Правит playbook (селекторы, код, эндпоинт, параметры), пишет/обновляет тесты, прогоняет их на сессии владельца, публикует ревизию
   `draft→canary→active`.
4. Итог — короткий отчёт в чате источника: что сломалось, что изменил, что проверил, что осталось непроверенным. Не удалось — честное
   «не получилось», список попыток и что нужно от человека.
5. Прежние данные не теряются; ложная починка откатывается ревизией.

### 2.7. Два пользователя: общие playbook, раздельные данные

По умолчанию playbook **общий в пределах двух аккаунтов** (D-018), если не помечен личным: второй человек подключает вуз без
повторного обучения, но со своей сессией. Раздельны: аккаунты источников, сессии/cookie, секреты, учебные записи, личные
артефакты, память. Общи: reading- структура (адреса, селекторы, код), тесты, health; canary выполняется на сессии каждого. Личные
параметры (группа, ОП, факультет, ящик) — в `source_bindings.params`; если значение нельзя параметризовать, playbook становится
личным. Право «поделиться/сделать личным» — настройка.

## 3. Поток «Добавить источник»

### 3.1. Точки входа

Кнопка **«Добавить источник»** у каждого вуза и в панели «Источники»; свободная просьба в чате («подключи лмс ЦУ», «вот ссылка на
таблицу», «добавь календарь»); файл, приложенный в чат или выбранный в шите (файл становится источником); присланные агенту
ссылка/письмо/скриншот. Кнопка ведёт в чат с готовой просьбой (как `chat-links.ts`); отдельного мастера подключения и отдельного
потока для документов нет.

### 3.2. Шаги

1. **Вуз:** из пространства треда/переключателя; если неясно — вопрос с кнопками; если вуза нет — агент создаёт пространство.
2. **Что это:** агент классифицирует сам (§3.3); при сомнении — один короткий вопрос, а не выбор из списка.
3. **Проба (`PROBE`):** до сохранения — HTTP/браузер, проверка входа, поиск эндпоинтов и разметки, чтение образца; в домен ничего не
   пишется, источник не создаётся. Нужен вход — защищённый вход (D-008), затем проба продолжается.
4. **Виды:** из пробы выводятся природа и виды данных; превью показывает их словами, владелец поправляет («это не оценки, а баллы за
   курс»).
5. **Превью:** «вот что вижу» — сколько занятий/сроков/документов, охват дат, ближайшие записи, как часто обновляется, какой вход
   нужен; без придуманных процентов готовности, кнопки «Подключить», «Уточнить вид», «Показать образец».
6. **Сохранение:** источник `active` после первого успешного чтения, playbook rev1 `active`, расписание sync, индекс RAG, итоговая
   строка в чат; неудача не оставляет мусора — черновик удаляется по сроку или остаётся с «не завершено» и кнопкой «продолжить».
7. **Дальше:** источник в «Учёбе» со статусом и видами; данные в производных экранах; агент отвечает по ним с провенансом.

### 3.3. Как агент понимает тип

| Признак | Решение |
|---|---|
| `webcal://`, `.ics`, `/export/ics`, `ical`, опубликованная ссылка сервиса | `calendar`; ссылка — в защищённое поле |
| страница самого сервиса календаря (`calendar.yandex.ru`, Google Calendar) | не источник: объяснить, где взять ссылку экспорта |
| `docs.google.com/spreadsheets`, xlsx по ссылке | `sheet` |
| PDF/DOCX/Google Docs/страница-документ | `doc`, вид `documents`; больше данных — доп. виды |
| Moodle/ЦУ/иная LMS по разметке и адресам | `lms` + `site`/`portal` |
| страница входа, SPA, скрытые XHR | `site`/`portal`; вход — защищённые поля |
| файл из чата/шита | `file`, вид `documents` |
| «почта», «письма», «ящик» | `mail`; app password — защищённое поле |
| произвольный URL, «сайт с дедлайнами» | `site` + данные из пробы |

Двусмысленность — вопрос: «Это документ или раздел сайта, откуда ещё есть расписание?» Календарь и документ никогда не требуют
отдельного экрана.

### 3.4. Добавить / заменить / починить / дополнить

| Просьба | Действие |
|---|---|
| «добавь ещё календарь/таблицу/кабинет» | новый источник; ничего не заменяется |
| тот же нормализованный адрес/ссылка | «уже подключено»: название, статус, «дополнить», «перечитать», «починить» |
| «замени ссылку», «ссылка перестала работать» | замена секрета у названного источника; данные живут до первого успешного чтения |
| «почини», «почему не обновляется» | `REPAIR` с артефактами; итог в чате |
| «добавь ещё задания/оценки» к работающему | дополнить виды источника; прежнее не теряется |
| «удали источник/документ» | удаление с подтверждением; общий playbook остаётся |
| «подключи календарь», когда он уже есть | вопрос: «Добавить ещё один» / «Заменить ссылку у «X»»; при сомнении — добавить |

Добавление обратимо, замена ссылки — нет; поэтому при сомнении агент спрашивает, а если спросить нельзя — добавляет.

### 3.5. Секреты и ошибки

**Первичные секреты** — пароль, MFA, ключ-ссылка календаря, app password почты, токен по запросу сервиса — не попадают в историю
чата, промпт и артефакты: ввод защищённым полем задачи → API → Vault → воркер, агент получает только secret-хендл (`secret_use`).
**Cookie/bearer/storage/ сессия** — рабочий материал агента: читает, экспортирует, переиспользует, вызывает API от имени владельца
(D-008); в артефактах и логах сессия допустима, первичный секрет — нет. Ссылка календаря, вставленная в чат, распознаётся клиентом
и переводится в защищённое поле; сервер её в истории не сохраняет.

Проба не удалась → понятный текст и действия («ввести пароль», «дать ссылку», «другой адрес», «оставить как есть»), ничего не
создаётся до подтверждения. Вход/капча/антибот — технический барьер (D-007): агент пробует, при необходимости просит человека,
фиксирует барьер в трассе, а не выдаёт за «данных нет». Частичный успех — норма: «расписание нашёл, задания не нашёл — попробовать
раздел «Задания»?». Отмена и истечение черновика не трогают подключённые источники и данные.

## 4. Склейка и наслоение

### 4.1. Приоритет и доверие

Настройка — на пару **«вуз × вид данных»**, не на источник целиком. `primary` — источник, который решает конфликт и задаёт основу
вида (для `schedule` — кабинет, для `documents` — сайт кафедры); «основной источник» — настройка, а не архитектурный потолок:
источников сколько угодно, у каждого вида может быть свой основной, остальные — дополнительные. `priority` — упорядоченный список
источников вида (порядок заполнения пустых полей и разрешения конфликтов). `trust` — `high | normal | low`: решение владельца +
статистика health (успешные прогоны, drift, свежесть, полнота полей); влияет на порядок и пометку, но не удаляет данные. Без
явного выбора: сначала здоровые и свежие, затем выбранные владельцем, затем старые; отключённый основным не бывает, при
отключении/удалении выбор откатывается к правилу (как FR-054, `domain/primary.py`).

### 4.2. Дедуп: ключи и контент

Первичный ключ — `external_id`, если источник даёт стабильный id; иначе `match_key`: нормализованный естественный ключ
(`schedule`: дата/время + нормализованное название; `courses`: код/название; `deadlines`: срок + название; `documents`:
`sha256`/URL; `messages`: `Message-ID`; `news`: URL или заголовок+дата). `content_hash` — отпечаток содержимого; повторный sync не
создаёт дублей, изменение даёт новую версию. Склейка между источниками — один-к-одному, как сейчас в `domain/merge.py` для
занятий: время (±10 минут или сильное пересечение), похожесть названия, запрет склеивать разные типы (лекция/семинар,
занятие/экзамен). Те же принципы для других видов: задания по названию+сроку, курсы по коду/названию, документы по хешу/URL,
письма по `Message-ID`. Склейка **вычисляется при чтении** и не переписывает хранимые записи: sync пишет по источникам, провенанс
и обратимость выбора основного сохраняются.

### 4.3. Происхождение каждого поля

У склеенной записи в ответе API: `sources[]` (основной первым), `fieldSources` (какое поле откуда), `disagreement` (`time`,
`title`, `location`, `teacher`, `group`, `address`, `several`, `not_in_primary`). База — основной источник (его время, название,
тип); пустые поля заполняются по порядку приоритетов; непустые поля основного не перезаписываются; UI раскрывает «откуда это» и
открывает источник. Хранимые записи остаются по источникам — провенанс восстановим в любой момент.

### 4.4. Конфликты и расхождения

Расхождение не скрывается и не «усредняется»: оно возвращается в `disagreement` и показывается в карточке записи и источника.
`not_in_primary` — «похожее занятие есть у основного, а в этот час нет» (перенос/отмена) с теми же правилами охвата, что в
`domain/merge.py`. Инструмент `compare_sources` расширяется с расписания на любой вид: сколько записей, что только в одном
источнике, в чём расходятся, какое значение у основного. Смена основного — настройка (кнопка/чат), действует при следующем чтении;
данные не пересчитываются и не удаляются.

### 4.5. Файлы, документы и RAG

Загруженный файл — источник `file`; страница/PDF с сайта — артефакт этого сайта; «Документы» показывают документ с источником и
датой. Один документ из двух источников — одна запись с `sources[]`; разные версии — расхождение с датами/хешами. Новая версия
(`sha256`) создаёт версию артефакта, удалённый документ помечается отсутствующим. Отдельная сущность `documents` удаляется (05 §2.1).

Индексируется всё прочитанное: страницы, JSON, документы, письма, календарь, таблицы, вложения, скриншоты, ответы и факты. Чанк
хранит `user_id`, `source_id`, `artifact_id`, `data_kinds`, `playbook_rev`, `fetched_at`, `url`, текст, `tsv`, эмбеддинг; поиск
гибридный (Postgres FTS + pgvector + rerank), фильтры: вуз, источник, вид, свежесть (D-011). Инжест после каждого успешного прогона и
загрузки файла (`INGEST`), повтор по `sha256` идемпотентен; ответ чата ссылается на артефакт, источник и дату.

### 4.6. Что уже готово и что переделывать

Готово: склейка занятий N источников и выбор основного (`domain/merge.py`, `domain/primary.py`, `domain/repo._events`), провенанс
(`contracts/domain.schema.json`), `compare_sources`. Переделать: `sources/merge.py` — overlay для всех видов; `match_key`,
`content_hash`, `fieldSources`, `disagreement` вне расписания; `source_priorities` вместо `primary_schedule_connection_id`; дедуп
документов по артефактам/хешам.

### 5.3. Карточка источника

Шит (как `ConnectionSheet`, шире), разделы:

- **что это:** природа, вуз, хост входа, чипы видов, основной/дополнительный, доверие, дата подключения;
- **что знает:** счётчики по видам, охват дат, последняя синхронизация, сколько данных лежит; переходы в производные экраны;
- **как читает:** playbook — формат, ревизия, состояние, дата обучения, «посмотреть описание/код» с диффом и историей;
- **запуски:** `PROBE/CONNECT/SYNC/REPAIR` — время, результат, длительность, этап, ошибка, артефакты, «почему не получилось»;
- **ошибки и расхождения:** текущий `error_code`/`detail`, конфликты с другими источниками, «нет в основном», «Починить»;
- **действия:** перечитать/починить/дополнить виды/войти заново/заменить ссылку/сделать основным/спросить агента/открыть
  сайт/выключить/удалить;
- **автономия:** режим `auto`/`ask`/`never` по классам действий (D-006), частота, мягкий лимит стоимости, журнал действий;

| `POST /spaces/{id}/sources` | создать источник и задачу `CONNECT`: `{url?, fileAttachmentId?, title?, kinds?, note?}` → 202 `{sourceId, jobId}` |
| `GET /sources/{id}` · `PATCH /sources/{id}` | карточка; `{title?, kinds?, priority?, trust?, autonomy?, schedule?}` |
| `POST /sources/{id}/probe` · `/sync` · `/repair` · `/disable` · `/enable` | задачи и статусы |
| `PUT /sources/{id}/secret` | защищённая запись секрета (`ical_url`, `mail_password`, пароль) → 204, значение не возвращается |
| `GET /sources/{id}/runs?limit=` · `/playbook` · `/conversation` | история, описание/код ревизии без секретов, тред |
| `PUT /spaces/{id}/priorities/{dataKind}` | `{primarySourceId?, order?}` — настройка склейки |
| `GET /schedule` · `/deadlines` · `/tasks` · `/today` · `/grades` · `/spaces/{id}/documents` | как сейчас; + `space_id`, `source_id`; в ответе `sources[]`, `fieldSources`, `disagreement` |
| `GET /jobs/{id}/events` | SSE, как в `contracts/events.md` |

События SSE помимо существующих `status/block/block_update/error/done`:

| Событие | Данные | Когда |
|---|---|---|
| `source.status` | `{sourceId, status, error?}` | смена статуса/здоровья |
| `run.preview` | `{runId, kinds, counts, sample?, coverage?}` | проба нашла данные (превью, не текст модели) |
| `run.artifact` | `{artifactId, kind, name?, url?}` | сохранён артефакт |
| `run.done` | `{runId, stats, error?}` | прогон завершён |
| `playbook.revision` | `{playbookId, revision, state}` | новая ревизия/canary/откат |
| `merge.conflict` | `{spaceId, dataKind, entityId}` | появилось расхождение источников |

Job-типы: `PROBE` (проба без сохранения), `CONNECT` (проба + первый playbook + сохранение), `SYNC`, `REPAIR`, `INGEST`/`REINDEX`,
`CHAT`, `ACTION` (действие по политике). Долгие задачи остаются заданиями с `thread_id`: SSE, вопросы/ответы, `waiting_user`,
карточка `task` в чате; один источник одновременно обрабатывает одну задачу, повтор отвечает ссылкой на её тред.

### 6.4. Секреты и права в API

API возвращает только `storedSecrets: ["ical_url", …]` и «сохранён/не сохранён», никогда значения. Пароль/MFA/ключ-ссылка/app
password принимаются только защищённым полем и ходят API → Vault → воркер; в модель, историю, логи, артефакты не попадают.
Чтение/запись/удаление проверяют владельца (`user_id`), чужой id — 404; данные двух пользователей не смешиваются даже при общем
playbook.

## 7. Критерии приёмки и тесты

### 7.1. Критерии (FR-подобные)

- **FR-056.** University 1—N Source: сколько угодно источников; два кабинета на одном хосте, две таблицы/два календаря существуют
  одновременно; идентичность — адрес/ссылка/файл/решение владельца, не origin.
- **FR-057.** У источника несколько `kinds`; природа и виды данных определяются агентом при пробе, подтверждаются превью и правятся
  владельцем; UI показывает только виды с данными.
- **FR-058.** Playbook хранит вход, auth, эндпоинты, селекторы/код, sync-программу, health/test cases, провенанс, версии; исполняется
  в песочнице; recipe — частный случай; агент создаёт, правит и откатывает playbook.
- **FR-059.** «Добавить источник»: кнопка/чат → классификация → проба → kinds → превью → подтверждение → сохранение → первый sync;
  добавление/замена/починка/дополнение видов различаются; при сомнении агент спрашивает.
- **FR-060.** «Мои материалы» и отдельные «Документы и вложения» отсутствуют; файл из чата/шита — источник вуза; документы —
  производный экран с источником.
- **FR-061.** Склейка при чтении для любого вида: приоритет и доверие, дедуп по ключам/контенту, заполнение пустых полей,
  происхождение каждого поля, видимые конфликты.
- **FR-062.** «Основной источник» — настройка на «вуз × вид»; N=4/5/10 источников работают; отключение/удаление основного откатывает
  выбор.
- **FR-063.** RAG по всем артефактам; ответ чата ссылается на источник/артефакт/дату; изменения и удаления отражаются в индексе.
- **FR-064.** Починка: drift/ошибка → repair с артефактами и трассой → новая ревизия → тесты/canary → отчёт; неудача честно
  сообщается, данные сохраняются.
- **FR-065.** Карточка источника: что знает, когда синхронизировался, playbook и история запусков, ошибки, «починить», «спросить
  агента», настройки автономии.
- **FR-066.** Общие playbook'и и раздельные данные/сессии двух пользователей; личные параметры — в `source_bindings`, секреты — в
  Vault.
- **FR-067.** Первичные секреты не встречаются в промптах, истории, логах, артефактах, API; cookie/сессия доступны инструментам
  агента.
- **FR-068.** Миграция: старые подключения/рецепты/документы читаются как источники/playbook'и/артефакты; up/down/up проходят;
  «Мои материалы» переносятся без потери файлов.

### 7.2. Тесты

**L0:** нормализация `identity_key` (пути/порты/IDN/секретные query); валидация `kinds`; чистые функции overlay/дедупа/конфликтов
для расписания, заданий, курсов, документов; `fieldSources`/`disagreement`; схема/версии playbook; health/тесты; чанки с провенансом.

**L1 (`fakeuni`):** два источника на одном хосте и два календаря; источник с видами `schedule+deadlines+grades`; `PROBE` без записи →
`CONNECT`; классификация типов; файл из чата/шита — источник; `add/replace/repair/extend`; повтор адреса; N=4/5/10; основной и
отключение; конфликты и `not_in_primary`; RAG по артефактам; изоляция двух пользователей; общий playbook + раздельные сессии;
grep секретов; миграция up/down/up.

**L2:** «добавь ещё календарь» → новый источник; «замени ссылку у «…»» → замена; «почини» → repair; «это документ, а не сайт» → вид;
«добавь ещё задания» → виды; агент пишет playbook-код и чинит селектор на записанной фикстуре.

**L3 (живой вуз, 04-benchmark):** ВШЭ/ЦУ — вход, сессия, API, динамическая страница, парсер, превью, sync, ремонт, RAG-ответ.
Успех L1 не доказывает живой вуз; отчёт называет, что проверено, а что нет.

**Фронтенд:** Vitest — строка и карточка источника, шит «Добавить источник», «Документы» с фильтром, отсутствие маршрутов
«Мои материалы»/«Документы и вложения»/«Источники», фразы в чат. Playwright desktop/mobile: добавление через чат → источник в
списке; два источника на одном хосте; конфликт; документы с источником; доступность.

## 8. Открытые вопросы

1. **Почта:** app password + IMAP или OAuth; как фильтровать письма по вузу (отправитель, папка, метка)? Влияет на `auth.mode` и
   виды Vault.
2. **Порядок склейки:** общий список приоритетов на вид или ещё «сила источника» на каждый вид? Предложение: `source_priorities` на
   «вуз × вид» + `trust` на источник.
3. **`/study/documents`:** отдельный маршрут или документы в карточке вуза? Предложение: производный экран с фильтром по источнику.
4. **Файл без вуза:** спрашивать всегда или разрешать «источник вне вуза» на время выбора? Предложение: спрашивать; при отказе —
   черновик.
5. **Параметризация общих playbook'ов:** что выносить в `source_bindings` (группа, ОП, ящик); правило проверки на утечки при
   публикации.
6. **Хранение артефактов:** срок жизни HAR/скриншотов/страниц (предложение — 30 дней, кроме документов и процитированного), квоты,
   очистка.
7. **Карточка источника:** шит или маршрут для `botai://sources/{id}`? Предложение — шит.
8. **Названия:** подпись второго источника на том же хосте (предложение: спросить владельца, иначе «<вид> (2)»; для сайтов — хост в
   скобках).
