# План реализации BotAI v4: свободный harness

Статус: **draft 2026-10-31, пишется параллельно с аудитом и бенчмарком.** Это
большой план пивота: что удалить, что переписать, в каком порядке, какими PR и по
каким критериям принимать. Основание — [манифест](README.md),
[решения владельца](06-decisions.md), [целевая архитектура](02-architecture.md),
[источники и UX](03-sources-and-ux.md), [бенчмарк](04-benchmark.md),
[аудит as-is](01-as-is.md), [login UX](08-login-ux.md),
[production-инциденты логина](09-prod-login-incidents.md),
[лимиты и остановка research](10-limits-and-research.md).

Главный принцип плана: **ни один пункт не должен требовать от исполнителя
разрешения «архитектора»**. Если задача выглядит как «сделать можно», её делаем;
если нужен выбор — выбираем вариант, дающий больше возможностей агенту, и
записываем в [06-decisions](06-decisions.md). Ограничения — только продуктовые:
стоимость, время, сохранность данных владельца, стабильность production.

## 2. Целевая структура кода (ориентир, не догма)

```
backend/src/botai/
  agent/
    runtime.py          # цикл агента: думает, вызывает инструменты, сохраняет трассу
    context.py          # сборка контекста: задача, память, RAG, наблюдения, источники
    providers/          # deepseek.py, anthropic.py, openai_compat.py, mock.py
    tools/
      base.py           # Tool, ToolResult, JSON-схема, исполнитель
      http.py           # http_request: любой метод/URL/заголовки/тело
      browser.py        # navigate/click/type/read/eval/screenshot/cookies/storage/network/har
      code.py           # code_exec: python/js/bash в песочнице, файлы
      files.py          # fs_*: workspace агента
      secrets.py        # secret_use: брокер, хендлы, никогда не в промпт
      sources.py        # source_*: создать/обновить/проверить/синхронизировать playbook
      rag.py            # rag_search, rag_ingest
      memory.py         # memory_read/write, заметки
      jobs.py           # job_schedule/cancel/status
      traces.py         # trace_read: свои и прошлые трассы
      ask.py            # ask_user: вопросы и защищённый ввод
    executor/           # песочница исполнения кода: docker/local process, лимиты
    traces.py           # агентские трассы (не только job_events)
    policies.py         # политики автономии (auto/ask/never), а не запреты
  browser/
    control.py          # полный CDP/Playwright-контроль, несколько вкладок
    profiles.py         # persistent profile пользователя, копирование, импорт cookie
    login.py            # вход: нативные поля + автоматический, без архитектурных запретов
    screen*.py          # удалённый экран и капча как человек-в-цикле
  sources/
    manager.py          # создание/обновление/статусы источников
    playbooks.py         # версии playbook'ов, код+декларативная часть, тесты
    runner.py            # исполнение playbook в песочнице/браузере, canary
    merge.py             # наслоение данных (расширение domain/merge)
    calendar.py          # iCal, но уже как один из playbook'ов
  search/
    embeddings.py        # провайдер эмбеддингов, батчи, кэш
    hybrid.py            # FTS + vector + rerank
  api/                   # REST/SSE: источники, действия, трассы, бенчмарк
  ops/                   # миграции, диагностика, live-прогоны
```

### Фаза 0.5. Login UX и наблюдаемость [P0] — 5–7 PR

**Цель:** убрать production-боль логина и сделать её наблюдаемой. Основание —
[09](09-prod-login-incidents.md) (инциденты 31.10), [08](08-login-ux.md) (что уже

Код task-8 (0.5.1–0.5.3) уже сделан, task-9 закрывает 0.2/0.3 и остановку research;
0.5.4–0.5.7 — недостающие части плана.

- **0.5.1. Нативные поля — приоритет (native-first).** `browser/forms.py`,
  `browser/login.py`: распознанная credential-форма (логин/пароль, IdP/SSO-подсказки,
  скрытый пароль, email/телефон/«учётная запись») ведёт в поля BotAI; пресет
  `mode:"screen"` не отменяет распознанную форму; возврат к нативным полям после
  ввода на экране (08 §2.3). iframe/shadow DOM — известный предел, отдельная задача
  (09 §2.3). Критерий: на ЦУ/IdP-страницах поля BotAI, а не экран; тесты в

- **0.5.2. Ограниченное подтверждение «Я вошёл».** `browser/login.py` +
  `apps/web/src/features/remote-screen/`: `done_grace_s ≈ 90 с`, `max_done_tries = 3`,
  клиентский таймаут подтверждения и первого кадра, понятные ошибки `LOGIN_FAILED` /
  `done_unconfirmed` и повтор вместо `human_wait` 30 мин/TTL 600 с; экран не закрывается
  молча (08 §2.1–2.2). Критерий: после «Я вошёл» либо подтверждение, либо ошибка и
  повтор; нет многочасового `waiting_user` (09 §2).
- **0.5.3. Удалённый экран: качество, FPS, метрики, тикеты.** `browser/screen.py`,
  `apps/web/.../remote-screen`: FPS-first адаптация, `BOTAI_SCREEN_MIN_QUALITY=40`/
  `START=75`/`MAX=85`/`MAX_FPS` из env; персистентная диагностика `frames/bytes/fps/
  quality/rtt/dropped/close_reason` (расширить закрытый словарь `core/diagnostics.py`);
  WS close-code, новый тикет на реконнект, first-frame timeout 20 с и
  «Переподключиться»; первый кадр ≤2 с, нет 403-волн (08 §2.4–2.5, 09 §3).
- **0.5.4. Явные фазы CONNECT и остановка.** `jobs/runner.py`, `browser/login.py`,
  UI работы агента: фазы `login` → `research` → `sync` в состоянии задачи, трассе и
  чате; прогресс/ETA, кнопка «Остановить» на любой фазе, штатный исход остановки;
  фаза входа не маскируется под «подключение»; после `research` без прогресса —
  `source_no_progress` (0.2, 09 §2.1). Критерий: видно, что идёт — вход или
  исследование; 22-минутный лоудер после входа невозможен.
- **0.5.5. Caddy access-лог, таймауты, алерты.** `ops/deploy/*`, Caddyfile, runbook:

- **0.5.6. Network-first чтение источников.** `sources/runner.py`, playbook-раннер,

- **0.5.7. Секрет из чата.** `agent/chat.py`/API сообщений + secret broker: детект

### Фаза 1. Фундамент свободного harness [P0] — 6–9 PR

**Цель:** агент, который умеет всё, что умеет внешний harness, и оставляет следы.

#### 1.1. Agent runtime v4

- Новый модуль `agent/runtime.py`: цикл «собрать контекст → вызов модели →
  инструмент → наблюдение → трасса», поддержка нескольких моделей, стриминга,
  остановки/паузы/продолжения, вложенных подзадач.
- `agent/tools/base.py`: единый протокол инструмента (имя, описание, JSON-схема,
  исполнитель, таймаут, идемпотентность, политика).
- `agent/traces.py`: шаг, вызов, результат, токены, стоимость, артефакты, ссылка
  на задачу; запись в БД и файлы; API/инструмент чтения.
- Совместимость с существующими задачами: CONNECT/SYNC/REPAIR/CHAT на первом
  этапе можно оставить как вызывающие новый runtime с профилями.
- Тесты: L0 на цикл и трассы; L2 с живой моделью на `fakeuni`; бенчмарк B1–B3
  не хуже текущих.
- Критерий приёмки: агент решает задачу «зайди на `fakeuni`, найди расписание,
  сохрани источник» инструментами, без рецепта в коде, и любой шаг виден в трассе.

#### 1.2. Полный набор инструментов

- `http_request`: любой метод, URL, заголовки, тело, куки; ответ и ошибки
  структурированы; таймауты; редиректы; потоковая загрузка файлов.
- `browser_*`: навигация, клик, ввод, выбор, нажатия, ожидания, чтение DOM/текста,
  `eval` JS, скриншоты, cookie/localStorage/sessionStorage, перехват и
  модификация запросов, HAR, несколько вкладок/контекстов.
- `fs_*`: рабочая директория агента (per-task), чтение/запись/список/архив.
- `code_exec`: Python/JS/bash в песочнице с сетью и ФС workspace; установка
  пакетов — из локального кэша/интернета по политике; артефакты сохраняются.
- `secret_use`: получить хендл секрета, подставить в поле формы/HTTP-запрос/
  браузерный контекст; значение не печатается и не попадает в контекст модели.
- `ask_user`: вопрос с быстрыми ответами/полем/защищённым вводом.
- `job_*`: поставить/отменить/посмотреть фоновую задачу; расписание (cron).
- `rag_*`, `memory_*`, `trace_read`, `source_*` — см. фазы 2–3.
- Все инструменты описаны так, чтобы модель могла ими пользоваться без
  дополнительных «разрешений»; политика проверяется на уровне исполнителя.
- Критерий: агент в одном прогоне проходит: HTTP → рендер браузером → клик →
  чтение динамической страницы → запуск своего парсера → сохранение результата.

#### 1.3. Браузер под полным управлением

- `browser/control.py`: Playwright/CDP-обвязка без фильтров; любой домен,
  редирект, IP, WebSocket; downloads/uploads; service workers; несколько
  контекстов; сохранение и импорт storage state.
- `browser/profiles.py`: persistent profile пользователя на сервере и на маке;
  копирование реального Chrome-профиля (для «как текущее устройство»); импорт
  cookie из Chrome через CDP/Keychain-хелпер; выбор профиля на задачу.
- Egress: allowlist удалить; `browser/proxy.py` переписать в опциональный
  логирующий прокси (запись HAR/метаданных), по умолчанию прямой выход.
  Настройка `egress_mode="direct"|"log"`; в `log` — ничего не блокируется.
- Капча/антибот: определить, как реальный Chrome с профилем проходит проверку;
  человек-в-цикле через удалённый экран; повторные попытки с backoff;
  сохранение сессии; никаких архитектурных отказов.
- Вход и чтение: native-first и network-first из фазы 0.5 переносятся в новый
  браузерный/playbook-слой — нативные поля приоритетны, удалённый экран fallback;
  API первичен, DOM подсказка; экран отдаёт fps/quality/rtt/close-reason в трассу.
- Критерий: живой вход в вуз и чтение динамической SPA-страницы через новый

## 5. Миграция данных

- **Стратегия:** новая схема рядом (новые таблицы), перенос фоновой миграцией;
  старые `connections`/`adapter_specs`/`documents` читаются как fallback до
  приёмки. Владелец разрешил пересоздание (D-016), поэтому идеальная точность
  переноса не требуется, но данные не удаляются без нужды.
- **Перенос:** connection → source (title/entry_url/status; playbook из
  adapter_spec: код-декодер → декларативная часть, если код нет — «legacy recipe»
  playbook); документ → source вида `document` + artifact; календарь → source
  `calendar` с секретом в Vault; историю сообщений/память не трогать.
- **Сессии:** браузерные storage state из Vault переносятся в `browser_profiles`;
  cookie, которые не расшифровываются, — перелогин.
- **Откат:** флаг движка позволяет вернуться на старый путь; миграция схемы —
  отдельными ревизиями с downgrade; данные не перезаписываются на месте.
- **Production:** деплой по SHA, миграция на копии, smoke, затем переключение
  флага; данные аккаунта владельца можно пересоздать при проблеме.

## 6. Риски и как ловим

| Риск | Вероятность | Что делаем |
|---|---|---|
| Утечка первичного секрета в промпт/лог | средняя | broker-хендлы, маскирование в артефактах, тест «пароль не встречается в БД/логах/LLM-запросах» |
| Бан аккаунта владельца вузом | средняя | профиль реального устройства, троттлинг, человек-в-цикле; фиксируем барьеры в бенчмарке |
| Разгон стоимости модели | средняя | мягкие лимиты, аварийный стоп, видимый счётчик; без глухих стен |
| Потеря данных при миграции | низкая | новые таблицы рядом, fallback, бэкап перед миграцией |
| Нестабильность production при пивоте | средняя | feature-флаг, старый путь до приёмки, деплой по SHA |
| Промпт-инъекции со страниц вуза | средняя | инструменты и политики; агент видит источник; действия журналируются; не отключаем здравый смысл |
| Неизвестный портал не подтверждает вход (МИСИС) | средняя | probe/навигация, обучение пресета из ручного входа, честный `LOGIN_FAILED` с повтором (0.5.1–0.5.2) |
| Клиентские обрывы/VPN недоказуемы | высокая | Caddy access-лог, `dial_timeout`/`response_header_timeout`, алерты 499/5xx/WS-403 (0.5.5) |
| Секрет в истории чата | средняя | детект и маскирование сообщений до сохранения, broker, grep-тест (0.5.7) |
| Код агента ломает сервер | низкая | песочница исполнения, лимиты ресурсов, отдельный контейнер |
| Сложность кода вырастет быстрее пользы | средняя | фазы, feature-флаг, бенчмарк на каждом шаге; удаляем легаси после приёмки |

## 7. Definition of Done пивота

1. `docs/v4/` — единственная архитектурная правда; старые ADR и ограничительные
   документы удалены; README/AGENTS/QUESTIONS/testing не противоречат.
2. Агент проходит живой бенчмарк L3: вход, сессия, API, динамическая страница,
   действие, свой парсер, RAG-ответ — на ВШЭ и/или ЦУ, с реальными кредами,
   без утечки секретов.
3. Источники v4: два источника на одном хосте, два календаря, N источников —
   создаются, живут, склеиваются; «Мои материалы» и отдельные документы удалены.
4. Права: POST/формы работают по политике; журнал действий; капча/антибот
   обрабатываются технически.
5. Логин и наблюдаемость: native-first вход, нет вечного лоудера после «Я вошёл»,
   экран отдаёт fps/quality/rtt/close-reason, реконнект без 403-волн; CONNECT
   показывает фазы login/research/sync и останавливается; Caddy access-лог/499/504/
   WS-403 в алертах; network-first чтение (174 задания ЦУ); секрет из чата вычищается.
6. `make check` зелёный; миграции проходят; PWA работает на телефоне.
7. Отчёт владельцу: что проверено на живом вузе, что нет, сколько стоило.

## 8. Открытые вопросы (решаем по умолчанию, не блокируем)

1. **Где исполнять код агента:** локальный Docker-контейнер на VPS (по умолчанию)
   или отдельная машина? Решение: контейнер рядом, если не упрёмся.
2. **Эмбеддинги:** локальная модель на VPS или API? Решение: провайдер за
   интерфейсом, на старте — локальный/дешёвый API, выбор по бенчмарку.
3. **Профиль устройства:** копировать Chrome-профиль владельца на сервер или
   держать браузер на маке и подключаться к нему? Решение: серверный Chrome с
   импортом профиля; позже — опция «браузер на устройстве».
4. **Общие playbook'и между двумя пользователями:** по умолчанию общие; личные
   данные и сессии раздельны.
5. **Судьба старых данных:** пересоздать аккаунт при проблеме (D-016); сохранить
   историю чатов, если миграция бесплатна.
6. **TTL удалённого экрана:** сейчас 600 с без ввода (до 1800 с с вводом); после
   ограниченного «Я вошёл» ожидание всё ещё длинное — сокращать ли до 3–5 минут
   по умолчанию? Решение владельца, остальные пункты 0.5 его не ждут.

## 9. Что не делаем (non-goals v4)

- Публичная регистрация, биллинг, реклама, мультитенантная изоляция.
- Мобильные нативные приложения (PWA достаточно).
- Telegram и другие каналы, кроме PWA.
- Соблюдение ToS вузов как архитектурное требование.
- Идеальная совместимость со старыми рецептами — только пока удобно.
- Красивая документация ради документации: каждый документ должен помогать
  следующему агенту кодить.
