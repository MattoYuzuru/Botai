## Что осталось (по приоритету)

1. **Приёмка и включение v4 в production.** Задеплоить интеграционный SHA (деплой по SHA,
   авто-деплой на `main`), проверить pgvector/collation, образ песочницы, compose-поля
   `BOTAI_AGENT_*` (deployment.md, «pgvector» и «v4-агент в production»). После приёмки —
   добавить `BOTAI_AGENT_ENGINE=v4` в `/srv/botai/compose.vars` и выпустить деплой; smoke:
   движок виден в api/worker, `docker version` из worker, `code_exec` реально стартует
   sandbox-контейнер, остатки убираются.
2. **Сертифицированный живой L3** через v4 на задеплоенном SHA (ВШЭ; креды в Keychain,
   `bench/v4/run_agent.py`), отчёт: SHA, стоимость, что проверено/нет. После маскирования
   выводов инструментов блокирующий дефект закрыт — нужен финальный прогон.
3. **v4-чат.** Сейчас CHAT остаётся v3. Нужна совместимость: история треда, вложения,
   asking/approval-блоки, SSE-проекция событий задачи — без регрессии v3-чата.
4. **Чтение v4-данных продуктовыми экранами.** Строки домена с `source_id` уже пишутся, но
   расписание/задания/оценки/новости читают v3-подключения; нужна склейка/overlay v4-источников
   (`source_priorities`, провенанс, отключённые источники), затем удаление «Мои материалы» из
   модели/API (03 §1.6, FR-060).
5. **REST-sync → job'ы.** Сейчас sync из UI выполняется inline в API (браузерный playbook
   поднимает Chromium в контейнере API); правильнее ставить `SYNC` job в worker и убрать
   необходимость docker-сокета у API.
6. **RAG:** автоиндексация артефактов после run (хук `build_indexer`/`reindex_source_artifacts`),
   живой API-провайдер эмбеддингов (нужен ключ; `BOTAI_RAG_DIMENSION` фиксируется до миграции).
7. **Фаза 3.3/3.4:** фоновая автономия (расписания sync/health/repair) и управление стоимостью
   в UI; мягкие лимиты и hard stop уже есть.
8. **UI следующего шага:** runs-API источника + история запусков в карточке, политики
   автономии/журнал действий, trace viewer run'ов агента (`GET /api/v1/agent/runs/{id}/events`).
9. **Чистка легаси после приёмки v4:** удалить v3-мосты (`learn/`, старые job-пути, v3-only
   моки/документы), если они перестали быть нужны; production-данные — после бэкапа (D-016).
10. **Документация:** после деплоя обновить статус в этом handoff/README и `docs/development/testing.md`
    фактическим SHA и результатами приёмки.

## Границы свободы (не менялись)

- **Можно:** произвольная сеть, браузер с полным управлением, клики/ввод/JS, cookie/storage/HAR,
  запуск кода в песочнице, POST/PUT/формы, обход капчи и антибота техническими средствами,
  действия по политике владельца, свои трассы, Claude/DeepSeek/любые модели.
- **Нельзя только того, что вредит владельцу:** сливать пароли/MFA/ключ-ссылки в промпт, логи,
  историю, репозиторий; ломать чужие аккаунты/сервисы; удалять данные без бэкапа; выходить за
  pet-масштаб в мультитенантность.
- **Секреты:** первичные скрыты от модели и проходят через Vault/broker; сессия (cookie,
  токены, storage) — рабочий материал агента (D-008). Репозиторий публичный: никаких реальных
  кредов, cookie, персональных данных в коде/доках/тестах/коммитах; сырые артефакты живых
  прогонов — вне репозитория.

## Чего не делать

- Не спрашивать разрешение на действия, уже разрешённые в [06-decisions.md](06-decisions.md).
- Не восстанавливать старые запреты (два контура, allowlist, read-only, запрет кода/капчи,
  вырезание сессии) даже «для безопасности».
- Не выдавать непроверенное за проверенное: живой прогон фиксируется SHA, датой, сценарием,
  барьером и стоимостью; без этого — «не проверено».
- Не ломать production: деплой по SHA, бэкап перед миграциями, миграции на копии; v3 остаётся
  рабочим до приёмки v4.
- Не строить инфраструктуру «на всякий случай» (Redis/Kafka/отдельный векторный сервис) —
  только под конкретное ограничение.
