## 1. Итоги фазы 0 (read-only аудит)

- `grades.value/scale` — строки; числовых полей для графиков нет. Код и стайлгайд запрещают

- Кнопки «Продолжить» для остановленного чата в коде нет: есть только текст «Можно продолжить в
  этом чате» и карточка-failure.

### 1.2. Continuity (сейчас)

1. Чекпоинт `RunResult.messages` нигде не сохраняется и не читается (только тесты).
2. «Продолжай» = новый CHAT-job; контекст = текстовая история треда + системный промпт, который
   велит читать `trace_read` (`agent/v4/chat.py:99-100`). Трасса вдобавок неполная (результаты
   инструментов обрезаны до 4000 символов). Отсюда 1–3 млн токенов на продолжение.
3. Счётчики runtime живут в одном `run()`: `hard_stop_usd=2.0` действует на сегмент, а не на
   цепочку — каждое ручное продолжение получает свежие $2.
4. `BOTAI_AGENT_AUTO_CONTINUE=true` снимает все стопы, кроме $2 на run и таймаута воркера: включать
   нельзя.
5. Бюджет CHAT-job в воркере 900 с (`jobs/runner.py:98`) меньше `BOTAI_AGENT_LIMITS_SECONDS=1800`:
   таймаут превращается в `SOURCE_UNAVAILABLE` и ретрай хода с нуля. Вывод из кода, данными не
   подтверждён.
6. `can_resume` не включает `error` (503, `quota_exceeded`) — ровно то, что случилось 2026-11-03.
   `reasoning_content` в чекпоинте не маскируется; исключение между `tool_calls` и ответами
   оставляет «висячие» вызовы; переиспользовать `run_id` нельзя (уникальность `(run_id, seq)`).
7. Обрыв SSE job не отменяет (`sse.stream` только читает `job_events`; на фронте нет cancel при
   размонтировании). Теста на CHAT-v4 нет.

## 2. D-039. Персональные панели «Учёбы» — декларативные, из реестра компонентов

См. текст решения в [06-decisions.md](06-decisions.md#d-039). Кратко:

- **Гибрид.** Данные — в доменных таблицах с провенансом и детерминированным sync; панель — тонкий
  конфиг представления (`panels`), без самих данных.
- **Таблица `panels`**: `id, user_id (CASCADE), space_id (CASCADE), source_id (SET NULL), key
  (unique per space), type, spec jsonb, status (proposed|active|dismissed), visible, hidden_in_all,
  position, origin (system|agent), proposed_by_job_id (SET NULL), created_at, updated_at`.
- **Типы панели** (реестр компонентов): `kpi` (плитки-показатели), `chart` (bar/line),
  `table`, `ranking` (рейтинг/лидерборд), `profile` (карточка студента), `list`.
- **`spec` v1** — Pydantic discriminated union: `{v:1, title, icon (имя из реестра иконок),
  dataset: {kind: grades|profile|ranking, board?, courseId?}, view: {...по типу}}`. Только строки,
  числа и перечисления; никакого HTML/markdown/URL/JS. Лимиты как у `CHART_LIMITS`. Неизвестный
  тип на клиенте — скрыть, не падать.
- **Новые виды данных (v4)**: `profile` (поле → значение строкой, как дал источник) и `ranking`
  (`board, position, label, score, score_num, is_me, total, period`). Оценки — существующий
  `grades` + nullable `value_num`, `scale_max`.
- **Правило оценок.** `value_num/scale_max` заполняются, только если источник дал оба числа
  однозначно («8» из «10»). Приложение не усредняет и не пересчитывает шкалы; средние/рейтинг
  показываются, только если их дал источник (вид `ranking`/`profile`). Графики — отдельные оценки
  во времени/по предметам в шкале источника.
- **Системные панели.** После записи данных вида с шаблоном (grades/profile/ranking) домен
  идемпотентно создаёт активную панель по умолчанию (`origin=system`, unique `(space_id, key)`);
  студент может скрыть. Агент добавляет свои через `ui_propose_panel` (`origin=agent`, сначала
  `proposed`, после согласия — `active`).
- **Видимость** хранится на сервере (`PATCH /panels/{id}`: `visible`, `hidden_in_all`,
  `position`); `localStorage` — только свёрнуто/развёрнуто.
- **Место в UI.** Наверху «Учёбы» блок «Успеваемость» над карточками вузов и источников. В режиме
  «Все вузы» панели сгруппированы по вузам (монограмма + акцент `accentHue`), в режиме одного вуза —
  панели этого вуза. Desktop — сетка 2–3 колонки; телефон 390 px — одна колонка, KPI в ряд с
  переносом, без горизонтальной прокрутки страницы. Новых вкладок нет (D-013).
- **Иконки** — только из `packages/design/src/ui/icon/registry.ts`; бэкенд хранит список
  допустимых имён (`PanelIcon` Literal), vitest проверяет, что каждое имя есть в реестре.

## 3. D-040. Continuity: персистентный чекпоинт + авто-продолжение сегментами одного job

См. текст решения в [06-decisions.md](06-decisions.md#d-040). Кратко (вариант B′ аудита):

- Runtime остаётся с остановкой на мягком лимите (сегмент). Цепочкой управляет чистая функция
  `decide_continuation` (`agent/v4/continuation.py`). Продолжение — **тот же CHAT-job** через
  `JobDeferred`: SSE, отмена, `AGENT_BUSY`, идемпотентность ответа работают как раньше; слот воркера
  освобождается между сегментами; рестарт воркера возобновляет со снимка, а не с нуля.
- Таблица `agent_run_checkpoints` (PK `run_id`; `user_id`, `thread_id` CASCADE; `job_id` SET NULL;
  `chain_id, segment, parent_run_id, status, error_code, resumable, messages jsonb, message_count,
  bytes, format_version, cost_usd_chain, tokens_chain, continuations, chain_started_at, created_at,
  updated_at, expires_at`). Плейн JSONB с маскированием, как трассы; TTL 72 ч; потолок 6 МиБ с
  детерминированной компакцией старых tool-ответов (пары `tool_calls`↔`tool` не рвутся).
- Снимок сохраняется после каждого полного шага (с дросселем) и при отмене/исключении; висячие
  `tool_calls` закрываются синтетическими ответами; `reasoning_content` маскируется.
- **Условия остановки на границе сегмента** (по порядку): ответ получен → стоп; отмена студентом →
  стоп (чекпоинт resumable); **деньги цепочки ≥ `BOTAI_AGENT_CHAIN_HARD_STOP_USD` (2.0)** по
  `llm_usage` (переживает крах) → стоп, каждому сегменту `hard_stop_usd = cap − spent`; число
  авто-продолжений ≥ `BOTAI_AGENT_CONTINUATIONS_MAX` (5) → стоп; время цепочки ≥
  `BOTAI_AGENT_CHAIN_MAX_SECONDS` (3600) → стоп; квота суток ≥ 90 % → стоп; `quota_exceeded`
  `scope=minute` → пауза ≤ 60 с, иначе стоп; `llm_unavailable` → пауза 60/180/600 с, не больше 3
  подряд; нет прогресса (< 3 шагов или ≥ 3 одинаковых вызова подряд) → стоп; `hard_stop` → стоп;
  иначе мягкий лимит → продолжить сразу.
- **Чат.** Авто-продолжение показывается стадией/ThinkingBlock «Продолжаю автоматически (2 из 5):
  достигнут лимит шагов. Потрачено $0.42 из $2.00.» Стоп объясняется словами («Остановился:
  потрачено $2.00 из $2.00 на эту задачу. Прогресс сохранён — нажмите «Продолжить»»). Кнопка
  «Продолжить» на остановленном ходе; «Остановить агента» работает и в паузе.
- **Следующий ход.** Если последний ход треда остановлен не ответом и его чекпоинт свежий (< 24 ч),
  новое сообщение (кнопка «Продолжить», `retry_thread`, обычный текст) продолжает **от чекпоинта**
  с заметкой «окружение перезапущено»; `trace_read` больше не рекомендуется для продолжений.
- **Бюджет воркера.** Время сегмента ≤ бюджет CHAT-job − 60 с, чтобы сегмент заканчивался мягким
  `time_limit`, а не `SOURCE_UNAVAILABLE`.
- **Флаги.** `BOTAI_AGENT_AUTO_CONTINUE` удаляется (его семантика — «не останавливаться вовсе»);
  `BOTAI_AGENT_CONTINUATIONS_MAX=0` возвращает ручное поведение.
- **Метрики.** На сегмент: `input_tokens_at_start, tokens, cost_usd, trace_read_calls,
  checkpoint_bytes, message_count, compacted`; событие трассы `continuation` и диагностика
  `chain.segment`. «До» — замер по прод-данным до деплоя.

Проверки:

- **Независимое ревью continuity.** Нашло 11 дефектов, все исправлены до слияния.
- **Полный гейт на интеграционной ветке.** Backend 5002 passed; vitest: дизайн 866, web 909; Playwright `data-study-panels`/`data-study-v4`/`chat`/`data-agent-trace` — 106 passed.
- **Живой L2 (DeepSeek, fakeuni, локально, $0.19).**
  - Continuity: 4 сегмента одного job без действий клиента; каждый следующий сегмент стартует с чекпоинта (история 4 → 13 → 23 → 32 сообщения); DeepSeek принимает `reasoning_content`; `trace_read` — 0.
  - Остановки: по числу и по деньгам срабатывают; обрыв SSE ход не останавливает.
  - Продолжение следующим ходом: от чекпоинта — 0 `trace_read` и 0 повторных чтений, $0.0050. Через историю — 1 `trace_read` и 6 повторных чтений, $0.0075.
  - Discovery: модель находит оценки, рейтинг и профиль, проверяет их чтением, задаёт один вопрос с числами записей, расширяет playbook и синхронизирует; по просьбе предлагает валидную панель.
- **Production.**
  - ЛК-источник пилотного студента ВАВТ: `draft → active`, 48 оценок, автосинк каждые 6 ч (оператором, $0).
  - Все 48 оценок словесные (пятибалльная шкала и зачёты), поэтому графика нет: показываются KPI и «Последние оценки».
  - Дым-тест чата на чистом тестовом аккаунте: ответ за 1 шаг, чекпоинт `answer`/`resumable=false`.

Не проверено: пауза при 503 и квоте вживую, рестарт воркера посреди цепочки на проде, компакция
у потолка 6 МиБ, кнопка «Продолжить» в настоящем браузере, живой вуз с профилем/рейтингом.
Замер «до» (прод, 14 дней): продолжения тратили 3,96 млн токенов на job против 0,89 млн у
обычного хода; «после» на проде копится в диагностике `chain.segment`.
