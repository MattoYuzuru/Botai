# Login UX: нативные поля, удалённый экран, таймауты

Статус: **реализовано 2026-10-31**, пилот v4, task-8. Задача — убрать вечный
лоудер после «Я вошёл», чаще обходиться нативными полями BotAI вместо
удалённого экрана, не отдавать плохую картинку на медленном канале и дать
понятный исход при обрыве/таймауте. Основание — жалобы владельца и разбор
production: [09-prod-login-incidents.md](09-prod-login-incidents.md) (§2
«Я вошёл» → лоудер, §3 удалённый экран, §4 VPN/таймауты),
[02-architecture.md](02-architecture.md) §5 «Браузер» и §7 «Секреты»,
решения [D-007](06-decisions.md) (капча/антибот — техническая задача, человека
по-прежнему зовут), [D-014](06-decisions.md) (наблюдаемость; кадры и ввод не
пишутся).

Код: `backend/src/botai/browser/{login,forms,screen}.py`,
`apps/web/src/features/remote-screen/**`, тесты `backend/tests/browser/**`
и `apps/web/src/features/remote-screen/remote-screen.test.tsx`.

## 1. Как было и почему болело

Два пути входа. Основной — нативные поля BotAI: страница распознаётся в шаги
(`forms.detect`/`best_step`), значения спрашиваются через `ask`/`ask_secret` и
печатаются в страницу сервером. Запасной — удалённый экран (`browser.screen`):
кадры CDP-скринкаста в canvas, ввод человека назад в Chromium; сюда попадают
капча, незнакомые формы, ручной запрос «открыть браузер».

1. **Вечный лоудер.** `RemoteScreen.finish()` ставил `finishing=true` и слал
   `done`; сбрасывался флаг только при `success`. Сервер после «Я вошёл»
   продолжал проверять вход и, если подтверждения не было, слал `needs`
   («вход пока не подтверждён») и ждал дальше — до `human_wait_s` (30 минут).
   Кнопка всё это время крутилась, хотя экран просил продолжить на нём. Для
   МИСИС экран вообще жил до TTL (10 минут без ввода) и закрывался молча:
   задача отменялась «the login screen was closed», пользователь видел только
   «Подключение отменено» задним числом (09 §2.2–2.3).
2. **Слишком часто открывался экран.** Пресет с `mode: "screen"` (один раз
   экран понадобился) уводил на экран *любую* страницу, даже когда форма входа
   уже распознана, а возврат к нативным полям из `_human` требовал, чтобы
   человек ни разу не касался экрана (`not link.human_control`) — после первого
   же ввода он никогда не срабатывал. Распознавание `forms` не считало пароль
   в скрытом/невидимом поле и HTML без форм, поэтому guard иногда не видел, что
   страница всё ещё просит креды (`auth_ui_missing` в 09 §2.2, §5).
3. **Плохая картинка на медленном канале.** `QualityController` начинал
   адаптацию с JPEG-качества (`MIN_QUALITY=25`, старт 65) и только потом резал
   FPS; замеры production — 1,5–4,7 fps при 390×760 (09 §3). Читаемость экрана
   (качество) страдала первой.
4. **VPN/таймауты.** Клиент переподключался по обрыву WS (свежий билет), но
   если сокет открыт, а кадры не идут, экран оставался пустым без объяснения;
   человек не мог ни понять, что канал мёртв, ни перезапустить его вручную.
   Серверные таймауты (TTL, human_wait) не менялись: доказанной причины менять
   их нет — сервер по 09 §4 отвечал быстро.

## 2. Что изменено

### 2.1 Вечный лоудер: клиент (`apps/web/src/features/remote-screen/`)

`remote-screen.tsx`:

- `finishing` сбрасывается на `needs` (серверу нужен ещё шаг), на
  `success`/`expired`/`error`, на уходе WS из `live` (reconnecting/ended) и по
  клиентскому таймауту. Кнопка «Я вошёл» снова доступна, статус остаётся
  честным: «Вход пока не подтверждён…» или «Связь прервалась…».
- Клиентский таймаут подтверждения `DONE_TIMEOUT_MS = 90 000` (согласован с
  бэкендовым `done_grace_s`): если сервер не подтвердил вход, поверх экрана
  появляется предупреждение «Вход пока не подтвердился: экран не сообщил об
  успехе. Проверьте, что вход выполнен, и нажмите «Я вошёл» ещё раз.» Повтор
  отправляет новое `done`, а не висит на первом.
- Если `done` не ушёл (сокет в переподключении), вместо лоудера сразу
  показывается «Связь с экраном сейчас недоступна…».
- `expired` с причиной `done_unconfirmed` (сервер закрыл экран после
  неподтверждённого «Я вошёл») получает свой текст: «Вход не подтвердился после
  «Я вошёл». Начните вход заново.»
- Таймаут первого кадра `FIRST_FRAME_TIMEOUT_MS = 20 000`: если WS открыт, но
  ни одного кадра нет (медленный канал, чужой VPN), показывается «Экран не
  прислал ни одного кадра… Проверьте соединение и повторите.» и кнопка
  **«Переподключиться»**. Таймер заново взводится после каждого
  переподключения, т.е. молчащий канал не остаётся незамеченным. Это безопасно:
  сервер гарантирует первый кадр (`_ensure_first_frame` снимает скриншот, если
  страница не перерисовалась), а статичная страница без кадров — нормальный
  случай только *после* первого кадра.
- `remote-session.ts`: публичный `restart()` — новый одноразовый билет и новый
  сокет сразу, без траты бюджета автоматических попыток; старый сокет
  закрывается так, чтобы его `onclose` не запускал лишний реконнект. Это же
  переиспользуется кнопкой «Переподключиться».

Тесты: `remote-screen.test.tsx` — needs сбрасывает ожидание и повтор шлёт новое
`done`; таймаут подтверждения даёт текст и повтор; ошибка сервера убирает
лоудер; первый кадр/его отсутствие (+ после переподключения); `restart()`
берёт новый билет; истёкший экран с `done_unconfirmed`.

### 2.2 Вечный лоудер: сервер (`browser/login.py`)

- `LoginTiming.done_grace_s = 90.0`, `max_done_tries = 3`. «Я вошёл» — просьба,
  а не доказательство: после `done` поток продолжает проверять вход с
  `force=True`, но не бесконечно.
  - Вход подтвердился — как раньше, `link.succeed()`.
  - Нет подтверждения за `done_grace_s` и человек **не трогал экран** с момента
    «Я вошёл» — экран закрывается (`notify="expired"`, причина
    `done_unconfirmed`), поток падает с `BotaiError(LOGIN_FAILED)` «Вход не
    подтвердился: сайт не открыл учебный кабинет после «Я вошёл»…». Вместо
    30 минут ожидания и молчаливой отмены — понятный исход и повтор.
  - Человек продолжает работать на экране — окно ожидания сбрасывается, ему
    приходит `needs` «Вход пока не подтверждён: завершите его на экране и
    нажмите «Я вошёл» ещё раз». Слишком частые «Я вошёл» ограничены
    `max_done_tries`.
- Экран истёк/закрылся (TTL, браузер упал) без подтверждения — теперь
  `BotaiError(LOGIN_FAILED)` «Экран входа закрылся, а вход не подтвердился.
  Начните вход заново», а не молчаливый `JobCancelled` (09 §2.3, п. 3).
  Для этого у `ScreenLink` появились `close_reason` и `notify` у `close()`;
  `ScreenSession` хранит причину закрытия.
- `human_wait_s` остаётся 30 минут: это внешняя граница, а не путь к исходу;
  экран живёт по TTL 600 с (продление вводом до 1800 с).

Тесты `test_login.py`: «done, который сайт не подтвердил, заканчивается
понятной ошибкой» (экран закрыт `done_unconfirmed`+`expired`, ошибка
`LOGIN_FAILED`, сессия не сохранена), «истёкший экран без подтверждения —
понятная ошибка вместо отмены».

### 2.3 Нативные поля чаще

`browser/login.py`:

- Возврат к нативным полям (`link.close("mirrored")`) теперь не требует, чтобы
  человек ни разу не касался экрана: достаточно, чтобы появилась распознанная
  credential-форма, страница/форма отличались от выданной, и человек не трогал
  экран `resume_idle_s = 3` секунды. Явный ручной режим
  (`run.manual_requested`) по-прежнему уважается. Никогда не касавшийся экрана
  путь не изменился.
- Пресет с `mode: "screen"` больше не уводит на экран распознанную форму: на
  экран сразу идёт только `UnknownPage`, которую зеркалить нечем. Это прямо
  исполняет «в ЦУ лучше вводить в нативных полях — надо чаще»: выученный
  экранный режим — не запрет на нативные поля.

`browser/forms.py`:

- `has_credential_fields` считает пароль креденшелами, даже если контрол
  невидим/не зеркалится (скрипт откроет его позже), и узнаёт пароль в HTML,
  если сканер вообще не вернул форм. Это уменьшает ложные `auth_ui_missing`
  (guard не путал страницу с формой входа с кабинетом).
- Шире контекст распознавания: IdP/SSO-подсказки (`idp`, `identity`, `oauth`,
  `openid`, `saml`, `keycloak`, `realm`, `аутентификац`, `учётн…`), телефон и
  «учётная запись» как логин. Форма только с email/тел/логином теперь
  зеркалится на страницах IdP, а контактная форма телефона на обычной странице
  остаётся данными.

Ограничение, не исправленное здесь: `PageSnapshot` собирается по главному
документу (`browser/pagescan.py`), формы внутри iframe и shadow DOM сканер не
видит. Такие страницы по-прежнему уходят на запасной экран; чтобы зеркалить и
их, нужен отдельный обход фреймов в сканере (вне файлов этой задачи).

Тесты: `test_forms.py` — телефон/email/учётная запись на IdP-страницах,
контактный телефон не креды, скрытый пароль и пароль в HTML без форм,
`has_credential_fields`; `test_login.py` — пресет `mode: screen` зеркалит
распознанную форму, но незнакомую страницу всё ещё отдаёт человеку; возврат к
нативным полям после ввода на экране.

### 2.4 Удалённый экран: качество и FPS (`browser/screen.py`)

`QualityController` теперь приоритизирует FPS в обе стороны: на медленном
канале сначала понижается частота кадров (это не перезапускает скринкаст), и
только на её полу — JPEG-качество; на быстром канале FPS возвращается первым,
качество — последним. Пол/старт/потолок подняты: `MIN_QUALITY=40`,
`START_QUALITY=75`, `MAX_QUALITY=85`; значения клампятся в 1..100 и
`min<=start<=max`.

Параметры конфигурируются без перестройки, из env (новый
`screen_config_from_env()`, подключён в `get_screens`):

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `BOTAI_SCREEN_MIN_QUALITY` | 40 | нижний пол JPEG-качества |
| `BOTAI_SCREEN_START_QUALITY` | 75 | стартовое качество |
| `BOTAI_SCREEN_MAX_QUALITY` | 85 | потолок качества |
| `BOTAI_SCREEN_MAX_FPS` | 30 | потолок частоты кадров |

Лог закрытия экрана стал пригоден для разбора 09 §3 (раньше были только кадры
и вводы):

```
screen <id> closed (<reason>): 6345 frames, 1234567 bytes, 1048 inputs,
123 dropped, 4 restarts, quality=75 fps=20 rtt=42ms
```

`close_reason` — одна из причин (`ttl`, `success`, `browser closed`,
`mirrored`, …); она же отдаётся логике входа. RTT/quality/fps/dropped/bytes
хранятся только в логе: персистентные диагностические события требуют
расширения закрытого словаря `core/diagnostics.py` (вне этой задачи).

Тесты `test_screen.py`: FPS-first на медленном канале и восстановление,
конфигурируемые пол/старт/потолок, клампинг, значения из env, причина
закрытия `ttl`; интеграционный тест медленного/быстрого канала обновлён под
новый порядок адаптации. Заодно убран флейк проверки подписи билета
(`mac[-2:] = "AA"` иногда совпадал с исходной подписью).

### 2.5 VPN и переподключение

- Реконнект WS остался прежним по бюджету (<3 с, новый одноразовый билет на
  каждую попытку) — серверные таймауты не менялись.
- Добавлен клиентский таймаут первого кадра и ручной перезапуск канала
  (§2.1). После переподключения отсутствие кадров снова подсвечивается, а не
  остаётся «застывшей» картинкой.
- Первая попытка после повторного рендера блока (например, перезагрузка
  страницы с историей чата) может получить 403 на уже использованный
  одноразовый билет; клиент сразу переподключается с новым билетом через
  `POST /connections/{id}/login-session`, пользователь этого не видит. Так
  устроен существующий контракт (`contracts/events.md` §2), менять его в этой
  задаче не потребовалось.
- Caddy access-лог и transport-таймауты (09 §4) — эксплуатационная задача, не
  код логина; здесь ничего не менялось.

## 3. Что осталось и риски

1. **Подтверждение входа для неизвестных порталов.** `_try_finish` по-прежнему
   требует learnable probe или успешную проверку `entry_url`. Случай МИСИС
   (09 §2.3, §5): страница стабильна и похожа на кабинет, но confirm нет — вход
   теперь заканчивается понятной ошибкой, а не молчаливым TTL, однако
   подтверждение через probe/навигацию для неизвестных порталов не сделано.
   Это следующий шаг (нужен реальный портал или фикстура кабинета без
   известного probe).
2. **Научение пресета из ручного входа.** Если вход подтверждён только
   человеком на экране, а probe не выучен, пресет может не сохраниться/не
   ускорить следующий вход (09 §2.3, §7). Не менялось: требует отдельного
   дизайна «что считать успехом ручного входа».
3. **Исход по TTL.** Экран живёт 10 минут без ввода (до 30 минут с вводом);
   если человек не нажимал «Я вошёл» и не взаимодействует, исход наступает по
   TTL — теперь с понятной ошибкой, но ожидание всё ещё длинное. Сокращать TTL
   без решения владельца не стали.
4. **Iframe/shadow DOM** — см. §2.3, такие формы по-прежнему уходят на экран.
5. **Порог `done_grace_s=90 c`.** Очень медленный SSO (редиректы, 2FA на
   стороне вуза) может не уложиться, если человек после «Я вошёл» не трогает
   экран; он увидит понятную ошибку и сможет повторить вход. Порог
   настраивается тестами через `LoginTiming`, в проде — константа модуля.
6. **Метрики качества/fps/RTT** живут в логе воркера; для дашбордов/алертов
   нужно решение о персистентности (диагностика с закрытым словарём полей).

## 4. Как проверить

Целевые автотесты (Postgres: `make db` уже нужен для `test_login_db` и др.):

```bash
cd backend
uv run --frozen pytest tests/browser -q                 # весь браузерный набор
uv run --frozen pytest tests/browser/test_login.py -q \
  -k "done or screen_mode or quiet_normal or times_out"
uv run --frozen pytest tests/browser/test_forms.py tests/browser/test_screen.py -q
uv run --frozen ruff check . && uv run --frozen ruff format --check . && uv run --frozen pyright
```

```bash
pnpm exec biome check apps/web/src/features/remote-screen
pnpm --filter @botai/web exec vitest run src/features/remote-screen/remote-screen.test.tsx
pnpm --filter @botai/web exec tsc --noEmit
```

Живая проверка (креды только через secret broker Keychain, ничего не печатать):

```bash
python -m bench.live.run --scenario login
```

Что смотреть: `auth.session.ready`/`session.probe` после входа; в логах воркера
строку `screen … closed (…)` с `quality`, `fps`, `rtt`, `dropped`; на медленном
канале `fps` падает раньше, чем `quality` (и `quality` не ниже 40); после
«Я вошёл» либо `success`, либо `needs`/ошибка и закрытие `done_unconfirmed`, но
не многочасовая `waiting_user`. Ручной сценарий: открыть вход с распознанной
формой (должны быть поля BotAI, не экран), на медленном канале (VPN) — либо
кадр ≤20 с, либо сообщение и кнопка «Переподключиться»; нажать «Я вошёл», не
завершив шаг, — кнопка перестаёт крутиться, есть повтор.

Связь с решениями: D-007 — капчу/антибот по-прежнему проходит человек, экран
не отменяется; D-014 — кадры и ввод не записываются, добавлены только
счётчики в лог; §7 — нативный путь оставляет пароль вне экранного потока,
на экране ввод не логируется; D-008 — сессия остаётся рабочим материалом
инструментов, это не менялось.
