# ADR-0005: фабрика источников и самопочинка

- Статус: **accepted**, 2026-10-27
- Связь: FR-008–FR-011, FR-018, FR-031, FR-032, [contracts.md](../architecture/contracts.md), [HLD](../architecture/hld.md)

## Контекст

Источников много и они разные: JSON API личного кабинета, HTML-страница с новостями, Moodle с
токеном, iCal-ссылка, PDF с расписанием сессии, Google-таблица записи на экзамен. Владелец не
хочет писать парсер под каждый тип и каждый вуз: «агент должен сам структурировать».

## Решение

### Фабрика

Любой источник — это **подключение** с декларативной **спецификацией адаптера**. Фабрика по полю
`adapter` создаёт исполнитель из небольшого фиксированного набора; всё, что специфично для вуза,
лежит в спецификации, а не в коде.

| `adapter` | Что исполняет | Кто пишет спецификацию |
|---|---|---|
| `recipe` | HTTP по рецепту: ответы JSON (JSON Pointer) или HTML (CSS-селекторы) | Агент (Explorer) |
| `moodle_ws` | Moodle Web Services по токену пользователя (`core_calendar_*`, `mod_assign_*`, `gradereport_*`) | Шаблон + токен пользователя |
| `ical` | iCal-ссылка → события и дедлайны | Пользователь даёт ссылку |
| `document` | Файл или URL (PDF, DOCX, XLSX, HTML, Google Docs/Sheets экспорт) → текст → индекс; при наличии таблицы — извлечение строк по спецификации | Агент по образцу документа |

Новый тип адаптера — редкое событие и PR с ADR. Новый вуз или новый документ — только новая
спецификация, без кода.

### Агент не исполняет свой код

Агент **никогда** не пишет исполняемый код парсера. Он пишет спецификацию, которая проходит
JSON Schema и lint (нет личных значений, нет чужих хостов). Это главная граница безопасности:
текст со страницы вуза не может стать кодом на сервере.

Для неструктурированных документов (PDF с расписанием сессии в свободной форме) допускается
**разовое извлечение моделью при загрузке** с сохранением результата и происхождения; повторно
модель не вызывается, пока документ не изменился (хеш).

### Самопочинка

Поломка обнаруживается тремя путями: (1) Runner получил ответ, не совпадающий со спецификацией
(`recipe_drift`); (2) ежедневная проверка-канарейка на сессии автора рецепта; (3) студент пишет
в чат «расписание не показывается». Во всех трёх случаях создаётся задание **repair**:

1. Explorer открывает источник с сессией пользователя, сравнивает наблюдаемые запросы и разметку
   с текущей ревизией.
2. Предлагает новую ревизию, проверяет её на canary.
3. Применяет, если данные сходятся с последним подтверждённым снимком по ключевым полям; иначе
   спрашивает пользователя блоками `choice`/`confirm`.
4. В чате — короткий отчёт: что поменялось у вуза и что исправлено.

Пока идёт починка, пользователь видит прежние данные с меткой «обновляется», а не ошибку.

## Последствия

- Код адаптеров маленький и тестируется на фикстурах; разнообразие живёт в данных.
- HTML-рецепты хрупче JSON: вёрстка меняется чаще API. Самопочинка делает это дешёвым.
- Качество зависит от агента обучения; поэтому у каждой ревизии есть canary и откат.
