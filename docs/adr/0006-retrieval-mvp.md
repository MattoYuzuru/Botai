# ADR-0006: поиск для чата в MVP — SQL по домену + полнотекстовый поиск Postgres

- Статус: **accepted**, 2026-10-27 (выбор эмбеддингов отложен до приоритета 2, Q34)

## Решение

1. Вопросы о собственных данных («какая следующая пара») отвечаются **SQL по домену**, модель
   только формулирует ответ.
2. Документы и страницы индексируются **полнотекстовым поиском Postgres** (`tsvector`,
   конфигурация `russian`, `ts_rank_cd`). Исследование (RusBEIR) показывает, что лексический
   поиск силён на длинных русских документах.
3. Эмбеддинги — за протоколом `Embedder` с реализацией `NoopEmbedder`. Колонка
   `chunks.embedding` и расширение pgvector добавляются миграцией, когда выбрана модель и её
   размерность; гибридный поиск включается конфигом.
4. Корпус одного студента мал: при необходимости чат отдаёт модели документ целиком (контекст
   DeepSeek — 1M токенов) с кэшированием префикса.

## Почему

Владелец не хочет модель эмбеддингов на сервере без проверки его CPU; DeepSeek не даёт API
эмбеддингов. Лексический поиск плюс большой контекст модели закрывают MVP без нового узла.

## Наблюдение по серверу (2026-10-27)

`mnema`: 6 vCPU Xeon Gold 6240R **с AVX512-VNNI**, ≈ 10 ГиБ свободной памяти. Значит int8-модель
эмбеддингов (USER-bge-m3 int8 ONNX, ≈ 350 МБ) на этом сервере реалистична. Включаем её вместе с
пользовательскими источниками (приоритет 2), если FTS окажется недостаточным на реальных
документах; до этого — не тратим память, которую делим с Mnema.
