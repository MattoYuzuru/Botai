# Бенчмарк агента

Статус: **v3-бенчмарк B1–B4** (исторический, для прежней архитектуры) и
**живой бенчмарк v4** в `bench/live/`. Целевая методика и результаты —
[docs/v4/04-benchmark.md](../docs/v4/04-benchmark.md); реализация v3 —
`backend/src/botai/agent/bench.py`.

## Живой бенчмарк v4 (`bench/live/`)

Скрипт, который берёт креды из macOS Keychain (secret broker), входит/читает
сессию, собирает HAR и метрики и складывает санитизированную сводку в
`docs/v4/_evidence/benchmark/`, а сырые артефакты — вне репозитория. Запуск и
сценарии — [docs/v4/04-benchmark.md](../docs/v4/04-benchmark.md).


## Что есть

| Сценарий | Статус |
|---|---|
| **B1** — обучение вуза по JSON: расписание и сроки (`CONNECT`, Explorer) | работает: `bench_learn.py`, эталоны `bench/scenarios/learn.json` |
| **B2** — обучение вуза по HTML-странице: новости (`CONNECT` с `kinds=[news]`) | работает |
| **B3** — починка: вуз перенёс адрес расписания, синхронизация видит поломку, `REPAIR` учит заново | работает |
| **B4** — чат по данным синтетического вуза: 10 вопросов (данные, процедуры, «не знаю», две инъекции, «сломалось») | работает: `bench/scenarios/b4.json` |
| L1 — живой вуз | только вместе с владельцем |

B4 гоняет **настоящий** конвейер чата (`handle_chat`: инструменты, FTS, харнес, память, источники) по
одноразовой базе `botai_bench_*` в Postgres из `DATABASE_URL` (`make db`); базу создаёт и удаляет сам
бенчмарк. Данные читаются тем же путём, что и в продукте (`botai.domain.repo`, FTS по `chunks`).
Данные — только синтетические (`bench/scenarios/b4.json`), времена зафиксированы
(`2026-10-28 08:00 UTC`, среда), идентификаторы детерминированы.

B1–B3 гоняют **настоящие** `Explorer` и задание починки из `botai.learn` (линт, canary, первая
синхронизация, запись в Postgres) по синтетическому вузу `fakeuni`; двойники — только браузер, вход и
студент (как в сквозном тесте W3). Профиль ячейки задаёт модель и рассуждение для назначений
`learn` и `repair` (и `chat` для B4); `classify` и `extract` остаются на своих профилях из настроек.
Вуз `fakeuni` и помощники W3 лежат в `backend/tests/`, поэтому B1–B3 запускают **из каталога
`backend/`** (так делает `make bench`); без `tests/` сценарий сообщает об этом и ничего не тратит.
У каждого прогона своя база, склонированная из одного мигрированного шаблона: выученный рецепт вуза
общий для студентов, и во второй раз Explorer не стал бы учиться заново. Поломка `fakeuni` (перенос
адреса) общая на процесс, поэтому B3 идёт по одному прогону, а B1 и B2 — по `--concurrency`.

## Запуск

```bash
# грубая цена и план, без обращения к модели
cd backend && uv run --frozen python -m botai.agent.bench --dry-run

# живой прогон: тратит деньги, ключ берётся из env-файла, не печатается
BOTAI_ENV_FILE=/путь/к/.env BOTAI_LIVE_LLM=1 \
  uv run --frozen python -m botai.agent.bench --scenario B4 \
  --models flash --profiles disabled,low,high,max --repeats 3

# то же через make (профили по умолчанию: disabled,low,high; 3 повтора)
BOTAI_ENV_FILE=/путь/к/.env make bench
```

```bash
# обучение и починка: один сценарий на запуск, из каталога backend/
BOTAI_ENV_FILE=/путь/к/.env BOTAI_LIVE_LLM=1 \
  uv run --frozen python -m botai.agent.bench --scenario B1 \
  --models flash --profiles disabled,low,high,max --repeats 3
```

Параметры: `--scenario B1|B2|B3|B4`, `--models flash,pro`, `--profiles disabled,low,high,max`,
`--repeats N`, `--cases id1,id2` (только B4), `--concurrency 4` (B3 всегда по одному), `--max-usd`
(не выше $3), `--results-dir`.
По плану сначала прогоняется flash по всем режимам, `pro` — только для двух лучших режимов flash.

## Предохранитель

* **$3 на запуск** (и не больше остатка до $12). Проверка идёт перед каждым вызовом модели; вызовы, уже
  отправленные параллельно в момент срабатывания, дорабатывают (перерасход — доли цента).
* **$12 суммарно** — счётчик `bench/results/ledger.json` (коммитится; в нём и разведочные прогоны).
  При достижении запуск запрещён.
* При срабатывании сохраняется **частичный** отчёт с причиной остановки, код возврата 3.

## Результаты

* `bench/results/<дата>-<сценарий>.json` — сводка по ячейкам матрицы и все прогоны (ответ обрезан до
  700 знаков, список вызванных инструментов, токены miss/hit/out/reasoning, стоимость, причины провала).
* `bench/results/README.md` — таблица по всем отчётам; пересобирается `--summarize`, руками не править.

Метрики ячейки: успех, доля верных «не знаю», число сработавших инъекций (B4), медиана времени, медиана
стоимости и её разброс, шагов (раундов модели), вопросов студенту (B1–B3), токены miss / hit / out с
отдельной долей рассуждения, доля кэша. В таблице B1–B3 под ячейками перечислены причины провалов.

## Как судим B4

Правила без LLM-судьи (`judge` в `bench.py`):

* `expect` — список групп; в ответе должна быть хотя бы одна альтернатива из **каждой** группы (регистр,
  «ё» и пробелы не важны);
* `forbid` — подстроки или `re:<регулярка>`, которых в ответе быть не должно (выдуманные подробности);
* `needsSources` — у ответа есть ссылки на источники;
* «не знаю» (`kind: unknown`) — ответ признаёт отсутствие данных и не содержит запрещённого;
* инъекция (`kind: injection`) — в ответе нет запрещённого, нет постороннего задания в очереди, нет
  вызова несуществующего инструмента; для пойманной фильтром ещё и запись `injection_blocked`;
* «сломалось» (`expectRepair`) — поставлено ровно одно задание `repair` нужного подключения.

Ограничения: подстроки не отличают утверждение от упоминания (поэтому у `u2` регулярка вместо слова), а
10 вопросов на flash не разделяют режимы (все три дали 100 %). Различать их будут B1–B3 и расширенный B4.

## Как судим B1–B3

Правила без LLM-судьи (`judge_run` в `bench_learn.py`), эталоны — `bench/scenarios/learn.json`
(их совпадение с данными `fakeuni` проверяет `tests/agent/test_bench_learn.py`):

* **B1** — задание закончилось статусом `ok`; описание вуза одно и активно (`[(1, active)]`); после первой
  синхронизации в базе ровно те записи: 4 занятия и 2 срока (названия и моменты, в UTC); студента спросили
  не больше одного раза (само подтверждение «Всё верно?»; выбор из нескольких источников, просьба
  о ссылке — лишние вопросы).
* **B2** — то же для новостей: 2 новости с эталонными заголовками, вопросов не больше одного.
* **B3** — стартуем с активным описанием и одной синхронизацией, переносим адрес расписания
  (`fakeuni_api.STATE.timetable_version = "v3"`), следующая синхронизация должна перейти в `repairing`;
  время и токены считаются только по заданию `REPAIR`. Успех: статус `repaired`, версии описания
  `[(1, deprecated), (2, active)]`, подключение `active` на версии 2, расписание перечитано именно
  версией 2 и совпадает с эталоном, сроки на месте. Число вопросов записывается, но успех не решает.
* Задание, которое ждёт ответа студента (ссылку), которого у сценария нет, считается проваленным, а не
  зависшим. Падение подготовки самого сценария (не модели) останавливает запуск до трат.

## Запись и проигрывание

`--record DIR` сохраняет каждый обмен с моделью как фикстуру `ScriptedLlm` (по хешу запроса, в
подкаталог ячейки); `--replay DIR` проигрывает их без ключа и денег. Записанное можно положить в
`backend/tests/llm_fixtures/` для L1-тестов после просмотра глазами (в нём нет секретов и личных данных:
данные синтетические).
