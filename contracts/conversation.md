# Контракт треда: один агент, задачи в треде

Статус: accepted, 2026-10-30; обновлено 2026-10-31. Основание — [ADR-0013](../docs/adr/0013-unified-agent-hub.md) и [план агент-хаба v3](../docs/plan/agent-hub-v3.md) §3.1–3.4. Заменяет контракт подключения источника в чате от 2026-10-28 (`purpose`, `connectContext`, отдельные беседы подключения). Потребители: API/очередь/БД, агент, PWA (чат, список чатов, плашки источников). Пользователей нет, совместимость со старыми клиентами не требуется.

## Тред

Тред — единственная сущность разговора. У него нет назначения: любой тред умеет и отвечать, и подключать, чинить, входить, читать документы. Колонок `purpose` и `connect_context` нет. Связь треда с подключениями выражается только заданиями (`jobs.thread_id`).

```ts
type ThreadOut = {
  id: string; spaceId: string | null; title: string;
  createdAt: string; lastMessageAt: string;
  unread: boolean;         // есть сообщение агента (не строка прогресса) новее lastReadAt
  attention: "waiting_user" | "running" | "failed" | null;
  activeTask: { jobId: string; kind: "connect"|"repair"|"sync"|"ingest";
                connectionId: string | null; state: string; title: string } | null;
  preview: string | null;  // начало последнего текстового сообщения, ≤120 знаков
};
```

- `attention`: `waiting_user` — какая-то задача треда ждёт студента; `running` — идёт задача или ход агента; `failed` — последнее задание треда завершилось ошибкой и тред с тех пор не открывали.
- `activeTask` — задача треда, которой нужно внимание в первую очередь (ждущая студента, иначе новейшая идущая; продолженная родительская уступает дочерней). `title` — «Подключение: <название источника>», «Починка: …», «Обновление: …», «Документ: …».

| Метод | Назначение |
|---|---|
| `GET /api/v1/chat/threads` | все треды студента, по `lastMessageAt` убыванию |
| `POST /api/v1/chat/threads` `{spaceId?, title?, clientRequestId?}` | 201 `ThreadOut`; повтор `clientRequestId` с теми же `spaceId`/`title` вернёт тот же тред, иначе 409 `request_reused`; чужой `spaceId` — 404 |
| `PATCH /api/v1/chat/threads/{id}` `{title}` | переименовать |
| `DELETE /api/v1/chat/threads/{id}` | 204; в одной транзакции под тем же замком, что берёт отправка сообщения, останавливает идущие задачи и ход агента, удаляет сообщения и вложения; завершённые задачи остаются в журнале с `thread_id = null` |
| `POST /api/v1/chat/threads/{id}/read` `{upTo?}` | 204; `lastReadAt = upTo` (время последнего сообщения, которое клиент показал; не позже существующего), без тела — всё написанное к этому моменту. Сообщение, пришедшее после, остаётся непрочитанным; метка назад не двигается |
| `GET /api/v1/chat/threads/{id}/messages` | история |
| `POST /api/v1/chat/threads/{id}/messages` `{text: 0..8000, attachmentIds?: ≤10, clientMessageId?, targetJobId?, quote?: {text: 1..1000, blockId?}}` | 202 `{message, jobId}`; пустой `text` допустим только с файлами; `quote` — раздел «Цитата вопроса» |
| `GET /api/v1/chat/threads/{id}/runtime` | `ThreadRuntime` |
| `GET /api/v1/chat/threads/{id}/context` | шкала контекста |
| `GET /api/v1/me/memory`, `DELETE /api/v1/me/memory[/{id}]` | заметки агента о студенте: список, забыть одну, забыть все |

Чужой тред — всегда 404.

**Вложения.** Файлы загружаются заранее (`POST /api/v1/attachments`, до 20 МиБ, тип определяется по байтам) и остаются «неотправленными», пока их не несёт сообщение. `attachmentIds` привязывает их к сообщению в порядке списка; чужой или несуществующий файл — 404, уже отправленный — 409, больше 10 — 422; при любой ошибке не сохраняется ни сообщение, ни привязка. Сообщение получает блоки `attachment` (после текстового блока, если он есть). Документ (PDF, DOCX, XLSX, CSV, текст, HTML) сразу ставится на индексацию задачей `INGEST` в этом треде, в пространство вуза треда или в «Мои материалы». Файлы идут только агенту: сообщение с файлами не становится ответом на вопрос задачи (`targetJobId` с файлами — 422; без цели вопрос задачи остаётся открытым, а сообщение получает агент). Повтор `clientMessageId` возвращает то же сообщение с теми же блоками вложений.

**Цитата вопроса.** Сообщение студента, которое отвечает на вопрос, показывает его цитатой: короткая строка над текстом, как reply в мессенджере. Без неё нажатая кнопка быстрого ответа («Да») или выбранный вариант в ленте не говорят, на что отвечено. Цитата живёт в текстовом блоке сообщения: `TextBlock.quote = {text: 1..200, blockId?}` (`blockId` — цитируемый блок, если известен). Клиент присылает `quote` вместе с текстом кнопки быстрого ответа: вопрос последнего ответа агента простым текстом — последняя фраза со знаком вопроса, иначе последняя фраза; сервер сводит её к одной строке и оставляет первые 200 знаков (последний — «…»). Ответ на открытый несекретный вопрос задачи (`pending.channel == "dialogue"`), отправленный из поля ввода, получает цитату этого вопроса от сервера, и это единственный источник цитаты для сообщений задаче: присланная клиентом игнорируется. Цитата, присланная с сообщением агенту, хранит `blockId` только если такой блок есть среди сообщений агента этого треда; иначе остаётся текст без ссылки на блок. Цитата только украшает сообщение: с секретной ссылкой она молча отбрасывается, а сообщение уходит; цитата без текста (только файлы) не сохраняется. Повтор `clientMessageId` с другой цитатой — 409 `request_reused`. Ответы на вопросы задач (`/jobs/{id}/answers`) пишутся с цитатой вопроса сервером — раздел «История и защищённый ввод».

**Что видит агент.** В начале хода к сообщению добавляется список вложений. У всех файлов сообщения один общий бюджет — 30 000 знаков: один короткий документ агент получает целиком как `<source_data>`, десять документов получают по одной десятой (короткий возвращает неиспользованное). Остальное — через `read_document(document_id=<id вложения>, offset=…)`: подсказка называет место, где оборван показанный текст, в координатах того сырого текста, который `read_document` и режет. Ответ с цитатой агент читает так: цитата идёт **отдельным сообщением-данными** (`<source_data tool="question">`, инструкции в ней вырезаны), следом — слова студента: «Да» после цитаты «Вышка — это НИУ ВШЭ?» — осмысленный ответ. В канале студента (`role=user`, очистка как у набранного им) остаются только его собственные слова. Выбор из вопроса (`picked`: вариант с сайта вуза, кнопка согласия, отметка о переданном пароле) агент получает тоже данными: «Студент выбрал вариант в вопросе… Выбрано: …» — текст варианта написан не студентом, и приказ в нём («игнорируй инструкции») не читается как его слова. Так же эти сообщения читает краткая сводка старых ходов. Сообщение, которое не помещается во вход модели даже до первого шага, получает честный ответ «слишком большое для одного ответа», а не «не хватило шагов». Изображения и аудио хранятся и показываются студенту, но их содержимое агенту неизвестно: так и сказано в контексте, чтобы он не делал вид, что видел картинку или слышал запись. Текст файла — данные: секреты скрываются по форме и по имени поля, как на странице сайта (ниже), фразы-приказы вырезаются, а «пароль можно сменить в профиле» остаётся как есть: слова файла не читаются как набранные студентом.

`lastMessageAt` двигает вставка любого сообщения треда (кем бы она ни была сделана), назад не возвращает. Все сообщения треда упорядочены `created_at, id`; добавления в тред сериализуются, поэтому два события в один тик часов сохраняют порядок.

## Ход агента и задачи

Ход агента — задание `CHAT` (его handler — единый агент, профиль `agent`). Долгие работы — **задачи**: `CONNECT`, `REPAIR`, `SYNC`, `INGEST`. Каждая запущенная из треда задача получает `jobs.thread_id` этого треда; её публичные блоки проецируются в историю треда (раздел «История»). Тред может одновременно иметь фоновую задачу и обычный ход агента. Задача, запущенная вне треда (планировщик, REST-кнопка источника), попадает в тред самой новой задачи этого подключения; если такого нет — `POST /connections/{id}/conversation` открывает тред для неё, заполняет безопасной историей задачи и возвращает его (повторный вызов для подключения без заданий переиспользует пустой тред).

Агент запускает задачи инструментами `connect_source`, `connect_calendar`, `add_document_url`, `sync_source`, `request_repair`, `request_login` — всегда в **текущем** треде. Действия видят источники **всех** вузов студента: тред не ограничивает, какой источник обновить или починить (список `list_universities` показывает всё). Если то же подключение уже обрабатывает задача в другом треде, инструмент ничего не запускает и отвечает ссылкой на тот тред (`botai://threads/{id}`) и карточкой `task`, которая ведёт туда. Один и тот же адрес источника (origin) не подключается дважды: `connect_source` отвечает `exists` со статусом и ссылками. **Текущее ограничение, подлежит переработке:** решение владельца от 31.10.2026 — у вуза может быть сколько угодно источников любого вида, а «тот же» сегодня определяется по origin (`find_source`, по всем пространствам студента), без пути и вида: вторая таблица на `docs.google.com` или второй кабинет на том же хосте принимается за первый и возобновляется или дополняется ([план](../docs/plan/many-sources.md)). Создание пространства вуза и источника сериализуется теми же замками, что и REST (`university-space:{user}:{university}`, затем `source:{user}:{origin}`), поэтому параллельные запросы из чата и из формы дают одну запись. `connect_source` принимает название источника (`title`, не адрес сайта), вуз (`university_query` из вопроса студента) и необязательные `url`, `kind_hint`; без адреса источник создаётся пустым, и задача сама ищет вход. Календарь вуза по личной ссылке экспорта подключает отдельный инструмент `connect_calendar` (раздел «Календарь по ссылке»): ссылка не аргумент ни одного инструмента.

## Сообщения и маршрутизация

Сообщение студента идёт в **inbox задачи**, только если в треде есть задача в состоянии `waiting_user` с несекретным диалоговым вопросом (`pending.channel == "dialogue"`), либо если задан `targetJobId`. Иначе запускается `CHAT`, даже если фоновая задача идёт; `409` «уже идёт задание» из-за фоновой задачи не бывает.

- `targetJobId` обязан быть задачей (connect/repair/sync/ingest) этого треда: чужая, из другого треда или `CHAT` — 404; завершённая или уже продолженная другой задачей — 409 `stale_target`. Сообщение попадает в inbox и в этом случае, даже если вопрос не диалоговый.
- Сообщение, адресованное задаче, проходит `safe_text`: ссылка с секретом отвергается до записи (422). Сообщение для агента хранится как написано, но ссылка с токеном, кодом, JWT или учётными данными тоже отвергается до записи (422).
- Отправки в один тред и удаление треда сериализуются (advisory lock `thread-post:{id}`); тред, удалённый, пока сообщение ждало замок, для него «не найден». Задание нельзя поставить в несуществующий тред: `jobs.thread_id` — внешний ключ `ON DELETE SET NULL`.
- Пока в треде идёт `CHAT`, новое сообщение без `targetJobId` — 409 `agent_busy` «Ассистент ещё отвечает на прошлое сообщение».
- Личная ссылка календаря — экспорт с ключом в адресе (`webcal://`, файл `.ics`, `/export/ics`, путь `/ical/`, опубликованные адреса Яндекс, Google, Outlook, iCloud, Nextcloud; с `https://` и без) — в сообщении агенту или в ответе на вопрос задачи не сохраняется никогда: сообщение не пишется, не попадает в историю, задачу и ход агента, ответ — `409 secret_link_calendar`. Проверка выполняется первой, раньше адресата (`targetJobId`) и повтора `clientMessageId`. Открытый `.ics` без ключа (календарь праздников, страница про подписку) — обычная ссылка. Правила общие с клиентом, примеры — [`contracts/calendar-link-vectors.json`](calendar-link-vectors.json) (раздел «Календарь по ссылке»).
- Защита секрета: если у задачи треда открыт нативный секретный вопрос (`channel == "native"`, `secret`), то сообщение на неё по `targetJobId` и неадресованное сообщение, похожее на пароль или код, отвергаются 409 `secret_in_chat` до записи. Похоже: слово «пароль» (или «пасс») и следом слово («пароль: …», «пароль от ЛК qwerty12», «мой пасс Qwerty123»); код с цифрами после слова «код»/«смс» без постороннего слова («код из смс 424242», «код 123 456», «код подтверждения 1234»); токен или cookie; строка из цифр и разделителей, где цифр шесть и больше; в коротком сообщении (до четырёх слов) слово с буквами и цифрами вместе, символом или заглавной буквой внутри, длинная фраза через дефисы («это Qwerty123», «ivanov / Qwerty123»). Не похоже, и сообщение проходит: «да», «ок», «спасибо», «Привет!», «?», «2», название группы («ИВТ-21», «БПМ-231»), слово с годом («Москва2024»), число из четырёх цифр («2101»), «Код группы 2101», «Где мой пароль?», обычные вопросы и фразы. Защита работает в обе стороны: слова разговора не блокируются, а то, что набрано в чате вместо защищённого поля, не записывается и не попадает в историю, задачу и ответ ошибки.
- Повтор `clientMessageId` с теми же владельцем, тредом, текстом и target возвращает канонический ответ; другое содержание — 409 `request_reused`.

Все 409 на отправку сообщения несут в теле (`application/problem+json`) машинное поле `code`, по которому клиент решает, что делать:

| `code` | Когда | Что делает клиент |
|---|---|---|
| `agent_busy` | в треде ещё идёт ход агента | повторить отправку позже, сообщение сохранить |
| `secret_in_chat` | текст похож на секрет, а задача ждёт защищённый ввод | удалить сообщение из composer и не повторять; пароль и код вводятся в защищённое поле |
| `secret_link_calendar` | в сообщении личная ссылка календаря | удалить сообщение из очереди и хранилища; в поле вернуть остальной текст без ссылки; показать `detail`; тред уже задал вопрос про календарь, историю и runtime перечитать |
| `stale_target` | `targetJobId` завершён или продолжен другой задачей | перечитать runtime и адресовать актуальную задачу |
| `request_reused` | `clientMessageId` (или `clientRequestId` при создании треда) уже использован для другого содержания | сгенерировать новый идентификатор |

## Runtime

```ts
type ThreadRuntime = {
  activeJob: JobOut | null;   // задача, которой нужно внимание, иначе идущий ход агента; завершённая не остаётся
  tasks: JobOut[];            // новейшие задачи треда (до 20), новые первыми, включая завершённые
  pending: {jobId: string; blockId: string; channel: "native"|"dialogue"|"manual"|"approval"; secret: boolean}[];
  receipts: {jobId: string; messageId: string | null; blockId: string | null;
             status: "accepted"|"applied"|"superseded"|"rejected"; at: string}[];
};
```

Ровно одно из `messageId`/`blockId` в receipt заполнено. `pending` — открытые вопросы идущих задач: `dialogue` — несекретное уточнение (отвечается обычным сообщением), `native` — типизированные поля или выбор, `manual` — защищённый браузер, `approval` — конкретное write-подтверждение. В runtime нет значений ответов, билетов и кадров. Подробности активных блоков приходят существующим SSE `/jobs/{id}/events`; ответ на нативный вопрос — `/jobs/{id}/answers`; новый билет выдаёт `POST /connections/{id}/login-session`. Runtime перечитывается после `block`/`status`/`done` и действий человека.

## История и защищённый ввод

Каждый публичный блок задачи проецируется отдельным `ChatMessage` со стабильной идентичностью (upsert по id блока) и временем первого появления; очередное обновление «думаю» не перемещает его. Ответ человека — следующий user turn. Исторические controls read-only по `runtime.pending/receipts`. Блоки `login`, `input`, `choice`, `confirm`, `approval`, `wait` в истории становятся безопасной текстовой отметкой (кроме `confirm` с `details`, он остаётся блоком); ticket/wsUrl не сохраняются. Секретный ответ идёт существующим `jobs/answers` → Vault; история получает только отметку («Пароль передан», «Код передан», «Ссылка передана») без значения. Любой ответ на вопрос задачи (`/jobs/{id}/answers`) становится следующим сообщением студента (`picked: true`) с **цитатой вопроса** (`quote.text` — вопрос или суть предложения действия, `quote.blockId` — блок) и текстом словами: выбор — подписи выбранных вариантов (`label`, не `value`; «Другое» — введённый текст), согласие — подпись нажатой кнопки («Да, всё верно»), несекретное поле — введённый текст; необязательный одиночный вопрос без выбора — «Не знаю», пустой множественный — «Ничего не выбрано»; **любое поле входа** (`InputBlock.login = true`: форму входа рисует автор, и помечены все её поля — логин, пароль, код, номер студенческого, дата рождения) — без значения: «Пароль передан», «Код передан», «Логин передан» или «Ответ передан»; секретная ссылка (личная ссылка календаря, `inputKind: url`, `secret`) — «Ссылка передана». Поле входа никогда не задаётся как обычный вопрос в чате. Введённый текст, похожий на секрет, тоже заменяется «Ответ передан». Ответ в диалоге (несекретный `input`) — само сообщение студента, и цитату вопроса получает оно. Клиент до прихода этого сообщения ставит под вопросом такую же отметку (с цитатой и теми же словами), чтобы в ленте не было провала, и убирает её, когда пришло сообщение сервера с цитатой этого вопроса: ответ не показывается дважды. После ручной передачи (`manual`) старый auth-вопрос — `superseded`, а не фиктивно отвеченный. Write-подтверждение свободным текстом не подменяется.

**Вход после обновления.** Если плановое или ручное обновление источника с рецептом (`adapter = recipe`) закончилось статусом `needs_reauth` и подключение действительно ждёт входа, воркер **не запускает** окно входа сам: оно ждёт человека до получаса и занимало бы слот воркера, а когда протухли десятки источников, встала бы вся очередь. Вместо этого в треде источника (новейшая задача подключения, иначе новый тред) появляется сообщение агента «Нужно войти заново в «…»» со ссылкой на источник и кнопкой быстрого ответа «Войди снова в «…»»; тред становится непрочитанным, а пока источник ждёт входа, его тред получает `attention = waiting_user`. Нажатие отправляет агенту обычное сообщение, и агент вызывает `request_login`. Сообщение пишется один раз на протухание (не пишется, если задача источника уже идёт или с последней успешной синхронизации тред уже спрашивал). Одновременно идущих окон входа (`CONNECT` с `manual_login`) во всей системе не больше двух (и не больше `concurrency - 1` на воркер): остальные ждут в очереди, слоты остаются для работы, которая не ждёт человека. Токен, ссылка на календарь и отключённый источник входа через браузер не требуют, для них ничего не пишется.

Завершение задачи пишет одну итоговую строку по виду: «Подключение не завершено…», «Починка завершена.», «Данные источника обновлены.» и т. п. Подключение и документ итог пишут сами (см. ниже), общей строки к ним не добавляется. Ответ агента — одно сообщение `[text, task…]` (+ отдельное сообщение `plan`, если ход показывал план, и отдельное сообщение с шагами хода — блоки `thinking` в последнем состоянии, до 40 штук, — которое сохраняется прямо перед ответом: свёрнутый «Думал · N» остаётся над ним и после перезагрузки; такое сообщение не делает тред непрочитанным). Пока ход идёт, шаги приходят только потоком задания.

## Календарь по ссылке

Расписание вуза часто живёт в календаре (Яндекс, Google, Outlook): у календаря есть личная ссылка экспорта iCal, а её чтение не требует ни браузера, ни входа (адаптер `ical`). Ссылка открывает весь календарь, поэтому это секрет владельца: в чат она не вставляется, модель её не получает, ввод идёт **защищённым полем задачи** (API → Vault → воркер, как пароль).

> **Решение владельца 31.10.2026:** «У вуза может быть сколько угодно источников любого вида; ни один вид не ограничен одним источником» ([FR-055](../docs/product/requirements.md)). Второй календарь (например, Google при уже подключённом Яндексе) — отдельный источник, а не замена. **Текущее ограничение, подлежит переработке:** ниже описано, как работает код сегодня, и в нём календарь вуза **один**; вторая ссылка предлагается как замена первой (так выяснилось на production 31.10.2026). Что менять и в каком порядке — [many-sources.md](../docs/plan/many-sources.md). До переработки правила этого раздела про «один календарь», `replace_link` и вопрос «Заменить ссылку на новую?» действуют как написано.

- **Инструмент** `connect_calendar(university_id?, university_query?, title?, replace_link?)`. Вуз — как у `connect_source` (без аргументов: вуз чата или единственный вуз студента, иначе «нужно уточнение»). **Сегодня** календарь вуза **один** (`connections.kind = calendar`, `adapter = ical`; текущее ограничение, подлежит переработке): повторный вызов при идущей задаче отвечает «уже идёт» со ссылкой на её тред и карточкой `task`, при работающем календаре — статусом («уже подключён»). Новая ссылка спрашивается, если источник ещё без ссылки, в `needs_reauth` или `error`, либо при `replace_link = true` (старая не работает или студент хочет заменить; рабочий календарь при этом не сносится). Второй календарь тем же инструментом не подключается. Имени `url` у инструмента нет.
- **Задача** — обычный `CONNECT` с `payload.calendar = true` и `thread_id` текущего треда; `CONNECT` всегда с `connection_id`: источник (kind `calendar`, adapter `ical`, origin пуст) создаётся до постановки задачи под замком `university-space:{user}:{university}`. Любой вход, починка или ручной вход для такого источника (инструменты, REST) ставит ту же задачу «запросить ссылку заново»: браузер для календаря не открывается.
- **Ход задачи.** Текст с инструкцией для Яндекс/Google/Outlook (без вузовской специфики) → `input` `{inputKind: "url", secret: true, maxLength: 2000}` → проверка → при ошибке понятный текст и повторный вопрос (до 3 попыток; затем источник в `error`, рабочий календарь остаётся как был) → ссылка в Vault (`ical_url`) → спецификация `{adapter: "ical", origin}` (общая на origin, без ссылки) → чтение календаря и первая запись данных → источник `active` → сводка теми же словами, что у любого подключения (`learn/summary.py`: «Нашла в календаре: расписание — 124 занятия с 26 октября по 29 января — 14 недель, 2 задания со сроками», ближайшие два дня занятий) и закрывающее сообщение («Готово! … обновляется само каждые 3 часа — спросите, например, …»); отдельной строки «Источник подключён» нет, как у остальных подключений. История получает «Ссылка передана».
- **Проверка ссылки**: `https`/`http`/`webcal(s)` (всё хранится как `https` без порта и фрагмента), без логина и пароля, публичное имя хоста (IP в любой записи, `127.1`, `0x7f.1`, `localhost`, `.local`, `.internal` отвергаются; IDN переводится в punycode), только порт по умолчанию схемы (`https`, `webcals` — 443, `http`, `webcal` — 80); загрузка через EgressProxy с грантом на host ссылки, без cookies, до 10 МиБ и 30 с, редирект на другой host запрещён; ответ должен быть `VCALENDAR`. Причины отказа словами: ссылка не принята сервисом (401/403/404/410, «возможно, неполная или отозвана»), сервис отвечает ошибкой, открылась не выгрузка календаря, сайт не отвечает, адрес не ссылка или клиент не может его использовать. Запись в Vault идёт после проверки задачи и ставится назад, если регистрация источника не удалась: рабочий календарь остаётся с прежней ссылкой. Ссылку принимает только защищённое поле задачи: `PUT /connections/{id}/secrets` вид `ical_url` не принимает (`422`).
- **Ссылка в чате.** Клиент узнаёт личную ссылку календаря **до очереди отправки** (те же правила и те же примеры): в `localStorage` и на сервер она не попадает, остальной текст возвращается в поле, а тред просит сервер задать вопрос (`POST /chat/threads/{id}/calendar-link`, без тела, `204`; для нового чата клиент сначала создаёт тред). Сервер при любом пути, где ссылка всё же дошла (другой клиент, расхождение правил, ответ на вопрос задачи, `POST /jobs/{id}/answers`), делает то же: сообщение не пишется, `409 secret_link_calendar`. **Источник и задача при этом не создаются.** В тред пишется несекретное сообщение агента с кнопками, один раз, пока оно последнее слово треда: «Похоже, это личная ссылка календаря… Подключить календарь вуза «…»?» (кнопки «Да, подключить календарь», «Нет, это другое»); если вузов несколько и подсказки нет — «Для какого вуза подключить календарь?» с кнопками «Календарь для <вуз>» (до четырёх; больше — просьба написать название; вузов нет — просьба назвать вуз); если календарь вуза уже подключён — «Заменить ссылку на новую?» («Да, заменить ссылку календаря», «Нет, оставить как есть»; текущее ограничение, подлежит переработке: варианта «добавить ещё один календарь» нет); если поле для ссылки уже открыто в этом треде — «введите её выше», в другом — ссылка `botai://threads/{id}`; отключённый студентом календарь не трогается. Вуз — вуз треда (пространство «Мои материалы» считается за отсутствие вуза), иначе единственный вуз студента. Нажатие кнопки — обычное сообщение агенту, и агент вызывает `connect_calendar` (с `replace_link=true` для замены); защищённое поле открывает только эта задача.
- **Слот источников.** Задача календаря не держит слот «один источниковый браузер на студента» и не ждёт его: она не работает с браузером и сайтом студента. Но она держит воркер, пока человек ищет ссылку (до получаса), поэтому таких задач одновременно не больше двух на систему (и не больше `concurrency - 1` на воркер, `RunnerConfig.max_calendar_links`, как у окон входа), остальные ждут в очереди. Две задачи одного источника не идут вместе: пока календарная задача ждёт или работает, обновление того же календаря стоит в очереди (иначе оно прочитало бы заменяемую ссылку, получило 404 и объявило, что нужна новая). Задача, которая не дождалась ссылки (срок, отмена, остановка), оставляет не настроенный календарь черновиком, а работающий — как был.
- **Остальные ссылки с секретом** (токен, код, JWT, логин:пароль в адресе) по-прежнему отвергаются до записи (`422`), с понятным текстом: в ссылке есть секретный ключ, пароли и коды вводят в защищённое поле.
- **Где ссылки нет**: ни в БД вне `secrets` (шифртекст), ни в сообщениях и событиях задач, ни в запросах к модели, ни в логах и диагностике (строки логов скрывают ссылки календаря и ключи в query, `httpx` не пишет адрес каждого запроса), ни в ответах API (`storedSecrets: ["ical_url"]`).

## Блоки интерфейса

Схема — `contracts/agent-ui.schema.json`; Pydantic-зеркало — `botai.contracts.agent_ui`.

- `text` + `quickReplies?: string[]` (≤4, ≤60 знаков) — кнопки быстрых ответов под последним ответом; нажатие отправляет текст как сообщение студента вместе с цитатой вопроса. `text.quote` у сообщения студента — раздел «Цитата вопроса». `text.picked` — сообщение студента составлено не им, а выбором из вопроса (его пишет сервер).
- `input.login` — поле формы входа в источник (любое); его значение не показывается и не читается моделью.
- `confirm` `{id, question, confirmLabel, cancelLabel, details?: ≤2000}` — подтверждение; `details` (markdown) — то, что подтверждается: человеческая сводка собранного. Сводка, вопрос и кнопки — **одно сообщение**. Блок с `details` сохраняется в истории как есть (в остальном вопросы задач в истории — текстовая отметка), поэтому сводка не попадает в текст, который читает модель как историю; в контекст ответа входит только цитата вопроса.
- `plan` `{id, title, steps: [{id, title, state: pending|active|done|skipped}]}` — план ответа; блок с тем же `id` заменяет предыдущий (upsert в истории); повторный запуск того же задания продолжает свой план.
- `task` `{id, jobId, kind, title, state, threadId, connectionId?}` — карточка задачи; `threadId` — тред, где она живёт.
- `attachment` `{id, attachmentId, name, mime, size, kind: image|audio|document|other}` — вложение сообщения студента; содержимое отдаёт `GET /api/v1/attachments/{id}/content` (`botai://attachments/{id}` в тексте открывает вьюер).
- Markdown в `text.markdown`: GFM-таблицы, `**жирный**`, ссылки, списки, код и блок ` ```chart ` с JSON `{type: "bar"|"line", title?, labels: string[], series: [{name, values: number[]}]}`.

Ссылки между сущностями приложения — только `botai://threads|connections|documents|attachments/{id}`; клиент превращает их в `/chat?thread=…` и т. п. Голые идентификаторы в тексте для студента не пишутся.

## Итог подключения

Подтверждение подключения — одно сообщение `confirm`: в `details` — что найдено словами и ближайшие пары, в `question` — «Всё верно? …», затем кнопки. Текст собирает код по записям проверки (canary), в модель он не уходит; текст источника в нём очищен от разметки, чтобы не стать ссылкой или списком.

- **Что найдено** — счётчики словами вида данных: «35 занятий с 26 октября по 6 декабря — 6 недель» (недели считаются по календарю), «12 заданий со сроками», «8 курсов»; число без единицы («записей») не пишется, в шагах «Думает» тоже: «Найдено занятий: 35». Адреса из данных вуза в сводке сокращаются до хоста (без схемы, пути и параметров), чтобы ни один токен не стал ссылкой. Текст сводки при нехватке места обрезается по целым строкам, не посреди разметки.
- **Ближайшие пары** — два ближайших дня, в которых ещё есть занятия (с сегодняшнего, прошедшие пары не берутся; свободные дни пропускаются): «Среда, 28 октября» и список «13:00–14:20 · Базы данных · В-310» (время, название, аудитория; до восьми в день, дальше «…и ещё N»). Если будущих пар в данных нет, так и сказано.
- **Итог после подтверждения** — одна дружелюбная фраза без рода: что подключено и на сколько, как часто обновляется (по настоящему расписанию обновлений рецепта) и что спросить: «Готово! Расписание из «НИУ ВШЭ» подключено: 35 занятий на 6 недель вперёд. Дальше обновляется само каждые 3 часа — спросите, например, «что у меня завтра?»». Название вуза — сокращение из справочника (иначе название пространства) в кавычках после «из», никогда не в именительном падеже внутри предложения. Занятия в итоге считаются только впереди (с текущего момента): «35 занятий» — те же, что лежат впереди, а «на N недель вперёд» — число недель от сегодня до последнего занятия, округлённое вверх; прошедшая неделя в расчёт не входит. Если источник не обновляется по таймеру, фраза про обновление опускается. Сбой при составлении этой фразы не ломает уже подключённый источник: пишется простое предложение «Готово! Источник подключён: …».
- Починка при изменившихся данных показывает такое же подтверждение («Вот что читается теперь:»).

## Диалог воркера

`DialogueTurn(message_id, text, created_at, reply_to_block_id=None)`; отдельный runtime-checkable `DialogueContext`:

- `ask_dialogue(InputBlock) → str`, только несекретный learning input;
- `drain_dialogue() → list[DialogueTurn]` в серверном порядке, at-least-once до checkpoint;
- `checkpoint_learning(intent: dict) → None`: атомарно сохраняет проверенное намерение в `Job.payload.learning_intent`, подтверждает полученные turns и закрывает пройденный dialogue question.

`Job.payload.learning_intent`: `{entry_urls, requested_kinds, absent_kinds, user_note, discovery_mode?}`. Private dialogue cursor не попадает в API. Crash до checkpoint повторяет turn; повторное применение идемпотентно. `CONNECT` всегда запускается с `connection_id`: подключение (название — человеческое, пространство — вуз) создаёт `connect_source` до постановки задачи, поэтому вопроса «какой сайт подключить» у задачи нет.

## Несколько сайтов

Один recipe по-прежнему имеет один origin (это не ограничивает число источников вуза, [FR-055](../docs/product/requirements.md)). Явная ссылка человека на другой origin создаёт отдельный источник того же пространства и `CONNECT` в том же треде (`continue_source`); источник получает человеческое название, а не адрес сайта: по тому, что у него просили (курсы, задания, оценки — «Система обучения», одно расписание — «Расписание»), иначе «Источник»; если в вузе уже есть источник с таким названием, к нему добавляется сайт в скобках («Система обучения (study.example.org)»); родительская задача завершается статусом `continued`, а сообщение с `targetJobId` на неё — 409 `stale_target`. Bearer/пароль между origin не копируются; любое дополнительное разрешение сети ограничено конкретным host.

## Живое чтение источника

`browse_source` — единственный способ чата читать подключённый источник вживую: только GET, только хосты allowlist этого подключения, сессия студента берётся из Vault внутри инструмента и модели не показывается, заголовок и cookie не уходят на хост вне audience сессии. Адреса, похожие на действие (выход, удаление), не открываются. Открывается только то, на что источник сам указал: страницы из сохранённой карты разделов (`site_map`), ссылки со страницы, которую агент уже читал в этом треде (запоминаются по треду, `chat_threads.seen_links`), и адреса, названные студентом в этом вопросе. Адрес режется на целые слова по смене регистра и по `_ - . / & = ?` после раскодирования (в том числе двойного): глаголы действий (выход, удаление, запись, подписка, подтверждение, отмена, переключение, пометка, голосование, регистрация, сброс и т. п.) в пути и в параметрах отвергают его, даже если источник сам его показал; `/api/deleteItem`, `/doLogout`, `/log_out`, `/cancelBooking/5` — действия, `/address` и `/examinations` — нет. Каждый переход редиректа проверяется так же до отправки. Ссылка со страницы открывается в том виде, как её показала страница (с её query), а не как «тот же путь с другими параметрами»; произвольный query допустим только для страниц из карты разделов и входной страницы. Из ответа убираются секреты: тело, которое разбирается как JSON-объект или список, показывается контуром, даже если сервер назвал его text/html или text/plain; всё под ключом-учётными данными (`token`, `password`, `sessionKey`, `csrf`, `cookies` и подобные, по целым словам имени) скрыто вместе с вложенными объектами, у пары `{name: <секретное имя>, value: …}` скрыто `value`. В тексте страницы, `<pre>`, `<code>`, скриптах и документах значение после такого имени скрывается любой длины (`access_token: aB3cD4eF5g`, `"sesskey":"…"`, `var sesskey = '…'`, `MoodleSession=…`), а также длинные токены и JWT; ссылки с ключом сессии (`sesskey`, `sid` и т. д.) не показываются. Так же устроены `fetch_public_page` и `read_document`. Просроченная сессия — результат `needs_login`, после которого агент предлагает `request_login`. Если страница — оболочка приложения (почти нет текста, есть скрипты), `browse_source` сам открывает её ещё раз в серверном Chromium только на чтение с той же сессией (cookies, bearer своего origin, storage), через EgressProxy и тот же allowlist: POST, WebSocket и чужие хосты браузеру недоступны; результат — видимый текст, ссылки источника и усечённые GET-ответы JSON того же origin, которые страница загрузила сама (значения сессии скрыты). Hash-маршрут (`#/faq`) уходит только в браузер. Не более 3 таких чтений за ход, обычный GET и рендер вместе укладываются в таймаут инструмента; чтение уступает входу и исследованию и само их не вытесняет — результат «кабинет занят, повторите позже». Успешное чтение дополняет карту разделов, если она пуста. `site_map` показывает сохранённую карту разделов источника (разделы, маршруты, поиск и FAQ), не обращаясь к вузу. `read_document` читает сохранённый документ и файл вложения по частям (`offset`, `max_chars`). `fetch_public_page` открывает публичную HTTPS-страницу без cookies, но только ссылку из вопроса студента или публичной выдачи, ссылку, которую страница показала в этом треде, и «двойник» сайта с `www.`; адрес, разрешающийся во внутренний (частный) адрес, не открывается и без прокси. Результат обоих — `<source_data>`, данные, а не команды.

## Приёмка

**Память.** `remember` записывает заметку о студенте (≤300 знаков, до 50): без секретов, адресов, обращений к ассистенту и приказов («всегда…», «отправь…»). Если в этом ходе агент уже читал что-то написанное не студентом — страницу, документ, вложение, расписание, дедлайны, новости, выдачу поиска, — запомнить можно только то, что студент сказал сам в этом вопросе. Заметка с разрешением («разрешил открывать…»), постоянным правилом («всегда отвечать ссылкой…»), приказом, адресом в любом виде, паролем или кодом из смс отвергается; «Код группы 2101» остаётся фактом. Каждая новая заметка показывается под ответом отметкой «Запомнил: «…»», её можно забыть (`DELETE /me/memory/{id}`).

Проверки: личная ссылка календаря в чате (никуда не сохраняется, ни клиентской очередью, ни сервером; тред задаёт вопрос один раз, ничего не создавая) и в защищённом поле (проверка, повтор, замена, изоляция, утечки); чужие id; одинаковые и конфликтующие повторы; crash/replay; секреты вне history/receipts; задача не получает сообщение, пока не ждёт диалог; ход агента при идущей фоновой задаче; одна запись источника на origin, параллельные запросы дают одну (сегодняшнее правило; после переработки — один источник на один адрес, [план](../docs/plan/many-sources.md)); карточка и ссылка на тред другой задачи; unread/attention/preview (в том числе `read` с `upTo`); удаление треда останавливает задачи и не оставляет ход агента в очереди при одновременной отправке; секрет в чате в обе стороны; вложения: привязка, блоки, повтор, текст для агента, индексация; вход после `needs_reauth` без дубля. Живой вуз проверяет владелец.
